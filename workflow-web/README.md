# Workflow web adapter

Ordinary Java 17 library JAR; built with JDK 21. It depends on core's public contracts and supplies independently enabled viewer, administration, runtime-read and optional runtime-command groups. It installs no Boot auto-configuration, security, datasource, migration runner, transaction manager, global codec or advice.

Explicitly `@Import(WorkflowViewerConfiguration.class)` in the host and supply:

- `WorkflowViewerOptions("/your/api", "trusted.correlation.attribute")`; correlation attribute may be null. The base path must be nonempty, non-root literal path segments.
- `WorkflowViewerAccess`, using trusted request identity. `requireInstanceRead` applies to every read; `requireHistoryRead` additionally grants full retained evidence for history summaries/exact events. Throw `WorkflowViewerException` for unauthenticated (401), concealed missing/denied (404) or bounded failure (422). No permissive adapter is provided.
- Core's managed `WorkflowRuntimeQueryService` and `WorkflowDefinitionService`, with the host's existing transaction infrastructure.

`readableLinks(instanceId, candidates)` returns independent activity grants (`taskId=null`) and exact-task grants. Each returned grant must match a supplied candidate's activity and optional task. Missing grants hide links; adapter exceptions fail the read. Graph construction uses internal history summaries after INSTANCE authorization, without disclosing raw evidence or requiring HISTORY.

Routes relative to the configured mount are `/instances/{id}`, `/instances/{id}/graph`, `/instances/{id}/history` and `/instances/{id}/history/{sequence}`. Serialization and error handling are scoped to this controller. Plain configuration/controller classes and a dedicated viewer-only mapping make dependency inclusion or package scanning inert. Only one mount per application is supported.

History defaults to cursor zero and 50 rows, maximum 100. Summary pages preserve complete rows within dual 1 MiB limits. Exact events preserve stored details within dual 4 MiB and final UTF-8 envelope within 8 MiB; they are never truncated. Numeric Java longs serialize as strings. Graph pin, contiguous-prefix watermark and existing size/shape checks remain in the projection service.

The sandbox's gated configuration and `ConsoleViewerAccess` illustrate composition. APOLO integration and production security/dependency acceptance are separate work.

## Definition and catalog administration

Explicitly import `WorkflowAdministrationConfiguration` and provide `WorkflowAdministrationOptions(basePath, correlationAttribute)`, core's managed definition/catalog services, and each required host dependency:

- `WorkflowAdministrationIdentity.requireActorRef()`: authenticated stable actor; throw `WorkflowAdministrationException` for 401. Null/blank adapter results fail with `500 HOST_FAILURE`.
- `WorkflowAdministrationAuthorization.requireAdministrationAccess(actorRef)`: one administration grant for reads/writes; deny with the existing 403 response.
- `WorkflowAdministrationAuditRecorder.record(audit)`: synchronous same-transaction persistence, throwing unchecked on failure.
- A host-provided `java.time.Clock` and the existing `PlatformTransactionManager` governing both core and audit resources.

A host class may implement all three interfaces. Viewer activation and package scanning remain inert. Missing any required dependency fails administration activation. Hosts retain authentication and mutation CSRF protection. Every request obtains identity once and authorizes that actor once before parsing. Mutations require a nonblank String from the trusted request attribute (sandbox: `console.correlation`); missing/non-string/blank values fail with `500 HOST_FAILURE` before core, without client-header or generated fallback. Read correlation behavior is unchanged.

Reads call core directly. Shared web's internal `WorkflowAdministrationService` calls existing core commands and records only changed results through the host audit recorder. It captures the Clock once inside the mutation transaction, truncates to 100-nanosecond precision, and shares the context between definition operations and audit. Task-type core signatures remain context-free. `WorkflowAdministrationAudit` contains operation, entityKind/entityId, context, trusted correlationId and before/after core summaries (TaskTypeView, DefinitionView or DefinitionVersionSummary). Creation has null before; deletion has null after. Hosts own serialization, audit row IDs and storage schema. The sandbox preserves schemaVersion 1, its UUID correlation conversion, 512 KiB UTF-16 evidence bound and audit failure injection.

Hosts must enable annotation-driven transaction interception through existing Spring/Boot configuration. Shared web installs no transaction manager or `@EnableTransactionManagement`. Configure unambiguous manager selection when multiple managers exist; merely injecting a manager does not establish interception or select a different manager for annotations. Controllers call the managed service proxy. Public mutation methods use `@Transactional(propagation = Propagation.REQUIRED)`: service-owned transactions commit before returning to the controller; commit failures propagate. An outer host transaction owns completion when joined, so successful service return is provisional and the outer caller must complete it before reporting committed success. Audit failure rolls back a service-owned transaction or marks a joined transaction rollback-only. Do not use REQUIRES_NEW or automatic retries.

### F029 Java adapter migration

Replace the removed `WorkflowAdministrationHost` command-forwarding implementation with the three host interfaces above and supply the host Clock/transaction prerequisites. The sandbox's `ConsoleAdministrationHost` now supplies identity, policy and audit storage directly; `ConsoleManagement` is removed. No generic administration forwarding remains in the host. The shared coordinator is internal to web controllers despite Java-public methods for cross-package calls/proxying; it accepts an already authenticated and authorized actor and is not a supported host command API. Hosts with custom business orchestration continue to use core services under their own trusted boundary. Deploy compatible web/host adapters together; independently activated runtime groups are unchanged.

Routes are the existing `/task-types`, `/definitions` and `/versions` operations listed in [F014](../docs/features/F014-definition-catalog-administration/spec.md). IDs/tokens remain decimal strings; raw document import/replacement retains its 4 MiB UTF-8 limit, ordinary bodies 16 KiB, and exports return stored text. Local handlers retain management error categories and diagnostics, including 403 rather than viewer concealment. No task-type deletion, new authoring semantics or automatic write retries are supplied.

F023 successor-draft creation and draft deletion now use the shared F029 coordinator. POST `/versions/{id}/drafts` requires an empty JSON object and `X-Expected-Lock-Version` for the saved source. DELETE `/versions/{id}` requires the loaded token and no request body. Both return HTTP 200 using the core change/deletion result and preserve existing access, CSRF and error categories. Creation uses the normal version audit; deletion records the removed ID and summary as `before`, with `after=null`. Both audits belong to the same host transaction as the command. These commands have no automatic retry or receipt replay guarantee.

Before activating F023 writers, quiesce older definition writers and apply the core `highest_allocated_version` family-counter migration through the host migration owner. Deploy compatible writers together; mixed counter-unaware writers and downgrade to them are unsupported. Automatic creation allocates counter + 1; a new explicit import must exceed the counter, including when a lower gap was never used. Equivalent imports of retained versions remain unchanged. New allocations advance the family lock token; stale metadata editors must refresh. Deletion retains the family and counter, so deleting the highest or all drafts never restores lower-number capacity. See [F023 revision 3](../docs/features/F023-create-next-definition-version/spec.md).

## Runtime reads and optional command mapping

F015 adds two independent explicit imports: `WorkflowRuntimeReadConfiguration` and `WorkflowRuntimeCommandConfiguration`. Supply `WorkflowRuntimeOptions(basePath, correlationAttribute)` and the required `WorkflowRuntimeReadIdentity` and core `WorkflowRuntimeReadAuthorization` for reads, or `WorkflowRuntimeCommandHost` for commands. Neither import activates the other; broad package scanning remains inert. The read group additionally uses core query/definition services. The host owns authentication, CSRF, access policy and transaction infrastructure.

Read routes cover monitor, variables, assigned/instance tasks, exact task/contract/submission and activity/submissions, as inventoried in [F015](../docs/features/F015-runtime-task-instance-extraction/spec.md). The library-owned `WorkflowAuthorizedRuntimeReadService` supplies authorized pages and exact-resource access. The host supplies actor-only decisions; the monitor grant runs before query parsing. A filtered page may be empty with continuation; consumers must retain it. IDs/tokens remain decimal strings and pinned contracts retain existing fields.

F017 adds separate assignment and current assignee fields, plus pinned claim policy and server-derived ownership actions on the exact task contract. F026 makes assignment the effective current target; original assignment remains in immutable `TASK_CREATED` history. The read group can run by itself. History summaries and details for ownership events require the host's exact-task grant in addition to general history access.

The optional command group maps completion, claim, owner release and administrative release under `/instances/{instanceId}/tasks/{taskId}/{operation}`. Each operation has a matching lookup-only `/commands/{operation}/replay` route. Supply `X-Expected-Lock-Version` on both. Claim and release mutation bodies contain `commandId`, and `admin-release` also requires an exact reason. Replay bodies include the instance and task IDs. See [F017](../docs/features/F017-task-claim-release/spec.md) for the full request and result contracts.

The host creates trusted context and owns business authorization, transactions, durable handoff and post-rollback lookup. Preserve receipt-before-current-state validation. Ownership operations require the core ownership authorization adapter for exact-task business access and explicit administrative release permission. Replay uses current business access and the original receipt actor, independently of current membership or administrative permission. Sandbox start/replay routes and request linking remain host-owned.

F025 adds `POST /instances/{instanceId}/cancel` with exactly `{commandId, reason}` and lookup-only `POST /commands/cancel/replay` with those fields plus `instanceId`. Both require `X-Expected-Lock-Version`, canonical UUID/decimal-string transport and at most 16 KiB UTF-8 JSON. The reason is required, nonblank, valid Unicode and at most 2000 UTF-16 code units; it is retained exactly. Duplicate and unknown fields fail. Implement `WorkflowRuntimeCommandHost.cancel` and `replayCancellation`; mutation returns `{replayed, execution}`, recovery returns `{found, result}` with the cancellation command wrapper on a hit. Hosts return only after commit and recover in a fresh transaction after rollback, without retrying the mutation.

The independent read group adds `GET /instances/{instanceId}/cancellation-availability`, returning exactly `{allowed, lockVersion}` after current instance access. The optional `WorkflowCancellationAvailabilityContextHost` supplies trusted operation context only after instance read authorization and the ACTIVE check, when `WorkflowCancellationAuthorization` is configured. Missing support suppresses availability; actor mismatch fails as HOST_CONFIGURATION and authorization adapter failures fail closed. Availability is advisory and ACTIVE-only. Core requires `WorkflowCancellationAuthorization` for both commands and replay: current business access is separate from fresh cancellation permission, and only USER actors are supported. Original-actor replay requires current business access but no continued cancellation privilege. The sandbox's `ConsoleWorkflowCancellationAuthorization`, `ConsoleRuntimeTransaction` and `ConsoleRuntimeCoordinator` demonstrate linked-instance access, administrator permission and transaction/recovery composition; cancellation preserves request status and links. Deploy cancellation-aware core/web/host adapters together.

Cancelled graphs retain the stopped human node with state `CANCELLED`, retain prior traversed edges and add no outgoing traversal. Instance/activity cancellation history uses general history access; `TASK_CANCELLED` summaries and details use the exact-task grant. Existing task/submission authorization remains in force.

F026 adds `GET /tasks/administration` to the runtime read group. Implement the separate `WorkflowRuntimeReadAuthorization.canAdministerTasks(actorRef)` grant and `canReadTask(context)` row policy. The collection defaults to OPEN and accepts status (OPEN/COMPLETED/CANCELLED/ALL), taskType, assignmentKind, assignmentRef (requires kind), assigneeRef, instanceId, afterId and limit (default 50, maximum 100). The authorized facade supplies one bounded metadata candidate page, filters through host policy and preserves source continuation, including an empty filtered page. Core's joined administration query supplies pinned node/type labels without fetching metadata per row. The wire projection omits outcomes and closure attribution; protected review data remains behind exact-task reads.

Task administration additionally accepts optional `taskName` (nonblank Unicode, at most 200 UTF-16 units). It matches a case-insensitive literal substring of the pinned display name within the bounded candidate page; empty results may retain `nextAfterId`. Other filters keep exact semantics.

`GET /tasks/{id}/reassignment-availability` returns `{allowed, instanceLockVersion}` after exact-task authorization, with false as the default for unsupported hosts. `GET /tasks/{id}/reassignment-targets?kind=USER|GROUP|ROLE&query=...&cursor=...&limit=...` requires exact-task access plus `canReassignTask` before calling the host's `reassignmentTargets` directory lookup. Query is bounded to 200 UTF-16 code units; cursor to 1000; target pages default to 20 and allow at most 50 `{ref,label}` choices with `nextCursor`. The UI exports matching TypeScript `WorkflowReassignmentTarget` and `WorkflowReassignmentTargetPage` contracts; this does not change the endpoint, host bean registration or opaque cursor format. Adapter failures fail closed. Directory choices are advisory and must be revalidated in core command authorization.

Implement optional `WorkflowRuntimeCommandHost.reassign` and `replayReassignment` to enable F026 mutation/recovery. `POST /instances/{instanceId}/tasks/{taskId}/reassign` accepts exactly `{commandId, assignment:{kind,ref}, reason}`; `POST /commands/reassign/replay` adds instanceId/taskId. Both require `X-Expected-Lock-Version`, canonical UUID/decimal-string transport, the existing 16 KiB bound and duplicate/unknown-field rejection. Reason is exact, nonblank, valid Unicode and at most 1000 UTF-16 code units. Mutation and lookup use the existing task-bearing result wrappers. Hosts return only after commit and perform post-rollback receipt lookup in a fresh transaction; they never automatically retry mutation. Core requires `WorkflowTaskReassignmentAuthorization` for current business access, fresh permission and destination suitability. Successful original-actor replay needs current business access but no continued reassignment privilege or destination lookup. Deploy compatible core/web/UI/host adapters together; older writers/readers enforcing creation/current-target equality cannot coexist once reassignment is used. See [F026](../docs/features/F026-task-administration-reassignment/spec.md).

Definition-family lists additionally accept `order=ASC|DESC` (default ASC). DESC starts at omitted/zero afterId and continues with IDs strictly below nextAfterId; keep the same order while paging. The sandbox Definitions page requests DESC so newly created families appear first. Existing consumers that omit order keep ascending paging; the separate start chooser is unchanged.

F022 adds `previousDecisions: {mode: "NONE" | "ALL_PREVIOUS" | "SELECTED"}` to the exact task contract and `GET /tasks/{id}/previous-decisions?afterSequence=0&limit=20` to this same read group. Every page checks the receiving-task grant; no source-task grant is required and source submission/history endpoints keep their existing protection. Pages contain only decision attribution and original comments, with exact decimal-string IDs/sequences and whole-entry continuation within 256 KiB in UTF-8 and UTF-16. Limit is 1–50, default 20; duplicate/unknown query fields and invalid decimal values fail with HTTP 400.

Hosts using their own facade may call core's `previousDecisionsPolicy(taskId)` and `listPreviousDecisions(taskId, afterSequence, limit)` after applying their own exact receiving-task read authorization. These detached DTO queries participate in the host's read transaction and grant no source-resource access. See the [F022 contract](../docs/features/F022-previous-decision-comments/spec.md).

### F028 completion adapters

Hosts offering completion must register exactly one core `WorkflowTaskCompletionAuthorization` and exactly one `WorkflowTaskCompletionValidator`, including for existing published workflows. `canAccess(TaskEligibilityContext)` protects mutation and receipt lookup using current business access. `canComplete(TaskCompletionContext)` protects fresh decisions; it is separate from the advisory runtime-read `canCompleteTask` hint and engine assignment eligibility. Missing or ambiguous adapters fail with `HOST_CONFIGURATION` (500). Read-only hosts need neither adapter.

Fresh completion validates the pinned outcome/comment/result structure, then invokes completion permission, general business validation and the existing optional F018 submission validator. General validation runs for every result mode, including FORBIDDEN and omitted OPTIONAL results. A host that needs no additional business check must still register an explicit validator that returns normally. Throw core `TaskCompletionRejectedException` for a sanitized business rejection. Completion permission denial maps to `COMPLETION_FORBIDDEN` (403), explicit business rejection to `BUSINESS_VALIDATION_REJECTED` (422), and unexpected validation failure to `BUSINESS_VALIDATION_FAILED` (503); arbitrary provider messages are not returned.

Original-actor receipt recovery requires current business access, but skips fresh permission and both validators, including when the general validator is unavailable. Lookup-only misses also skip fresh hooks. Host completion/recovery adapters must delegate to this boundary without first requiring current exact-task read visibility. Preserve the existing host transaction and post-rollback lookup in a fresh transaction. Validation runs within the completion transaction; hosts remain responsible for locking/version guards that protect authoritative business data through commit and for keeping effects outside validation hooks. HTTP payloads, success responses and receipt formats are unchanged.

### F027 Java adapter migration

`WorkflowRuntimeReadHost` is replaced; migrate custom restrictions explicitly, without a legacy page-provider fallback. Supply `WorkflowRuntimeReadIdentity.currentActorRef()` from authenticated server context and core `WorkflowRuntimeReadAuthorization`. The seven data-returning methods now belong to `WorkflowAuthorizedRuntimeReadService`: `listInstances(actorRef, query)`, `listMyTasks(actorRef, afterId, limit)`, `listInstanceTasks(actorRef, instanceId, afterId, limit)`, `listAdministrationTasks(actorRef, query)`, and `instance/task/activity(actorRef, id)`. Ordinary reads need no command context. Web configuration constructs the concrete facade with the existing core query and eligibility services; importing core alone requires no read policy.

Map monitor/admin collection grants to `canMonitor`/`canAdministerTasks`, monitor metadata to `canListInstance`, and exact-resource decisions to `canReadInstance`, `canReadTask` and `canReadActivity`. Completion remains a default-false advisory `canCompleteTask` hint. Ownership, reassignment and cancellation availability reuse their existing core authorization adapters; those adapters remain independent of broad read grants. Shared web retains command-activation gates for ownership hints, while completion remains visible independently of command activation.

Optional `WorkflowAssignmentDirectory` owns `assignmentLabel(task)` and `reassignmentTargets(context, kind, query, cursor, limit)`. Label-only implementations work: inherited search denies with 403 REASSIGNMENT_FORBIDDEN after normal exact-task/permission checks. Missing, blank, invalid, overlong or failing labels fall back to the stored assignment reference; explicit search overrides retain bounded opaque-cursor behavior.

My Tasks combines host task visibility with core current-assignee OR assignment eligibility, without ownership authorization. It remains personal even for administrators. Instance-task lists retain bounded refill (500 candidates); monitor and administration retain one candidate page without refill. HTTP/UI contracts and optional command activation are unchanged. See [F027 revision 6](../docs/features/F027-runtime-read-policy-separation/spec.md).
