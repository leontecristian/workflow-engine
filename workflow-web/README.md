# Workflow web adapter

Ordinary Java 17 library JAR; built with JDK 21. It depends on core's public contracts and supplies independently enabled viewer, administration, runtime-read and optional runtime-command groups. It installs no Boot auto-configuration, security, datasource, migration runner, transaction manager, global codec or advice.

## Request identity and Java adapter migration (F031)

Register one `io.github.leontecristian.workflow.web.integration.WorkflowRequestIdentity` bean for any enabled endpoint group. Implement `requireActorRef()` using trusted server authentication and throw `io.github.leontecristian.workflow.web.exception.WorkflowUnauthenticatedException` for a missing or anonymous principal. Each request captures identity once, including requests that recheck current access or recover a receipt. The scoped envelopes return `401 UNAUTHENTICATED` for that exception and `500 HOST_FAILURE` for a null or blank return. Configure host authentication and CSRF for each mounted route.

Replace `WorkflowRuntimeReadIdentity` and `WorkflowAdministrationIdentity` with this bean. Remove `WorkflowRuntimeCommandHost` and `WorkflowCancellationAvailabilityContextHost` implementations. Migrate the viewer adapter to actor-first authorization methods. Administration authorization and the viewer grant adapter remain distinct from identity. Deploy the migrated Java adapters and web library together.

## Instance viewer

Explicitly `@Import(WorkflowViewerConfiguration.class)` in the host and supply:

- `WorkflowViewerOptions("/your/api", "trusted.correlation.attribute")`; correlation attribute may be null. The base path must be nonempty, non-root literal path segments.
- The shared `WorkflowRequestIdentity` and a `WorkflowViewerAccess` adapter authorizing the supplied actor. `requireInstanceRead` applies to every read and `requireHistoryRead` additionally guards history. Both `requireHistoryEventRead` and `canReadHistorySummary` receive the captured actor. Use `WorkflowViewerException` for concealed missing/denied (404) or bounded failure (422).
- Core's managed `WorkflowRuntimeQueryService` and `WorkflowDefinitionService`, with the host's existing transaction infrastructure.

`readableLinks(actorRef, instanceId, candidates)` returns independent activity grants (`taskId=null`) and exact-task grants. Each returned grant must match a supplied candidate's activity and optional task. Missing grants hide links; adapter exceptions fail the read. Graph construction uses internal history summaries after INSTANCE authorization, without disclosing raw evidence or requiring HISTORY.

Routes relative to the configured mount are `/instances/{id}`, `/instances/{id}/graph`, `/instances/{id}/history` and `/instances/{id}/history/{sequence}`. Serialization and error handling are scoped to this controller. Plain configuration/controller classes and a dedicated viewer-only mapping make dependency inclusion or package scanning inert. Only one mount per application is supported.

History defaults to cursor zero and 50 rows, maximum 100. Summary pages preserve complete rows within dual 1 MiB limits. Exact events preserve stored details within dual 4 MiB and final UTF-8 envelope within 8 MiB; they are never truncated. Numeric Java longs serialize as strings. Graph pin, contiguous-prefix watermark and existing size/shape checks remain in the projection service.

The sandbox's gated configuration and `ConsoleViewerAccess` illustrate composition. APOLO integration and production security/dependency acceptance are separate work.

## Definition and catalog administration

Explicitly import `WorkflowAdministrationConfiguration` and provide `WorkflowAdministrationOptions(basePath, correlationAttribute)`, core's managed definition/catalog services, and each required host dependency:

- The shared `WorkflowRequestIdentity`.
- `WorkflowAdministrationAuthorization.requireAdministrationAccess(actorRef)`: one administration grant for reads/writes; deny with the existing 403 response.
- A host-provided `java.time.Clock` and the existing `PlatformTransactionManager` governing both core and audit resources.

For opt-in audit, register a `WorkflowAdministrationAuditRecorder` bean. Its `record(audit)` call is synchronous in the mutation transaction. Hosts may activate and commit mutations without a recorder. Shared durable administration auditing remains deferred. Hosts retain authentication and mutation CSRF protection. Every request obtains identity once and authorizes that actor once before parsing. Mutations require a nonblank String from the trusted request attribute (sandbox: `console.correlation`); missing/non-string/blank values fail with `500 HOST_FAILURE` before core, without client-header or generated fallback. Read correlation behavior is unchanged.

Reads call core directly. Shared web's internal `WorkflowAdministrationService` calls existing core commands and records changed results when the host supplies a recorder. Reads and unchanged mutations produce no record. It captures the Clock once inside the mutation transaction, truncates to 100-nanosecond precision, and shares the context between definition operations and audit. Task-type core signatures remain context-free. `WorkflowAdministrationAudit` contains operation, entityKind/entityId, context, trusted correlationId and before/after core summaries (TaskTypeView, DefinitionView or DefinitionVersionSummary). Creation has null before; deletion has null after. Hosts own serialization, audit row IDs and storage schema. The sandbox preserves schemaVersion 1, its UUID correlation conversion, 512 KiB UTF-16 evidence bound and audit failure injection.

Hosts must enable annotation-driven transaction interception through existing Spring/Boot configuration. Shared web installs no transaction manager or `@EnableTransactionManagement`. Configure unambiguous manager selection when multiple managers exist; merely injecting a manager does not establish interception or select a different manager for annotations. Controllers call the managed service proxy. Public mutation methods use `@Transactional(propagation = Propagation.REQUIRED)`: service-owned transactions commit before returning to the controller; commit failures propagate. An outer host transaction owns completion when joined, so successful service return is provisional and the outer caller must complete it before reporting committed success. Audit failure rolls back a service-owned transaction or marks a joined transaction rollback-only. Do not use REQUIRES_NEW or automatic retries.

### F029 Java adapter migration

Replace the removed `WorkflowAdministrationHost` forwarding adapter with the dependencies above. The sandbox uses `ConsoleRequestIdentity` for all four groups and `ConsoleAdministrationHost` for administration authorization and audit storage. The shared coordinator is internal to web controllers despite Java-public methods for cross-package calls/proxying; it accepts an already authenticated and authorized actor and is not a supported host command API. Hosts with custom business orchestration continue to use core services under their own trusted boundary. Deploy compatible web/host adapters together; independently activated runtime groups are unchanged.

Routes are the existing `/task-types`, `/definitions` and `/versions` operations listed in [F014](../docs/features/F014-definition-catalog-administration/spec.md). IDs/tokens remain decimal strings; raw document import/replacement retains its 4 MiB UTF-8 limit, ordinary bodies 16 KiB, and exports return stored text. Local handlers retain management error categories and diagnostics, including 403 rather than viewer concealment. No task-type deletion, new authoring semantics or automatic write retries are supplied.

F023 successor-draft creation and draft deletion now use the shared F029 coordinator. POST `/versions/{id}/drafts` requires an empty JSON object and `X-Expected-Lock-Version` for the saved source. DELETE `/versions/{id}` requires the loaded token and no request body. Both return HTTP 200 using the core change/deletion result and preserve existing access, CSRF and error categories. Creation uses the normal version audit; deletion records the removed ID and summary as `before`, with `after=null`. With a recorder configured, both audits belong to the same host transaction as the command. These commands have no automatic retry or receipt replay guarantee.

Before activating F023 writers, quiesce older definition writers and apply the core `highest_allocated_version` family-counter migration through the host migration owner. Deploy compatible writers together; mixed counter-unaware writers and downgrade to them are unsupported. Automatic creation allocates counter + 1; a new explicit import must exceed the counter, including when a lower gap was never used. Equivalent imports of retained versions remain unchanged. New allocations advance the family lock token; stale metadata editors must refresh. Deletion retains the family and counter, so deleting the highest or all drafts never restores lower-number capacity. See [F023 revision 3](../docs/features/F023-create-next-definition-version/spec.md).

## Runtime reads and optional command mapping

Import `WorkflowRuntimeReadConfiguration` and `WorkflowRuntimeCommandConfiguration` independently. Both use `WorkflowRuntimeOptions(basePath, correlationAttribute)` and the shared `WorkflowRequestIdentity`. Runtime reads use the managed core query, definition and eligibility services and `WorkflowRuntimeReadAuthorization`. Runtime commands use a managed `WorkflowExecutionService`, a host `Clock` and the host `PlatformTransactionManager` that governs core and business writes. The host selects the transaction manager unambiguously and enables core transaction interception. Package scanning alone leaves the groups disabled.

Read routes cover monitor, variables, assigned/instance tasks, exact task/contract/submission and activity/submissions, as inventoried in [F015](../docs/features/F015-runtime-task-instance-extraction/spec.md). The library-owned `WorkflowAuthorizedRuntimeReadService` supplies authorized pages and exact-resource access. The host supplies actor-only decisions; the monitor grant runs before query parsing. A filtered page may be empty with continuation; consumers must retain it. Navigation identifiers remain decimal strings. F034 task contracts project the task header, permitted frozen inputs, operation availability and editor fields before serialization.

The exact task, task list and submission projections expose display labels and business values. The task contract has an authoritative task summary and an editor selector and outcome keys only for actors who can complete. The generic editor receives a named form description derived from the pinned schema. The optional `WorkflowAssignmentDirectory` supplies current display names, and missing names receive neutral labels. Shared task responses carry the same safe fields for every actor. Resource authorization and submission rereads use the existing read policy. A host can expose diagnostics via its own administrator-protected HTTP route, as the sandbox does.

The optional command group maps complete, claim, release, administrative release and reassignment at `/tasks/{taskId}/{operation}`. Each has a lookup-only `/commands/{operation}/replay` route with `taskId` in the replay body. Both requests require the original opaque `X-Task-Precondition` from the reviewed contract. The server resolves the owning instance and performs the core receipt or fresh mutation checks. Task commands return `{replayed, status, taskStatus}` and may include `collectivePending` and an authorized `nextTaskId`. Replay wraps that outcome in `{found, result}`.

Deploy the web and UI transport changes together after recovering pending task envelopes in the previous format. Set the optional Spring property `workflow.runtime.task-token-key` to a persistent 32-byte Base64url key shared by nodes that serve these routes. Without a configured key, a restart invalidates outstanding task preconditions and previous-decision continuations.

Shared web creates a command context with the captured USER actor, one host clock reading truncated to 100-nanosecond precision and correlation from the configured trusted request attribute. Missing or non-string correlation becomes null. A shared HTTP command owns its transaction and returns success after commit. Following a confirmed rollback for core `STALE_VERSION` or `CONCURRENT_COMMAND`, one separate read-only transaction looks up the original command using the same context and expected token. A hit returns the stored result as replayed. A miss returns the original error. Lookup failures take precedence. Explicit replay only looks up a receipt. The sandbox maps its conditional business-row write conflict to HTTP 409 `SANDBOX_REQUEST_CONFLICT` after rollback. On that path the client may explicitly replay. Business callers coordinating an outer transaction call core directly and own transaction completion and recovery. Ownership operations require exact operation support in `WorkflowAuthorization` for current task business access and explicit administrative release permission. Replay uses current business access and the original receipt actor, independently of current membership or administrative permission. Sandbox start/replay routes and request linking remain host-owned.

F025 adds `POST /instances/{instanceId}/cancel` with exactly `{commandId, reason}` and lookup-only `POST /commands/cancel/replay` with those fields plus `instanceId`. Both require `X-Expected-Lock-Version`, canonical UUID/decimal-string transport and at most 16 KiB UTF-8 JSON. The reason is required, nonblank, valid Unicode and at most 2000 UTF-16 code units; it is retained exactly. Duplicate and unknown fields fail. Mutation returns `{replayed, execution}`. Recovery returns `{found, result}` with the cancellation command wrapper on a hit.

The read group exposes `GET /instances/{instanceId}/cancellation-availability`. After authorizing the instance read, it returns `{allowed: false, lockVersion}` when the instance is inactive, the host omits a `Clock` or its command policy omits `CANCEL_WORKFLOW`. For an active readable instance with both dependencies, the shared web submits the captured USER actor, one host clock reading truncated to 100-nanosecond precision and null correlation for the core availability policy. The clock is optional for read-only hosts. A host that already provides a clock and cancellation policy now receives the advisory hint even if it previously omitted the context factory or disables runtime commands. Actual cancellation and replay require `CANCEL_WORKFLOW` support through core `WorkflowAuthorization`. Original-actor replay requires current business access, while fresh cancellation also requires cancellation permission. Sandbox cancellation preserves request status and links.

Cancelled graphs retain the stopped human node with state `CANCELLED`, retain prior traversed edges and add no outgoing traversal. Instance/activity cancellation history uses general history access; `TASK_CANCELLED` summaries and details use the exact-task grant. Existing task/submission authorization remains in force.

F026 adds `GET /tasks/administration` to the runtime read group. Implement the separate `WorkflowRuntimeReadAuthorization.canAdministerTasks(actorRef)` grant and `canReadTask(context)` row policy. The collection defaults to OPEN and accepts status (OPEN/COMPLETED/CANCELLED/ALL), taskType, assignmentKind, assignmentRef (requires kind), assigneeRef, instanceId, cursor and limit (default 50, maximum 100). The authorized facade supplies one bounded metadata candidate page, filters through host policy and preserves source continuation, including an empty filtered page. Task collections accept opaque `cursor` values from `nextCursor` and return task references only for visible rows. Core's joined administration query supplies pinned node/type labels without fetching metadata per row. The wire projection omits outcomes and closure attribution; protected review data remains behind exact-task reads.

Task administration additionally accepts optional `taskName` (nonblank Unicode, at most 200 UTF-16 units). It matches a case-insensitive literal substring of the pinned display name within the bounded candidate page. If the page is empty and returns a `nextCursor`, pass it unchanged as `cursor` to continue. Other filters keep exact semantics.

`GET /tasks/{id}/reassignment-availability` returns `{allowed, precondition?}` after exact-task authorization, with false as the default for unsupported hosts. `GET /tasks/{id}/reassignment-targets?kind=USER|GROUP|ROLE&query=...&cursor=...&limit=...` requires exact-task access plus `canReassignTask` before calling the host's `reassignmentTargets` directory lookup. Query is bounded to 200 UTF-16 code units; cursor to 1000; target pages default to 20 and allow at most 50 `{ref,label}` choices with `nextCursor`. The UI exports matching TypeScript `WorkflowReassignmentTarget` and `WorkflowReassignmentTargetPage` contracts; this does not change the endpoint, host bean registration or opaque cursor format. Adapter failures fail closed. Directory choices are advisory. Core checks the exact destination through the host target validator on fresh execution.

`POST /tasks/{taskId}/reassign` accepts exactly `{commandId, assignment:{kind,ref}, reason}`. Replay adds `taskId`. Both use `X-Task-Precondition`. The reason is exact, nonblank, valid Unicode and at most 1000 UTF-16 code units. Core checks current business access, fresh permission and the destination validator. Original-actor replay still checks current business access. See [F026](../docs/features/F026-task-administration-reassignment/spec.md)../docs/features/F026-task-administration-reassignment/spec.md).

Definition-family lists additionally accept `order=ASC|DESC` (default ASC). DESC starts at omitted/zero afterId and continues with IDs strictly below nextAfterId; keep the same order while paging. The sandbox Definitions page requests DESC so newly created families appear first. Existing consumers that omit order keep ascending paging; the separate start chooser is unchanged.

F034 projects F022 previous decisions through `previousDecisionsAvailable` and `GET /tasks/{id}/previous-decisions?cursor=…&limit=20`. Omit the cursor on the first page and send `nextCursor` unchanged to continue. Every page checks the receiving task grant and returns display labels, time and the original allowed comment. Limit is 1–50, default 20. Full retained history remains subject to the host's separate evidence grant.

The sandbox keeps its existing `/instances/{id}/history` and event-detail HTTP routes behind its administrator and instance grants. Its host-owned `/instances/{id}/business-history` and `/instances/{id}/business-history/{eventRef}` routes return safe business history after the sandbox's instance and event checks. The same browser History and event routes work for both roles.

The F026-authorized `GET /tasks/administration` response includes `instanceId` and `createdAt`. Instance links open through the independently authorized instance route.

Hosts using their own facade may call core's `previousDecisionsPolicy(taskId)` and `listPreviousDecisions(taskId, afterSequence, limit)` after applying their own exact receiving-task read authorization. These detached DTO queries participate in the host's read transaction and grant no source-resource access. See the [F022 contract](../docs/features/F022-previous-decision-comments/spec.md).

### F032 Java adapter migration

Replace the four operation-specific authorization beans with one core `WorkflowAuthorization` bean and a separate destination validator for hosts offering reassignment. See the [core Java migration](../workflow-core/README.md#migrating-to-f032) for a completion-only example. Rebuild host, core and web together. Runtime-read and command routes retain their existing activation and payloads. Missing operation support makes the corresponding ownership, reassignment and cancellation hints unavailable and returns `HOST_CONFIGURATION` on direct command or replay requests. Read-only hosts may omit the command policy. Current business access denial continues to conceal the resource, and lookup failures remain `AUTHORIZATION_LOOKUP_FAILED`.

### F028 completion adapters

Hosts offering completion declare `COMPLETE_TASK` through `WorkflowAuthorization` and register exactly one `WorkflowTaskCompletionValidator`, including for existing published workflows. `TASK/ACCESS_COMPLETION` checks current business access before receipt lookup. `TASK/COMPLETE` checks fresh decisions using `TaskCompletionContext`. Runtime-read `canCompleteTask` and engine assignment eligibility are separate from command permission.

Fresh completion validates the pinned outcome/comment/result structure, then invokes completion permission, general business validation and the existing optional F018 submission validator. General validation runs for every result mode, including FORBIDDEN and omitted OPTIONAL results. A host that needs no additional business check must still register an explicit validator that returns normally. Throw core `TaskCompletionRejectedException` for a sanitized business rejection. Completion permission denial maps to `COMPLETION_FORBIDDEN` (403), explicit business rejection to `BUSINESS_VALIDATION_REJECTED` (422), and unexpected validation failure to `BUSINESS_VALIDATION_FAILED` (503); arbitrary provider messages are not returned.

Original-actor receipt recovery requires current business access, but skips fresh permission and both validators, including when the general validator is unavailable. Lookup-only misses also skip fresh hooks. The shared coordinator delegates directly to core, preserving receipt recovery after task closure. Hosts calling core from a custom transaction use the same receipt-first boundary. Validation runs within the completion transaction; hosts remain responsible for locking/version guards that protect authoritative business data through commit and for keeping effects outside validation hooks. HTTP payloads, success responses and receipt formats are unchanged.

### F027 Java adapter migration

`WorkflowRuntimeReadHost` is replaced; migrate custom restrictions explicitly, without a legacy page-provider fallback. Supply the shared `WorkflowRequestIdentity` and core `WorkflowRuntimeReadAuthorization`. The seven data-returning methods now belong to `WorkflowAuthorizedRuntimeReadService`: `listInstances(actorRef, query)`, `listMyTasks(actorRef, afterId, limit)`, `listInstanceTasks(actorRef, instanceId, afterId, limit)`, `listAdministrationTasks(actorRef, query)`, and `instance/task/activity(actorRef, id)`. Ordinary reads need no command context. Web configuration constructs the facade with the core query, eligibility and authorization support services. A core-only host needs a read policy when it constructs the facade.

Map monitor/admin collection grants to `canMonitor`/`canAdministerTasks`, monitor metadata to `canListInstance`, and exact-resource decisions to `canReadInstance`, `canReadTask` and `canReadActivity`. Completion remains a default-false advisory `canCompleteTask` hint. Ownership, reassignment and cancellation availability use the relevant declared operation and command policy alongside the read grant. Shared web retains command-activation gates for ownership hints, while completion remains visible independently of command activation.

**Partial hosts.** A host that omits `COMPLETE_TASK` from `supportedOperations()` can still return a positive `canCompleteTask` read hint for an eligible task. The hint describes read-side availability. An attempted completion on that deployment returns `HOST_CONFIGURATION` before command policy is called.

Optional `WorkflowAssignmentDirectory` owns `assignmentLabel(task)` and `reassignmentTargets(context, kind, query, cursor, limit)`. Label-only implementations work: inherited search denies with 403 REASSIGNMENT_FORBIDDEN after normal exact-task/permission checks. Missing, blank, invalid, overlong, failing or raw-reference labels fall back to approved neutral display text; explicit search overrides retain bounded opaque-cursor behavior.

My Tasks combines host task visibility with core current-assignee OR assignment eligibility, without ownership authorization. It remains personal even for administrators. Instance-task lists retain bounded refill (500 candidates); monitor and administration retain one candidate page without refill. HTTP/UI contracts and optional command activation are unchanged. See [F027 revision 6](../docs/features/F027-runtime-read-policy-separation/spec.md).
