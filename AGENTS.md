# Agent instructions

These instructions apply throughout this repository. Follow explicit user instructions and any applicable instructions in more specific `AGENTS.md` files. Keep changes focused on the requested task.

## Start with project context

- Inspect `git status --short` and the relevant files before editing. Preserve unrelated user changes; do not reset, overwrite or stage them.
- Read [README.md](README.md), [constitution](docs/constitution.md), [constraints](docs/constraints.md) and [assumptions](docs/assumptions.md) before architectural or behavioral work. Use [design sources](docs/design-sources.md) to find the authoritative detailed design.
- Treat AGREED decisions as constraints. Keep PROPOSED, PROVISIONAL, OPEN and DEFERRED items distinct; examples are not finalized contracts. Resolve material ambiguity before implementing dependent behavior, while continuing independent work.

## Specification-driven changes

- Follow the [development workflow](docs/specification-driven-development.md). Substantial features belong in `docs/features/<feature-id>-<name>/`, with exactly four process documents: `spec.md` (required behavior), `plan.md` (intended approach), `tasks.md` (execution) and `implementation.md` (actual results, verification and handover). Keep them proportional; technical artifacts may be added when needed.
- Specify observable behavior, errors and acceptance scenarios before dependent code or migrations. Reference applicable CON/ASM identifiers; keep schemas, examples, implementation and evidence consistent. Do not invent unresolved API fields, business rules or persistence mappings.
- Keep planned verification in `plan.md` and actual checks/outcomes/gaps in `implementation.md`; do not require separate evidence or verification files. Link rather than repeat requirements and architecture. Implementation discoveries that change behavior must update the specification and reconcile the plan/tasks before dependent work.
- Small maintenance changes may use a concise change description instead of a feature document set. Avoid speculative abstractions, extra modules and unrelated refactoring.
- **Owner clarification — 2026-11-07: keep delivery proportional.** Every added behavior, abstraction and acceptance check must serve the requested slice, a changed dependency or a concrete regression risk. Preserve global guarantees as constraints; do not turn them into new functionality or a full acceptance checklist in every feature. Defer hypothetical future-consumer needs. Historical verification gaps belong to their owning feature or integration/release milestone, not automatically to the next task.

## Architecture and implementation

- Follow [coding standards](docs/coding-standards.md) for Java, Spring, JPA, Lombok and error handling, and the [frontend style guide](docs/frontend-style-guide.md) for shared UI and sandbox presentation. Preserve the distinction between general rules and page-specific decisions.
- Follow the [layer-first package structure](docs/package-structure.md) and its supported dependency boundaries. Use concrete services by default; introduce interfaces only for a documented need. Feature plans must name exact packages. Preserve the root `WorkflowConfiguration` import and scanning marker.
- Preserve the three Maven modules: `workflow-core` (ordinary Spring/JPA library), `workflow-web` (optional Spring MVC adapter library depending on core) and `workflow-test-host` (executable development host). `workflow-ui` is a separate Angular library. Core must not depend on web, UI, the test host or APOLO backend implementation; see the [architecture](docs/architecture/workflow-engine-design.md).
- Hosts own endpoint activation, business endpoints and orchestration, identity, authorization policy, datasource, transaction infrastructure and external delivery. Shared web/UI libraries supply reusable implementation through explicit host adapters; they must not create competing infrastructure or alter global host configuration. See the [web](workflow-web/README.md) and [UI](workflow-ui/README.md) integration contracts.
- Public core contracts use workflow-owned or standard Java types, without exposing persistence entities or security/messaging-provider objects. Preserve one authoritative library implementation; defer source moves, reparenting and coordinate changes until requested.
- Follow existing Java/POM conventions: compile against Java 17 APIs/bytecode and use JDK 21 for the current build/runtime. Declare direct dependencies in the module using them and read current POMs for versions.
- Keep required synchronous business effects, workflow state, history, receipts and durable handoff atomic in the host transaction. Preserve aggregate concurrency protection and authorized idempotent replay. Do not automatically retry business actions or duplicate an effect in host orchestration and the engine.
- Preserve immutable published definitions, pinned workflow versions and authoritative execution evidence. Read the [language design](docs/architecture/workflow-definition-language-design.md), [database design](docs/architecture/Workflow_Engine_Database_Design_v1.md) and owning feature specifications before changing their contracts or persistence mechanisms.
- Enforce trusted identity, authorization and allowed inputs at execution boundaries. Preserve restricted expression evaluation and failure behavior; expressions must not access arbitrary application objects. Follow the [constitution](docs/constitution.md) and [constraints](docs/constraints.md) for the applicable guarantees.
- Core owns `db/changelog/workflow/workflow-master.xml`; hosts execute migrations, with APOLO the production migration owner. Preserve applied changeset identities/paths, add ordered changesets and keep host fixtures outside core's master. JPA must not independently create/update production schema.
- Implement only the selected, specified scope. Use the [feature index](docs/features/README.md) to find owning specifications and handovers for implemented, proposed and deferred behavior. Do not infer implementation authorization from roadmap entries or historical examples.

## Build and verification

- Plan verification from the actual change: state what changed, which prior evidence still applies, what needs fresh checking and the completion condition. Reuse applicable evidence with its source/revision and a short applicability reason; label it REUSED, not a fresh PASS. A new revision alone does not invalidate evidence, but changed code paths, dependencies or environment may. Existing evidence cannot establish new behavior that it never exercised.
- Select focused existing suites and add tests only for changed behavior or a concrete uncovered risk. Do not add/select idempotency, replay, rollback, concurrency or broad browser scenarios for unrelated changes. Revisit those guarantees only when their implementation or relevant integration boundary changes, an observed failure implicates them, or an explicitly selected integration/release gate requires fresh evidence. Retain existing tests; do not weaken them to avoid execution. Database-test authorization permits relevant checks; it does not require running all available tests.
- Keep browser checks to changed interactions/rendering and host wiring; use focused automated tests for detailed cases and reuse evidence for unchanged workflows. Do not rerun whole workflows merely to obtain a viewer state when retained/test-owned fixture state suffices. Do not repeat an identical build already performed successfully by the selected packaging command.
- **Stopping rule:** once the requested scope and its relevant checks pass, finish with the results. Repeat or broaden checks only for a subsequent relevant change, failure or identified coverage gap; record why. A small follow-up fix repeats its affected checks, not the entire acceptance matrix. A blocked required check remains open, but does not justify unrelated work or reopening prior acceptance. Reconcile inherited broad feature checklists with these rules in the plan/tasks before executing them; preserve historical outcomes and required guarantees.
- **Owner clarification — 2026-11-01: isolated unit tests and database integration tests against `localhost:1433/apolo_workflow_test` may be created and run as part of implementation and verification without further approval.** This includes applying project migrations and creating/cleaning up test-owned fixtures in that database. Other database targets, including `apolo_workflow_dev`, require task-specific authorization. Do not reset/drop databases, erase unrelated data or stop another session's processes. This supersedes older blanket no-tests and per-run authorization wording, including feature documents; preserve historical results and NOT RUN evidence. See [database integration testing](docs/testing/database-integration-tests.md).
- Unit tests must run without a database, migrations, a running host or external services. Test doubles for repositories/adapters are appropriate. SQL Server, embedded databases (including H2), Testcontainers and database-backed Spring context tests count as integration tests, regardless of their name. Unit-test success does not establish real transaction, locking or database behavior.
- Use the Maven wrapper from the repository root with `JAVA_HOME` pointing to an installed JDK 21; verify the selected JDK. Select known unit-only suites explicitly, for example `./mvnw.cmd -pl workflow-core '-Dtest=<UnitTestClass>' test`. The default Surefire run selects `*UnitTest.java` in all three Maven modules. Database tests live in the host, use the guarded `DatabaseIntegrationTest` base and run through `-Pintegration-tests verify`; they must not be named `*UnitTest`. Inspect discovery when changing profiles. Use separate source/build directories and serialize runs targeting the same test database when another agent is testing.
- Packaging without test execution remains available: Windows `./mvnw.cmd '-Dmaven.test.skip=true' package`; other systems `./mvnw -Dmaven.test.skip=true package`. Record unit-test, build and manual/integration results separately and mark unperformed checks NOT RUN. Do not build or run tests merely for documentation-only changes; inspect content, links and whitespace instead.
- Start the host or access a database only within the task's authorized scope. Startup runs Liquibase. The normal host uses `apolo_workflow_dev`; the integration harness uses only `apolo_workflow_test` on the same local SQL Server, with Windows authentication. Do not change the normal host URL or environment to redirect tests. See the README for commands and the matching native DLL.
- For temporary verification, record the process you started and stop that process afterward unless asked to leave it running. Check its identity before stopping it; never kill an unrelated process to free a port. Report final process state.
- Do not treat packaging or connection success as proof of rollback, concurrency, authorization, expression safety or recovery. Record commands, observations and evidence gaps accurately.

## Files, Git and handoff

- Use `rg` for scoped searches. Keep credentials, private runtime data, logs, native DLLs and generated `target/` artifacts out of commits. Avoid machine-specific absolute paths in shared instructions/configuration where relative paths suffice.
- On Windows, use PowerShell file operations with literal paths; verify resolved targets remain inside the intended workspace before directory moves or recursive deletion.
- Review the final diff and run `git diff --check`; check newly added documentation too. When committing, follow the [commit message structure](docs/coding-standards.md#commit-messages), stage only intended files and inspect `git diff --cached --check`. Commit or push when the user requests it.
- Finish with what changed, how it was checked, unresolved issues and whether changes are committed. Keep the constitution and feature records current when behavior or decisions change; do not claim planned functionality is implemented.
