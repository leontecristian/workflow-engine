Workflow event catalog

The workflow engine emits one event for each history row and hands off one batch per new command in increasing history sequence order. The host persists the batch in the command transaction and delivers the stored events after commit. Use the stable event ID for idempotent consumption and delivery retries.

Envelope

eventType, eventSchemaVersion
The event type and its outgoing schema version. Stored history details have their own version.
eventId, historySequence
eventId is the stable string instanceId:historySequence. historySequence is the event's sequence within its instance.
commandId
UUID of the originating command. Several events can share a command ID.
instanceId, definitionVersionId
The instance and its pinned definition version.
actorKind, actorRef, occurredAt, correlationId
The command actor's kind (USER or SYSTEM) and reference, the command timestamp and optional correlation ID. Assignment targets and individual owners appear in the payload where applicable.
activityId, taskId
Activity events carry the activity ID. Task events carry both IDs. VARIABLES_WRITTEN carries the activity ID for human output writes and the task ID for SINGLE human output writes. These references are null in other cases.
sourceNodeKey, targetNodeKey, transitionKey
The traversed edge's keys on TRANSITION_TAKEN. These fields are null on other events.

Event types and payloads

The payload is a map of strings to strings, including counts and booleans. Empty means an empty map. Keys are present unless marked conditional. Input values, submission values, comments and reassignment reasons are outside the outgoing payload contract.

APOLO booking review and assignment

Suppose APOLO starts a workflow to review bookings B-742 and B-743. In the workflow creation transaction, APOLO associates both bookings with the engine-issued instance ID 120 in its own business data. After commit, its consumer receives a TASK_CREATED event. The following excerpt shows a direct assignment to Maria.

{
  "eventSchemaVersion": 3,
  "eventType": "TASK_CREATED",
  "instanceId": 120,
  "taskId": 701,
  "actorRef": "alex",
  "payload": {
    "taskKey": "review",
    "assignmentKind": "USER",
    "assignmentRef": "maria",
    "assigneeRef": "maria"
  }
}

For initial assignment to the Finance group, the creation payload is:

{"taskKey":"review","assignmentKind":"GROUP","assignmentRef":"FINANCE"}

The GROUP payload omits assigneeRef. A later TASK_CLAIMED identifies the individual who claims the task. Changing the assignment target emits TASK_REASSIGNED.

When Maria opens the task, APOLO uses event.instanceId() for two reads.

  1. Look up the APOLO-owned associations for instance 120 to find the two booking references. Apply APOLO's booking access policy before showing the details. The optional workflow businessType and businessId fields provide correlation. APOLO's associations establish booking membership.
  2. Resolve Maria's actor reference from the authenticated request and call WorkflowAuthorizedRuntimeReadService.instance(viewerActorRef, event.instanceId()). The authorized WorkflowInstanceView supplies current status(), currentNodeKey() and definitionVersionId(). The event's actorRef identifies Alex as the originating command actor.

APOLO uses event.taskId(), here 701, for the review itself. Both paths below are relative to the host's runtime API mount and check the authenticated viewer's access to the task.

When Maria opens the review, APOLO calls GET /tasks/701/contract. Suppose the workflow author bound a JSON input named bookingRefs and configured two outcomes. This response excerpt shows the input snapshot captured at activity entry and the outcome choices from the pinned definition version.

{
  "inputs": {
    "bookingRefs": { "type": "JSON", "value": ["B-742", "B-743"] }
  },
  "outcomes": [
    { "key": "APPROVE", "label": "Approve", "requiresComment": false },
    { "key": "REJECT", "label": "Reject", "requiresComment": true }
  ]
}

After Maria approves, APOLO calls GET /tasks/701/submission and reads the accepted outcomeKey. An illustrative response excerpt is {"actorRef":"maria","outcomeKey":"APPROVE"}. An authorized read before a submission exists returns JSON null.

ALL review outcomes

Suppose the booking review is an ALL activity with ID 301 and two reviewer tasks. The configured contribution outcome is APPROVE, so both reviewers must approve for the activity to resolve with APPROVE. A REJECT resolves it immediately. Read the outcome from event.payload().get("outcomeKey") in both completion event types.
