### Scoped precedence for the 2.x amendments

The owner's decisions recorded in database design v1.4 (including retained earlier decisions) supersede older consolidated-design, development-plan and registry examples for these topics:

- Multiple directly assigned tasks per activity are in V1, while the process retains one active position. SINGLE/ALL completion semantics and fixed-roster rules were proposals at the 2.x amendment; the later 2026-10-31 decisions below select SINGLE, ALL and the fixed task list.
- A simple retained task catalog replaces task-type business versions, publication lifecycle and outcome tables. Codes are immutable from creation; descriptive metadata and authoring selectability are editable. Published human nodes own outcome/input contracts; activities own the catalog reference and tasks inherit it.
- Hibernate-managed numeric BIGINT/Long JPA versions replace the SQL Server ROWVERSION proposal. The early checked instance write and final managed-version capture are selected approaches whose host behavior still needs O7 verification.
- APOLO stores instance IDs and uses the engine API; host data owns booking membership and historical links. The engine retains optional, immutable, nonunique business_type/business_id correlation, both populated or both null. No host association table is mandated.
- Structured completion results extend scalar-only task inputs. Each accepted result is immutable TASK_COMPLETED evidence with a pinned contract, supported authorized exact-task/activity retrieval, full-payload idempotency, host business validation and operational retention. Same-transaction downstream reads include the final submission. No new task-result table/column, draft form saving or automatic JSON-to-variable merging is selected; exact schema/limits/API shapes remain pending.
- JSON execution variables supplement the six scalar types, superseding the earlier scalar-only variable restriction. Mutable objects/arrays use workflow_variable.json_value with explicit null/type rules, whole-value replacement, declared bindings and bounded read-only path navigation. They do not replace task submissions or APOLO-owned membership. Exact contracts/limits and persistence/expression verification remain pending; indexed JSON search and implicit patch/merge behavior are not selected.

The consolidated design remains the detailed source for unaffected architecture. Older text on the superseded topics must not be used to implement the previous contracts. Dependent specifications must cite this precedence and the database design; unresolved proposals are not finalized by the amendment. Initial schema design changes are not migrations of an applied schema: preserve existing changesets and specify a separate forward migration if needed. APOLO owns migrations for host associations.

The owner's later instructions and completed project changes additionally establish the current local SQL Server connection, Windows authentication setup, Lombok alignment and no-tests development policy. These operational details do not settle the remaining APOLO production integration questions.

### Scoped precedence for the 3.0.0 routing amendment

On **2026-10-31**, the owner selected ordered first-match workflow routing after reviewing BPMN exclusive-gateway semantics. Architecture v0.9 section 7.3, language design v0.2 section 5.2, constitution C08 and CON-09 now supersede earlier statements requiring exactly one true condition or rejecting overlaps. Evaluate conditions in declared priority order, stop at the first true result, and consider a separate unconditional default only when every condition is false. No default in that case, or an error in an evaluated condition, fails the command. Later conditions are not evaluated or recorded as false.

All conditions remain subject to publication validation. The future designer must expose priority and preserve it independently of diagram layout. Exact JSON notation and diagnostics remain open; warnings for obvious unreachable routes are optional proposals. This is a workflow routing change, not authorization to implement the deferred decision-table component. Existing definitions must not be silently reinterpreted; the amendment changes no code or schema and leaves the F001/F002 baselines and evidence intact.

### Minimal-definition decisions — 2026-10-31

The owner confirmed all four recommendation groups in language design section 15.4. Use integer schemaVersion (initial 1), key and definition version, exactly one START and no startNodeKey. Start/task inputs and result behavior are explicit; empty contracts accept no extra fields, and inputContract: [] represents no simple task inputs. Guards may be omitted as an empty list, while authorization cannot silently default to unrestricted access. Each human step has shared node-wide input/result contracts; permissions, guards and comments are outcome-specific. Forbidden results must be absent, optional results may be absent, and required results need a valid object; reject top-level null in every mode and apply the schema to nested nulls. A named resolver with explicit validated inputs supplies exactly one directly assigned task for SINGLE; invalid count or missing assignee fails entry. The accepted outcome resolves the activity and routes within the command transaction.

These selections supersede older statements that SINGLE behavior, contract placement and task-result presence remain undecided. ALL and the fixed task list were subsequently agreed in the same review, as recorded below. Exact notation not explicitly selected, schema profiles, limits and diagnostics remain open. C02/C07, constraints, assumptions and the database design's later-decision notes preserve this distinction. No existing schema, application code or F001/F002 evidence is changed.

### ALL and the fixed task list — 2026-10-31

The owner confirmed language design sections 9.2–9.3. ALL collects one configured contribution outcome from every required task; another permitted outcome resolves the activity immediately. The full bounded nonempty task list is fixed and created atomically at activation. Audited reassignment preserves task identity; additions, removals and waivers cannot change the required work while active. Early completion cancels open siblings and preserves earlier evidence; cancelled tasks cannot submit or count as votes. Under concurrency protection, the first decisive command that successfully commits wins without implicit outcome priority; authorized successful retries still replay their receipt. Final or decisive submission, activity resolution, cancellations, routing and synchronous downstream work share one transaction. Failure rolls back that command while retaining prior committed contributions.

These decisions supersede descriptions of ALL as proposed or deferred. They do not choose APOLO approval rules, a numeric task limit, exact JSON/API/error contracts or an implementation. Existing schema and F001/F002 evidence remain unchanged. C02, CON-05 and the database design record the same decision.

### Relationship to BPMN — 2026-10-31

The owner confirmed L01 in language design section 16.1: use a custom JSON workflow language informed by BPMN concepts, without promising BPMN conformance or file interchange. Sections 6.1–6.2 record this agreed direction. Any future interchange capability requires a separate scope decision and a defined mapping. This confirmation does not finalize language contracts.

### Definition validation — 2026-10-31

The owner confirmed L02 as the validation approach: JSON Schema checks document structure, while a separate engine semantic validator checks relationships and meaning, including graph references, outcome routes, data contracts and registered application capabilities. Language design section 13.1 records the boundary and retains runtime checks. The exact JSON Schema version, supported features and detailed validation rules remain open. BPMN's role is covered by L01; ASL and Open Workflow remain research comparisons, without a format-support commitment. This decision changes no implementation or historical feature evidence.

### Definition identity and collections — 2026-10-31

The owner confirmed the remaining L04 choices in language design section 12.3. Nodes and transitions are JSON arrays whose elements use stable keys for references, never array positions. Workflow, node and transition keys are case-sensitive, begin with an ASCII letter and then allow ASCII letters, digits, dots, underscores and hyphens; spaces are forbidden. Node keys and transition keys must each be unique across the definition, in separate namespaces. Human-readable labels may use spaces and Unicode. Maximum key length remains under L16, and route-priority notation remains under L03. This decision does not change applied persistence contracts or implementation evidence.

### Workflow graph rules — 2026-10-31

The owner confirmed L09 and the graph rules in language design section 8.3. Require one START with no incoming routes and exactly one unconditional outgoing route, at least one END with no outgoing routes, valid node references, one unconditional service success route and one route per human activity outcome. Decisions retain ordered first-match behavior and at most one unconditional default. Every node must be reachable from START and have a structural path to an END. Human-review loops are allowed, but every automatic-only cycle is rejected, including one within a larger review loop. Structural reachability does not prove runtime termination. These decisions supersede the earlier proposal status; exact diagnostics and route-priority notation remain open. No implementation or historical feature evidence is changed.

### Value representation and absence — 2026-10-31

The owner confirmed L10 and language design sections 10.2–10.3. Declared LONG and DECIMAL values use JSON strings; STRING preserves contents without automatic trimming, BOOLEAN accepts only true/false, and JSON values use schema-validated objects/arrays. DATE uses ISO 8601 YYYY-MM-DD; DATETIME includes date, time and seconds with Z or an explicit offset. Invalid dates, offset-free timestamps and invalid/lossy conversions are rejected. Missing, explicit null and empty values remain distinct. Required and nullable are separate, and typed defaults apply only to missing values at declared initialization boundaries, never to explicit null, invalid input or failed evaluation. Task-result presence rules remain unchanged.

Numeric grammar/range checks, decimal and timestamp precision, offset normalization, nested JSON numbers and remaining initialization/read rules still require specification. This decision does not convert schemaVersion to a string, select all schema features or numeric limits, or change applied persistence contracts and historical evidence.

### Embedded data schemas — 2026-10-31

The owner confirmed L11: embed variable and task-result schemas in the workflow definition, freeze them at publication and allow only local, noncircular references within each embedded schema. Support declared properties, required fields, types, explicit nullability, fixed values, enumerations, nested objects/arrays and length/count/value bounds. Objects must declare accepted fields and explicitly reject additional ones. Support data-based if/then/else requirements and oneOf alternatives with a shared required identifying field whose fixed value differs for every shape. Reject external references and defer recursive schemas and arbitrary text patterns. Only explicitly documented format checks are supported, with date/time checks following L10; unsupported validation features and formats must be rejected before publication.

The profile belongs to the workflow-language version. Engine upgrades must preserve its validation behavior or explicitly reject unsupported versions; incompatible profile changes require a new language version. These features remain within the node-wide result contract and do not execute workflow branches or replace host authorization/business checks. Exact keyword/composition rules, reference resolution, format allowlist and diagnostics remain specification work, alongside L16 numeric limits, L10 exactness details and the L02 JSON Schema version. See language design section 10.5. No implementation change is implied.

### Standard SpEL semantics within the engine boundary — 2026-10-31

The owner clarified L12: use standard SpEL syntax and semantics in a controlled, read-only context rather than separately designing ordinary operator behavior. Retain documented precedence, short-circuit and null handling; do not ban arithmetic by default. Expose only typed, declared facts and permitted variables, preserve precision and missing-required-data checks, and require Boolean routing results with command failure on evaluation errors. Existing restrictions on mutation, arbitrary objects, application/service access and costly unrestricted features remain. Specify and verify typed conversion, access enforcement, necessary restrictions and resource bounds. Language-version compatibility applies across Spring/SpEL upgrades; no separate expressionPolicy field is introduced. Language design sections 11.1–11.2 and architecture section 5.3 record the clarification. No runtime implementation is claimed.

### Designer metadata preservation — 2026-10-31

The owner confirmed L13 and language design sections 12.3/14.1: designer information belongs in an optional dedicated designer section and cannot affect execution or route priority. Associate element layout with stable keys. Editors and backend tools must preserve unknown metadata values within the section's structure/size limits; if safe preservation is impossible, explain the issue and block the save. Preservation covers values, numeric exactness and array order, not identical whitespace or object-property order. Unknown fields outside an explicitly designated metadata area remain invalid. Published metadata is immutable, so layout-only changes require a new draft/version. Exact layout fields and structural validation remain designer specification work; numeric limits belong to L16. No implementation change is implied.

### Definition content comparison — 2026-10-31

The owner confirmed L14 and language design section 12.4. Canonicalization ignores insignificant whitespace and object-property order, preserves actual values, numeric exactness and array order, and includes the entire definition with embedded designer metadata. It must not trim strings, insert defaults, remove nulls or round numbers. Reject duplicate object properties before normalization. Version the canonicalization rules without silently replacing published fingerprints or rewriting historical content. A content fingerprint does not replace workflow key/version or prove equivalent execution behavior. Exact canonicalization/fingerprint algorithms, fingerprint format and version representation remain specification work, consistent with L10 precision requirements. No implementation change is implied.

### Validation and runtime diagnostics — 2026-10-31

The owner confirmed L15 and language design section 13.2. Diagnostics provide stable machine-readable codes, stages, severity, readable messages with bounded safe details, and applicable JSON Pointer locations, element keys and related conflict locations. Errors block publication; warnings do not. Report bounded independent validation errors where possible and skip dependent checks when their prerequisites are invalid. Use line/column information for parsing failures where appropriate and omit irrelevant locations. Keep validation/runtime failure categories distinct, preserve command-failure semantics and do not expose internal stack traces, secrets or unauthorized data. Applications depend on codes, not exact wording. Exact catalog/response fields, host HTTP mapping and L16 numeric limits remain specification work; no core endpoints or runtime implementation are implied.

### Resource-limit enforcement — 2026-10-31

The owner confirmed L16's enforcement direction in language design section 14.2. Limits are centrally enforced and documented per supported workflow-language version; authors cannot raise them, and changes must preserve published-definition and running-instance support. Reject excessive definitions before publication and excessive runtime input before acceptance; never truncate submitted data or omit required tasks. Execution-budget failures roll back the command. Validate combined record budgets, paginate large reads and indicate omitted diagnostics. The owner subsequently selected the initial numeric values in language design section 14.2: 200 nodes, 500 transitions, 100 tasks per activity, 50 automatic steps per command, 100-character ASCII keys, 64 KiB serialized UTF-16 per structured result or JSON variable, 16 runtime JSON container levels, 100 properties per object, 1,000 items per array, 2,000 characters per expression, 16 alternatives per oneOf, read pages of 50 by default/100 maximum, and at most 100 returned diagnostics. Combined budgets still apply. Precise counting/serialization rules, remaining aggregate/work/byte budgets and validation against representative workloads remain pending. Existing F001 storage/task ceilings remain unchanged; this decision adds no migration or runtime implementation.

### Stable application capability contracts — 2026-10-31

The owner confirmed L17's simple compatibility approach in language design sections 11.3/14.3. Capability identifiers represent stable input/output and behavioral contracts; compatible implementation changes retain the identifier, while breaking changes use a new one. Check required registrations and declared contracts before publication and application upgrades. Retain old capabilities for published definitions that may still start and for running instances, including future steps. Missing/incompatible support must fail explicitly without substitution or skipped work. Current authorization and business data remain runtime checks. No separate capability-version system is introduced initially. Structural comparison or fingerprints cannot prove behavioral compatibility; application upgrade verification remains required. Exact registration metadata, check mechanisms and diagnostics are still specification work. No runtime implementation is implied.

### Top-level workflow document — 2026-10-31

The owner confirmed the first part of L18 in language design section 12.1. Require integer schemaVersion (initially 1), a workflow key, positive integer definition version, nonempty name, a top-level startPolicy object and explicit variables/nodes/transitions arrays. Description and designer are optional; omit unused optional fields rather than using null. Reject unknown top-level fields, retaining L13's bounded metadata allowance inside designer. The start policy groups authorization, guards and accepted start inputs; the START node identifies entry without duplicating those requirements. Administrative/database identity and lifecycle fields remain outside the portable definition. Internal contracts remain open, so L18 is partly agreed. No implementation change is implied.

### Start-policy structure — 2026-10-31

The owner confirmed startPolicy fields under L18: required nonempty permission string, required inputContract array and optional guards array whose omission means an empty list. Every declared guard must pass. Reject unknown fields and explicit nulls; denied permission, invalid input or a failed guard fails the start command without committing a partial instance or tasks. Input descriptors, guard-entry/input-binding notation and command validation order remain specification work. Language design section 12.1.1 records the contract. No implementation change is implied.

### Simple input-field descriptors — 2026-10-31

The owner confirmed a shared descriptor structure for simple start and human-task inputs: required key, type, required and nullable fields, with optional label and description. Keys are unique within the input contract. Types are the six established scalars using L10 representations. Missing required inputs, disallowed nulls, invalid types and undeclared fields are rejected; an omitted optional input without a default stays absent. Inputs do not automatically write variables. Structured task submissions retain resultContract, while structured start-input representation remains open. Language design section 12.1.2 records the contract. No implementation change is implied.

The owner additionally selected optional literal defaults, applied only to absent optional inputs. Reject required-plus-default descriptors and defaults incompatible with the type, nullability or engine limits before publication. Explicit null and invalid input are never replaced; default null requires nullable true. Expressions and cross-field references are not evaluated as defaults. Additional simple-input constraints are explicitly deferred as a future idea, not accepted descriptor fields; this does not defer the agreed structured-data schema features. Broader variable initialization and command ordering remain specification work.

### Start guard entries — 2026-10-31

The owner confirmed start guard objects with required nonempty guard identifiers and explicit inputs mappings (empty object when no declared arguments are needed). Each binding initially uses source startInput and a key naming a declared start input, read after validation/default application. Caller identity and trusted context are supplied separately. Guards execute in array order, stop on the first rejection or technical failure, and do not change business/workflow state. Reject invalid registrations/bindings and incompatible types before publication where detectable; validate actual arguments at runtime and never convert a missing required argument silently to null. The start command remains atomic. See language design section 12.1.3; guard-registration contracts, diagnostics and the complete command sequence remain specification work.

### Structured start-input descriptors — 2026-10-31

The owner selected JSON start inputs within the existing startPolicy.inputContract array, using type JSON and a required embedded schema under the L11 profile. Non-null roots are objects/arrays; required and nullable remain descriptor-level rules. Optional literal defaults must satisfy the same schema/nullability and applicable limits. Start guards bind whole values through source startInput and key; nested-path bindings are outside that initial structure. Structured task submissions remain in resultContract, and scalar constraints stay deferred. Valid structure does not establish host membership/authorization, and explicit bindings remain necessary to initialize variables. Start payload/evidence byte budgets still require specification. Language design section 12.1.4 records this decision; no implementation change is implied.

### Variable declaration structure — 2026-10-31

The owner confirmed variables with required key/type/nullable, optional label/description and a required embedded schema for JSON only. Variable keys are unique within the definition's variable declarations. The six scalar types and JSON follow L10/L11. Variables do not have an input-style required flag: they may remain uninitialized until assigned, while nullable governs explicit null and missing required reads still fail. Input names do not imply variable bindings. Initialization, default and permitted-write notation remain separate decisions; this agreement does not introduce a variable-default field. Language design section 12.1.5 records the structure. No implementation change is implied.

### Variable initialization and permitted writes — 2026-10-31

The owner confirmed optional startPolicy.initialize mappings from destination variable names to source startInput/key or source literal/value. Omission means no mappings. Destinations must be declared and unique; validated inputs include their defaults, while a missing optional source leaves its variable uninitialized. Reject invalid types, schemas, limits and disallowed nulls. Initializers cannot depend on other mappings or variables; validate the complete set before applying it atomically. There is no separate variable-default field initially.

Initialization and service-output mappings identify permitted writes without a duplicated writers list. Guards/expressions cannot write variables, task submissions do not implicitly write them, and separate variable-update commands require explicit authorization/write contracts. Whole-value replacement, concurrency, transaction and protected-review-material rules remain. Exact service-output notation, variable-command contracts and the complete start sequence still require specification. Language design section 12.1.6 records this decision; no implementation change is implied.

### Common node fields and START/END — 2026-10-31

The owner confirmed required node key/type/nonempty name and optional description, rejecting fields outside the selected node type and keeping connections in the top-level transitions array. START adds no fields; its identity comes from type rather than a reserved key, and start requirements remain in startPolicy. END adds a required nonempty result string for normal business completion, distinct from task outcomes and lifecycle status. END performs no business action and has no outgoing transitions; multiple ends are allowed. Other node-specific structures remain open. Language design section 12.1.7 records the decision; no implementation change is implied.

### Service-node structure and mappings — 2026-10-31

The owner confirmed SERVICE_TASK fields action, inputs and outputs alongside common node fields. Action is a nonempty registered identifier; inputs maps action argument names to sources and outputs maps destination variables to sources, with explicit empty objects when unused. Variable/key bindings read declared variables; actionOutput/key bindings select returned values for outputs. Output mappings may also read pre-update variables under the existing independent-update rules. Validate against the action's registered type contract and variable declarations without duplicating that contract in the node. Execution remains synchronous and atomic, with one unconditional success transition and no error route or automatic retry configuration. Fact/prior-submission source notation remains open. Language design section 12.1.8 records this decision; no implementation change is implied.

### Additional input sources deferred — 2026-10-31

The owner deferred direct application-fact and prior-task/activity-submission bindings as future ideas for service tasks and other node/capability inputs. This narrows the earlier L08 source-selection direction and supersedes the statement above that these source forms merely await notation. Initial service inputs bind declared variables; outputs use actionOutput or permitted pre-update variable sources. Existing startInput/literal initialization and startInput guard bindings remain unchanged. No fact, activitySubmissions or automatic completedActivity binding is selected. This does not remove application-owned data access, authorized exact-submission APIs or the separate declared facts expression context. Future retrieval bindings require explicit identity, authorization and bounds; no implicit latest-node lookup is approved. Language design sections 10.4 and 12.1.8 record the deferral.

### Exclusive gateway naming and future extensions — 2026-10-31

The owner confirmed renaming the workflow routing node from `DECISION` to `EXCLUSIVE_GATEWAY`, retaining ordered Boolean conditions on outgoing transitions. The gateway has common node fields only, with no node-level calculation or output mapping. A separate SERVICE_TASK may calculate a business result and explicitly map it to a variable used by routing conditions. Decision tables remain a future idea. Inclusive and parallel gateways are also deferred as distinct future node types, requiring branch/join and execution-state semantics beyond the current single active process position. Unsupported node types are rejected; no compatibility alias for DECISION, placeholder fields or parallel storage is selected. Language design section 12.1.9 and L03/L18 record the decision. Earlier references to DECISION as the current routing type are superseded; historical STATE/DECISION/FINAL descriptions remain historical.

### Human-task authorization through the host hook — 2026-10-31

The owner confirmed removing permission identifiers from human-task outcomes while retaining a mandatory engine-invoked authorization hook implemented by APOLO (or another host). The host owns business access and action permission policy; core invokes the hook before accepting a new completion and separately enforces assignment, state, declared outcomes, submission contracts, guards, concurrency and completion rules. Denial, missing registration or hook failure prevents completion and committed effects. Form access is checked separately; the submission endpoint need not duplicate the hook's authoritative business authorization check. Trusted actor context cannot come from ordinary browser fields. Successful receipt replay still reauthorizes access without rerunning completion or requiring an open task. Exact hook API and replay integration remain specification work. This supersedes earlier outcome-permission placement and the interrupted proposal to rely solely on authorization before calling core. The separately agreed startPolicy.permission is unchanged. See language design section 9.1.

### Human-task assignment structure — 2026-10-31

The owner accepted the proposed assignment structure: HUMAN_TASK requires assignment with a nonempty registered resolver identifier and an explicit inputs object, using an empty object when no arguments are needed. Initial inputs bind declared workflow variables through source/key forms. Core validates bindings and the resolver's complete task list and creates the activity/tasks atomically under the existing SINGLE/ALL cardinality and fixed-list rules. Direct fact/prior-submission bindings remain deferred. Exact resolver API and returned field names remain open. Language design section 12.1.10 records this portion of L18; remaining human-task field structures are still under review.

### Human-task completion structure — 2026-10-31

The owner accepted the completion notation: HUMAN_TASK requires a completion object with an explicit SINGLE or ALL policy and no default. ALL requires contributionOutcome referencing an outcome declared by the same node; SINGLE rejects that field. Existing fixed-task-list, early-resolution, concurrency and rollback behavior remains mandatory without additional configuration fields. Language design section 12.1.11 records this portion of L18. Remaining submission/outcome structures and resolver API details remain under review.

### Human-task submission-contract structure — 2026-10-31

The owner accepted required inputContract and resultContract fields shared by every outcome. Human-task inputContract uses the agreed scalar descriptors, with an explicit empty array when unused. resultContract requires mode FORBIDDEN, OPTIONAL or REQUIRED; schema must be absent for FORBIDDEN and is a required embedded schema object for OPTIONAL/REQUIRED, under the restricted profile and local-reference rules. Supplied results must be objects, never top-level null. Outcome and comment remain separate, and accepted submissions do not implicitly write variables. Language design section 12.1.12 records the structure; outcomes and remaining resolver/API details are still under review.

### Human-task outcome fields — 2026-10-31

The owner accepted a required nonempty outcomes array. Each outcome requires key, nonempty label and explicit Boolean requiresComment, with optional guards using the existing guard/inputs entry shape. Keys follow technical-key rules and are unique within their human node; array order is presentation only. Required comments reject missing/empty/whitespace-only values; optional comments remain allowed. Outcomes share the node submission contracts and require host-hook authorization, with routes declared separately. Permission fields and outcome-specific input/result overrides are unsupported. Section 12.1.13 records the fields; guard input sources remain under review.

### Outcome guard input sources — 2026-10-31

The owner accepted variable/key, taskInput/key and whole taskResult bindings for human-task outcome guards. Current submission inputs are defaulted/validated, results and comment requirements checked, before guards run. Trusted actor/task/outcome context is supplied separately. Missing required arguments fail; optional arguments may remain absent only under the registered contract, without converting absence to null. Guards run in order, stop on rejection/error and do not apply effects. Direct facts, earlier submissions and nested-path bindings remain deferred. Section 12.1.14 records this selection; it does not expand sources for other capabilities. Exact guard API/context and diagnostic details remain open.

### Human-task type and assembled fields — 2026-10-31

The owner confirmed required taskType directly on HUMAN_TASK as a nonempty existing catalog code, without taskTypeVersion or frontend component/form identifiers. The host owns presentation; the pinned node owns execution and submission rules. Disabling authoring selectability preserves support for published workflows, future starts and running instances. Section 12.1.15 assembles the selected human-node fields. Field placement is settled; host API contracts, diagnostics and transition notation remain specification work.

### Transition fields and gateway order — 2026-10-31

The owner accepted top-level transition objects with required key/from/to. START and SERVICE_TASK have one unconditional route; HUMAN_TASK routes use outcome; EXCLUSIVE_GATEWAY routes use either condition or default true, never both. Each gateway evaluates its conditional routes in their relative order in the transitions array, without numeric priority; the default is considered only after all conditions are false, regardless of array position. Existing first-match/error/rollback semantics remain. Source-inappropriate fields, unknown fields, transition actions/guards/permissions and outgoing END routes are rejected. Section 12.1.16 settles this notation under L03/L18; earlier statements leaving route-order notation open are superseded.

### Complete booking definition example — 2026-10-31

At the owner's request, language design chapter 15 now replaces the minimal single-review example with a complete illustrative booking workflow using the selected structures. It includes explicit start initialization, host-calculated review requirements, an exclusive gateway, fixed-roster ALL review, host-hook authorization, an approval guard and separate approval/rejection service actions with explicit output mappings and terminal results. The chapter explains host capability contracts and successful, rejected, failed, concurrent and replayed commands. One-booking scope, no-review eligibility and sample status/capability names are examples, not confirmed APOLO production policy. FORBIDDEN structured results keep this example focused; other selected result/guard forms remain illustrated in section 12.1. No implementation or runtime verification is claimed.

### Optional start authorization through guards — 2026-10-31

The owner explicitly selected optional start authorization via guards only, with no mandatory start authorization hook. Remove startPolicy.permission. A definition may declare a host guard such as hasAuthorisation with a fixed permission argument; if no authorization guard is declared, core performs no start authorization check. Declared guards still fail closed on rejection, failure or missing registration, while input validation and workflow rules remain mandatory. Start guard inputs now support literal/value for fixed configuration alongside startInput/key; permission names need not come from caller input. The host supplies trusted identity separately. This supersedes earlier requirements for a mandatory start permission and earlier notes preserving startPolicy.permission. The mandatory host hook for human-task completion and authorization of receipt access remain unchanged. Sections 12.1.1–12.1.3 and the booking example record the decision; no runtime implementation is claimed.
