# F026 — Task administration and administrative reassignment

**Status:** IMPLEMENTED revision 2 — 2026-11-14 (T09/T11/T13 complete; collapsible filters/chips, dialog spacing/action alignment and destination search feedback live-verified; Task name follow-up implemented with unit/build/fixture checks and subsequent owner-reported successful testing). ## Outcome and agreed scope

Provide a shared workflow-ui task administration page across instances, opening existing task details for authorized administrative actions. OPEN is the default; completed and cancelled tasks are available for inspection. Allow reassignment of an OPEN task's effective target, including USER, GROUP and ROLE kind changes. These decisions and the recommendations below were accepted by the owner on 2026-11-14.

Include core queries/command, optional shared web/UI integration, sandbox host adapters and focused verification. Preserve task identity, fixed SINGLE/ALL obligations, frozen review inputs, recorded answers and host policy. Existing administrative release remains available where permitted. Workflow cancellation remains an instance operation reached through the instance link; F025 delivery is separate and concurrent.

Exclude delegation/return-to-owner, completion on another person's behalf, individual-task cancellation, reopening, bulk actions, saved searches, exports, dashboards, user/group membership administration, input refresh, new assignment columns, history reconstruction and APOLO implementation. The owner explicitly selected existing task columns as current state and TASK_CREATED as original assignment evidence. Do not add duplicate original-assignment storage or a reconciliation state machine.

Authority: [constitution](../../constitution.md), [CON-03/05/06/07/08/10/12/13](../../constraints.md), [ASM-02/03/04/06/10](../../assumptions.md), [design precedence](../../design-sources.md), [F017](../F017-task-claim-release/spec.md), [F020](../F020-human-task-input-bindings/spec.md), [F021](../F021-all-collective-review/spec.md) and [database design](../../architecture/workflow-engine-database-design.md). This specification supersedes F017's permanent-target restriction only for explicit audited reassignment; ordinary claims/releases still preserve the target.

## R01 — Original evidence, current target and assignee

The existing assignment_kind/assignment_ref columns represent the effective target now. assignee_ref represents the responsible individual now. Current reads, inbox membership, eligibility and administrative filters use these columns. The original assignment remains in immutable TASK_CREATED history, interpreted using its existing schema version. Do not rewrite that event, add original-assignment columns or reconstruct current assignment by replaying history.

Remove only the historical-target/current-row equality assumption in RuntimeTaskCreationEvidence. Keep historical field/schema validity, task key/identity/linkage, creation time, original initial-assignee rules and input-snapshot/reference integrity. A legitimate difference between original and effective target is not corruption. Do not introduce a latest-reassignment lookup or require an assignment-event chain to read inputs. Reassignment remains atomic and audited under R04.

Example: task #123 was created for GROUP Finance and claimed by Ana. Reassigning it to USER Dan changes the row's target and assignee to Dan. TASK_CREATED still says Finance; a new administrative history entry explains the change. Claim/release events already explain ownership history. Current task details say Assignment and Assignee; the existing authorized history is the source for original assignment, without adding another field to every task DTO/list row.

Receipt snapshots remain frozen descriptions of their command's result. Replaying Ana's earlier accepted claim must not substitute Dan or compare its historical assignment with current columns. Preserve supported receipt formats. Completed tasks cannot be reassigned, so completion actor/USER-target consistency continues to use the effective target frozen at completion; do not weaken that check or rewrite submissions.

## R02 — Reassignment behavior

Only OPEN tasks belonging to the active activity of an ACTIVE instance may be reassigned, including claimed tasks. Preserve task ID/key, activity, task type, creation/due dates, fixed roster/count, review reference, pinned contract, inputs, variables and other tasks. Reassignment neither progresses the workflow nor generates outputs or answers.

The command replaces the target with one valid USER/GROUP/ROLE target. USER sets assignee_ref to that user's reference. GROUP/ROLE sets assignee_ref to null, including when the displaced claimant belongs to the new target. Normal pinned OPTIONAL/REQUIRED claiming then applies. No combined target-change-and-shared-user-reservation is supplied. Repeating the current target with a fresh command fails CONFLICT even if claimed; use existing administrative release to clear a shared claim. An identical successful command retry follows R04 replay.

Validate destination existence and task-specific suitability through the host, for USER as well as shared targets. A shared target also requires deployed membership-provider support. Reassignment is not a permission override: normal business access, current membership, claimant exclusivity, no-self-approval and host distinct-person rules apply when the task is later acted upon. ALL continues counting tasks, not distinct users; changing recipients cannot remove an obligation or invalidate/replace an earlier answer.

Frozen inputs remain exactly as captured. If they describe a review basis incompatible with the destination, the host rejects reassignment; core does not regenerate them or infer business suitability from JSON. No implicit business effects/callback are added for this administrative assignment operation.

## R03 — Host authorization and discovery

Separate permission to open/use task administration, current exact-task business access and permission to reassign that task. Shared libraries do not define a global administrator role. Sandbox administrators receive list/inspection/reassignment access; production hosts may restrict it by business scope. Viewing/reassigning never grants completion authority. Direct core commands also require the host authorization/target-validation adapter; no adapter or adapter failure grants permission.

The host offers a bounded target lookup for this exact task and chosen kind, returning reference/display label choices. Require current exact-task access and reassignment permission before exposing directory choices; ordinary task visibility is insufficient. Administration collection access independently requires its host administration grant. The host owns the directory, supported kinds, business eligibility and display labels. Never enumerate the entire directory in the browser. Lookup is advisory; revalidate the selected reference on execution. The sandbox uses its known user/shared-assignment fixtures, not invented account administration.

After reassignment, the former target/claimant loses access derived solely from that assignment. Other independent host grants remain. The new target gains the normal task access associated with its effective assignment; previous-decision and input visibility retain existing receiving-task rules. Receipt recovery separately requires current host business access and the original receipt actor, not current membership or continued reassignment privilege. Do not grant access merely because someone appears in TASK_CREATED or an old reassignment event.

## R04 — Command, audit, concurrency and errors

Add REASSIGN_TASK and ReassignWorkflowTask(commandId UUID, instanceId, taskId, expectedLockVersion, assignment TaskAssignmentTarget, reason). IDs are positive longs and token is nonnegative. References follow existing exact, case-sensitive bounded target rules. Reason is nonblank, well-formed Unicode, at most 1000 UTF-16 code units; retain exactly without trimming. No client actor, assignee override, result or variable input is accepted.

Require trusted USER context. Validate request shape/current business access, then resolve a successful receipt before fresh permission, lifecycle, destination lookup and version-dependent work. Successful replay returns its original snapshot and performs no target validation/mutation. On a miss require reassignment permission and validate expected version/active aggregate, target and unchanged-target rejection. Acquire and flush the existing early version-checked aggregate write before mutation. State, authoritative history, receipt and durable recorder participate in the host transaction; adapter/recorder/persistence failure rolls back the attempted operation.

Use the existing task-bearing WorkflowCommandResult/WorkflowExecutionResult shape, identifying the reassigned OPEN task and ACTIVE activity/instance. Preserve existing fingerprints; new operation uses request-v3 conventions with exact instance/task IDs, expected token, target kind/ref, reason and trusted actor identity. Attempt time/correlation are excluded. Reserve result schema 8 for REASSIGN_TASK only, retaining the existing task-bearing envelope and nested codecs; F025 schema 7 remains cancellation-specific. Validate resulting USER target/assignee equality or shared-null ownership, entity links, active state and single-event history range. Preserve older operation writers/readers and decode by operation/version without consulting current assignment.

Append one TASK_REASSIGNED history event, detailsSchemaVersion 1, with exactly previousAssignment {kind, ref}, assignment {kind, ref}, previousAssigneeRef, assigneeRef and reason. Existing columns hold task/activity/instance, actor, timestamp, command and sequence. This is an ordinary audit fact describing the row update, not a second state store. Do not emit synthetic claim/release/TASK_CREATED events. Delivery uses eventSchemaVersion 1 with previousAssignmentKind, previousAssignmentRef, assignmentKind, assignmentRef; omit free-text reason and assignee fields from delivery. History follows existing exact-task authorization. Do not mutate historical bytes.

No automatic mutation retry. Reassignment racing completion, claim/release, another reassignment or cancellation uses the same aggregate boundary; only a valid serialized mutation commits. A stale command cannot move a completed/cancelled task or displace a newer owner. Changing reason/target/token under an accepted command ID conflicts.

Malformed input: INVALID_INPUT (400). Missing/concealed access: NOT_FOUND (404). Accessible task without reassignment permission: REASSIGNMENT_FORBIDDEN (403). Invalid/ineligible destination: INVALID_ASSIGNMENT (422). Unchanged target: CONFLICT (409). Current token but closed/noncurrent work: INVALID_STATE (409). Stale token and command-ID/concurrent conflicts retain existing 409 categories. Authorization/lookup infrastructure failures fail closed using existing sanitized lookup/configuration categories. No existence/detail leak precedes access checks.

## R05 — Cross-instance administration collection

Add a dedicated administration query rather than changing My tasks or iterating through instances in the browser. Return task metadata only, not review inputs, results or arbitrary history. Include claimed and unclaimed work. Columns: task/node name and type, instance ID, status, effective target, current assignee and creation time; link to the existing exact-task page.

Filters are taskName (case-insensitive literal contains), status (OPEN default; COMPLETED, CANCELLED or ALL), taskType code, assignmentKind, assignmentRef, assigneeRef and instanceId. Assignment reference requires kind; assignee filter selects exact nonempty user reference. Other omitted filters mean unrestricted within the host-authorized scope. Only taskName supports substring matching; all other text filters retain exact semantics. No unassigned-only filter in this slice. Use stable ascending task-ID cursor pagination, default 50, maximum 100; no total count. Reset cursor when filters change. A page may be empty with continuation after host filtering; never infer exhaustion until continuation is absent. Filters do not grant access. Concurrent changes are observed on refresh; no snapshot-consistency promise.

Hosts must authorize the page and each returned task; denied rows and aggregate counts must not leak. Query and authorization work must remain bounded. Do not scan all instances/tasks to manufacture a complete page. Existing host-authorized paging semantics apply, including continuation when candidate filtering yields fewer visible rows. Opening a row rechecks exact-task access. Names/labels come from pinned/task-type metadata and host target labels, not arbitrary client content. Displaying retained node labels must not require current executable canonicalization or capability support; this does not grant execution compatibility. Missing/malformed required node metadata still fails explicitly, and command/evidence validation remains unchanged. Closed rows offer inspection, not reassignment/release.

## R06 — Shared web/UI integration

Under the existing independently enabled runtime read group, add GET /tasks/administration with R05 query fields plus afterId/limit, GET /tasks/{taskId}/reassignment-availability returning {allowed, instanceLockVersion}, and GET /tasks/{taskId}/reassignment-targets?kind=...&query=...&cursor=...&limit=.... Target search defaults to 20/max 50; query max 200 UTF-16 code units, optional opaque cursor max 1000, response {items:[{ref,label}],nextCursor}. Require host access before lookup. Missing reassignment support yields unavailable without breaking read-only consumers. Directory lookup/permission failures are errors, never permissive fallbacks.

Under runtime command activation, add POST /instances/{instanceId}/tasks/{taskId}/reassign with {commandId,assignment:{kind,ref},reason}, and POST /commands/reassign/replay with the same fields plus instanceId/taskId. Use X-Expected-Lock-Version, canonical UUID, decimal-string IDs/tokens, existing 16 KiB bound, duplicate/unknown-field rejection and existing mutation/replay wrappers. Read and command providers remain optional/independent as in F015/F017; no global infrastructure changes.

Add the Task administration page/navigation through host routing. From task details, Reassign opens a Material dialog showing the current target/assignee, target kind and host-backed selection, and required reason. Warn that existing ownership is replaced and review data is unchanged. Search performs the existing authorized host destination lookup, without submitting reassignment. Display a small indeterminate spinner and Searching destinations message beside Search while pending. After a successful search, show the number of destinations loaded (singular/plural, including zero), with More available when a continuation exists; this is not a directory-wide total. Reset feedback on changed kind/query, suppress stale results, and retain existing errors and loading guards. Keep the reassignment dialog controls in a single column with 16 px gaps and left-aligned Search/More actions. Place Reassign task inside the existing task-detail action row alongside Instance, Activity and Refresh, retaining natural narrow-screen wrapping. Administrative release remains separately labelled and authorized. Availability is advisory; backend checks are authoritative.

Export named TypeScript WorkflowReassignmentTarget ({ref,label}) and WorkflowReassignmentTargetPage ({items,nextCursor}) contracts from the root UI entry point. WorkflowTaskReassignment.targets and consumers use these names. Cursor remains opaque and host-owned; preserve limit/continuation, host registration and wire shape, without totals or Spring Page exposure.

Freeze the complete confirmed command and token. Preserve pending/unknown outcome and session isolation; no automatic mutation retry. Lookup-only recovery uses the same payload; a miss does not prove an in-flight command failed, so any explicit retry retains the original command. A definitive stale/conflict response requires refresh and a new confirmation. Success refreshes task details/list and current action availability; if the user loses access show the existing concealed-access state without displaying cached protected inputs. Read-only consumers still render details without command providers. Raw command recovery stays sandbox diagnostics. Follow the shared frontend style guide without redesigning unrelated pages.

## Acceptance and readiness

- AC01 (R01/R02): USER→USER, USER→shared, shared→USER and shared→shared on OPEN work preserve identity/inputs/roster; shared destinations clear claimants and follow pinned claiming. Unchanged/closed targets fail without writes.
- AC02 (R01): Original TASK_CREATED and input evidence remain valid after repeated kind changes; current inbox/eligibility uses effective target. No history replay/reconciliation is required. Old claim/start/completion receipts retain historical snapshots. Completion by the new USER reads back with correct original submission attribution.
- AC03 (R02/R03): Unknown/disallowed target, unavailable provider, unsuitable frozen basis and denied administration fail closed; former assignment grants disappear, independent grants persist, new recipient receives normal access. Administrator cannot complete solely by being administrator.
- AC04 (R04): Audit/receipt/handoff commit once; exact replay survives later reassignment/closure and privilege loss under current business access. Changed payload conflicts; recorder failure rolls everything back. Controlled races against completion, ownership and F025 cancellation do not overwrite winning state.
- AC05 (R05): Across multiple instances, default OPEN includes claimed/unclaimed; closed/status and each selected filter, exact identity, paging and filtered-empty continuation behave correctly without cross-scope disclosure or per-instance browser traversal.
- AC06 (R06): Shared page/details/dialog, target lookup, validation, stale refresh, uncertainty recovery, permission loss, closed inspection and view-only integration work through sandbox host adapters. Only changed UI interactions require fresh browser checks.
