# F035 implementation plan

Revision 1 · [Specification and acceptance scenarios](spec.md).

1. **Package and registration (R1–R3).** Add the `http` secondary entry point alongside `workflow-ui/projects/workflow-ui/administration` and `runtime`. Place shared transport and group-specific code under `workflow-ui/projects/workflow-ui/http/src/`. Import the existing tokens and types from their public package boundary. Keep root imports free of eager page or HTTP configuration. Expose group-specific provider functions and documented NgModule/standalone examples. For example, the proposed administration call is `provideWorkflowAdministrationHttp('/api/workflow')`. Expose a way to delegate to standard implementations when a host overrides individual operations. Retain existing peer versions.
2. **Map the existing server.** Use controllers under `workflow-web/src/main/java/io/github/leontecristian/workflow/web/controller/{definition,tasktype,instance,runtime}/` and the installed page contracts as the mapping authority. Extract reusable behavior from the pre-F035 console transport and command request builder. Preserve exact-text reads/writes, encoding, bounds, response shapes and group-specific failure handling. Bridge AbortSignal to HttpClient subscription lifetime, including synchronous errors, pre-abort and listener cleanup.
3. **Migrate the reference consumer.** In `workflow-test-host/frontend/src/main.ts` and `src/app/data/`, adopt the shared providers and remove duplicated standard endpoint mappings. Keep the sandbox’s own session bootstrap, mutation CSRF header, session-scoped 401 handling, member-facing business history, business start/replay, navigation and diagnostics working through host-owned composition. Configure any required Angular HTTP interceptor in the sandbox. Check interactions with other ConsoleSession callers before changing shared helpers. Document configuration, required server groups, permissions vs client capability selection and host overrides in [workflow-ui/README.md](../../../workflow-ui/README.md). Package from built output for downstream consumers.

## Verification planned for implementation

Register command, cancellation and reassignment providers in the application injector used by root-scoped `CommandRecovery`. Preserve optional method presence when a host enables only a subset. Keep a legitimate JSON null submission distinct from an unreadable response. Exercise a reserved-character lookup key, an opaque task precondition and the existing definitive `503 RESULT_VALIDATION_FAILED` case so error mapping does not change recovery decisions.

Existing wire behavior and expected results are documented in [F014](../F014-definition-catalog-administration/implementation.md), [F015](../F015-runtime-task-instance-extraction/implementation.md), [F031](../F031-shared-runtime-command-coordination/implementation.md) and [F034](../F034-shared-task-page/implementation.md). Those records do not exercise the new Angular HTTP adapter. Retain their existing assertions and move transport-specific coverage to the new owner.

Use a recording Angular HTTP backend and host interceptor to exercise A1–A5. Cover method-to-route mappings compactly; focus detailed assertions on raw JSON, error bodies, cancellation, preconditions, and host/adapter composition. Extend the existing `workflow-ui/verification/ngmodule-host` fixture to import the packaged entry point. Build the Angular library and its affected reference consumers once; inspect package exports and typings. Use a focused sandbox check of changed host wiring if the interceptor/session boundary changes. No APOLO integration tests, database runs, or repeated workflow walkthrough are planned. Finish when each selected group is usable via the public package, host overrides still work and the affected checks pass.
