# F035 — Optional Angular HTTP adapters for workflow-web

Revision 1 · IMPLEMENTED · 2026-11-20 · Owner: workflow maintainer. [Constitution v6.6.1](../../constitution.md), [constraints](../../constraints.md) CON-01/02/03/10/13/14, [assumptions](../../assumptions.md) ASM-01 and [design sources](../../design-sources.md).

## Outcome

An Angular host using the matching workflow-web endpoints supplies its existing HttpClient, selects the UI capabilities it wants, and configures their API base paths. It can use every shared page backed by those endpoints without writing per-method HTTP calls. APOLO’s first use is the Definitions and Task types pages at `/api/workflow`. The current @workflow-engine/ui 0.0.1 package exposes the page contracts and injection tokens; this feature adds an opt-in implementation. It does not require a coordinated change to the workflow-web 0.1.0 wire protocol.

## Registration and ownership

- **R1 — Explicit bindings.** Export optional Angular provider factories from a public `@workflow-engine/ui/http` entry point. Registration works in standalone and NgModule hosts. Each binding accepts its API base path, including an application context prefix when needed. Join paths with a single slash, encode dynamic segments and query parameters once, and preserve opaque cursors. No URL defaults to APOLO or the sandbox.
- **R2 — Existing host client.** Inject the host-configured Angular HttpClient for every request so its interceptor chain and backend apply. The host owns login, logout, authorization, CSRF, credential policy, global providers, deployment origin, session-scope changes and routing. Installing or importing the library alone performs no HTTP calls and registers no transport. The adapter introduces no retries, session storage, token reads, fetch bypass or alternate HttpClient.
- **R3 — Independent adoption.** Preserve the existing tokens, method signatures and page constructors. A host chooses the supplied provider or its own implementation per token. Enabling administration or read-only pages must not bind command providers or imply server-side access. Cancellation and reassignment are independently selectable and can use distinct read and command mounts. The host may compose a custom adapter with standard operations for host-owned extensions.

## Covered page contracts

Use the existing [UI contracts and consumer guide](../../../workflow-ui/README.md) and [web integration contracts](../../../workflow-web/README.md) as the authoritative operation and payload definitions. The following capabilities are all in scope for this release.

- **R4 — Administration.** Implement all 16 methods on `WORKFLOW_ADMINISTRATION_API`, covering task-type listing/creation/update, definition family listing/detail/metadata, version list/detail/lookup, draft import/replace/copy/delete, validate, publish, retire and export. Keep descending family order on every page, decimal-string cursors/lock tokens, filters, and the original `X-Expected-Lock-Version` where required. Send raw definition text as application/json for import/replace and return export as text without reserialization. Copying a version into a draft sends an empty JSON object; deleting a draft sends no body. A successful validation HTTP response can contain an invalid report. Preserve the report.
- **R5 — Instance viewer.** Implement `WORKFLOW_VIEWER_READS` for metadata, graph, retained history pages and exact history events. Honor the existing viewer error categories and concealed denials. A host can substitute business-history policy, present different navigation or hide history. Do not infer permissions from an actor name or probe alternate routes on denial.
- **R6 — Runtime reads.** Implement the shared `WORKFLOW_RUNTIME_READS` operations for instance lists, variables, My tasks, instance tasks, task detail/contract/submission/previous decisions, activity detail/submissions, and the shared task administration collection. Preserve filters, tokens, ordering and continuation even on empty pages. Preserve exact source tokens where the UI expects raw input, variable or structured result text; use existing form hydration and enforce existing response bounds. SQL IDs, cursor tokens and DECIMAL/JSON values must not lose precision through a JavaScript number conversion.
- **R7 — Runtime commands and recovery.** Bind `WORKFLOW_RUNTIME_COMMANDS` for shared completion and ownership operations, plus separate `WORKFLOW_CANCELLATION` and `WORKFLOW_TASK_REASSIGNMENT` capabilities for their availability, target lookup, execution and receipt lookup as applicable. Keep command ID, expected token, field errors and frozen result JSON intact. Use the established execution vs replay route/body shapes, including the task ID on replay, nested assignment on reassignment and the correct header family (`X-Task-Precondition` vs `X-Expected-Lock-Version`). Receipt lookup must not execute a command. Host-defined business starts, start replay, sandbox diagnostics, external delivery and host task editors are outside the HTTP adapter. Existing host implementations can still supply them.

## Failures, cancellation and acceptance

**R8.** A pre-aborted signal sends no request. Aborting an in-flight call unsubscribes its HTTP request, settles the promise as cancelled and releases listeners. A mutation may already have reached the server. Keep stale responses from replacing a newer page/session using the existing component and host scope contracts. Preserve HTTP status and safe code, diagnostics, field errors and correlation ID where the group contract supplies them, including JSON envelopes received as text. A non-JSON error must retain its known status. Network loss or an unreadable successful write response must not be reported as a successful write or definitive rejection. Administration offers inspection after an uncertain write; runtime keeps the original envelope available for its existing recovery flow.

1. **A1 (R1–R3).** An NgModule consumer registers only administration at a nondefault mount. The packaged Definitions page lists families through the host interceptor. A custom viewer provider continues to resolve; runtime command tokens remain absent. Standalone registration supports the same public API.
2. **A2 (R4).** Register a complete administration adapter. Observe the mapping of each method, including a second page with a large cursor, raw import/replace and export with a large integer and decimal scale, copy/delete body differences, a validation report and a stale-version response.
3. **A3 (R5–R6).** Render or consume a standard graph and history read, task form and submission using real adapter mappings and controlled responses. IDs, source JSON and form bindings survive; concealed reads and an empty page with a continuation remain distinguishable.
4. **A4 (R7).** Completion, ownership, cancellation and reassignment requests and their receipt lookups preserve command-specific bodies, headers and token text. A completion with a large numeric result retains the original lexeme. A lost response triggers no second mutation. Reassignment target pagination uses the read mount and execution uses the command mount.
5. **A5 (R2/R8).** Observe pre-abort and in-flight cancellation, a structured denial/conflict, a malformed error body and an unreadable write response. Host interception remains active. A late prior-session response cannot invalidate a replacement session.

No changes to APOLO source, backend activation, database schema, permissions or designer functionality are part of delivering F035. APOLO can adopt a newly packaged UI release after delivery.
