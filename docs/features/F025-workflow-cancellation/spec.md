# F025 — Workflow cancellation

**Status:** IMPLEMENTED. **Revision:** 1 — 2026-11-14. **Owner:** Workflow project owner. **Constitution:** [v6.6.1 plus the F025 scope clarification](../../constitution.md). Implementation authorized by the owner on 2026-11-14; see the implementation record for actual checks and integration limits.

## Outcome, decisions and scope

An authorized host user can immediately stop an ACTIVE workflow instance and its outstanding human work, retaining its evidence. The owner agreed whole-instance cancellation, immediate stop, explicit host authorization, mandatory reason, receipt-backed retries, optimistic concurrency and shared UI on 2026-11-14. The owner explicitly confirmed that previously committed business effects are not undone and partial ALL submissions survive without completing the review or producing its final output.

Scope: core command/replay, shared web mapping, optional shared instance-view action and sandbox adapters. Administrative describes an engine lifecycle operation, not a universal host role. Sandbox administrators may cancel active instances; APOLO roles, requester withdrawal eligibility and business-status changes remain host decisions.

Excluded: individual-task cancellation, reassignment, roster changes, compensation, cancellation handlers, graph routes on cancellation, asynchronous CANCELLING state, timers, bulk operations, subprocess propagation, deletion, reopening/restart, replacement-instance orchestration and APOLO integration. Normal completion at an END with business result CANCELLED remains distinct. Cancellation does not change pinned definitions or require new definition syntax.

Apply [CON-03/05/06/07/08/10/12/13](../../constraints.md) and [ASM-02/03/04/06/10](../../assumptions.md): host policy/transactions, aggregate coordination, authoritative retained submissions and durable handoff. APOLO access remains unavailable; local implementation cannot establish production integration. Sources: [database lifecycle and concurrency design](../../architecture/workflow-engine-database-design.md), [language lifecycle distinction](../../architecture/workflow-definition-language-design.md), [F017 authorization/recovery](../F017-task-claim-release/spec.md), [F021 ALL](../F021-all-collective-review/spec.md), [web](../../../workflow-web/README.md) and [UI](../../../workflow-ui/README.md) integration contracts.

## Required behavior

### R01 — Stop the complete active aggregate

Cancel only an ACTIVE instance waiting at its single active HUMAN_TASK activity under SINGLE or ALL. Atomically set the instance and active activity to CANCELLED and all OPEN tasks in that activity to CANCELLED with closure reason INSTANCE_CANCELLED. Claimed tasks are included; claimant permission or release is not required. Retain original assignment and assignee as evidence. Set activity closure reason INSTANCE_CANCELLED; activity outcome and instance result remain null. Use one trusted command actor/time for all new closure fields. Retain currentNodeKey at the stopped human node; do not invent an END visit.

Preserve completed tasks and their submissions, prior completed activities, immutable input snapshots, variables, earlier named outputs, associations and history. No task is deleted or credited with a cancellation vote. A partial ALL activity remains CANCELLED, not COMPLETED: exact-task/activity submission reads retain accepted answers, but original resolved-collection bindings remain unavailable and no named output is created for that activity. No downstream transition, service, gateway, output binding or compensation executes.

Cancellation is final for this instance. Later fresh completion/claim/release/cancellation commands cannot mutate it. A previously accepted command can still replay its original historical result under its existing access rules. Required missing/inconsistent aggregate evidence fails HOST_CONFIGURATION rather than committing a partial repair.

### R02 — Explicit host authorization

Core requires a host-supplied cancellation authorization adapter for this operation, including direct core callers. It receives detached instance identity/correlation and trusted command identity, not JPA or security-provider objects. Separate current instance business access from permission to perform a fresh cancellation. Task eligibility, task completion rights and instance visibility alone grant no cancellation permission. No engine roles table or configurable permissions framework is introduced.

Require ActorKind.USER for this slice. The host supplies trusted actor/time/correlation and enforces authentication, CSRF and business policy. Check current instance access for mutations and lookup-only recovery. After a receipt miss, require explicit cancellation permission before revealing lifecycle/version errors or executing effects. Denied access is concealed as NOT_FOUND; an accessible instance with cancellation denied yields CANCELLATION_FORBIDDEN (HTTP 403). Adapter exceptions fail closed as AUTHORIZATION_LOOKUP_FAILED. Missing adapter support cannot fall back to allowed.

Successful replay requires current business access, original actor and matching request, but not continued cancellation privilege. This follows F017 recovery semantics: recovering one's committed result does not execute a new privileged operation. A different actor cannot obtain the receipt. Sandbox policy initially grants fresh cancellation only to administrators; it changes no sandbox request business status and does not remove its instance link.

Hosts may perform cancellation-related business validation/effects through the cancellation-specific callback defined below, in their outer transaction. These follow receipt resolution and aggregate claim, occur once on fresh execution, and roll back with cancellation. Do not execute effects before the early version-checked claim or duplicate them in engine routing. Previously committed effects are never reversed implicitly.

Provide cancelWorkflow(command, context) for engine-only cancellation and an overload cancelWorkflow(command, context, WorkflowCancellationEffect effect). WorkflowCancellationEffect is a host callback with void apply(WorkflowCancellationContext context). Its detached context contains the validated CancelWorkflow command, trusted WorkflowCommandContext, and the pre-cancellation WorkflowInstanceView and WorkflowActivityView captured after the aggregate claim. It receives no entities. Invoke once after fresh permission/state/roster validation and successful claim, before any closure; never on receipt replay. The callback joins the existing transaction and must not independently commit, retry or perform irreversible external delivery. Throwing fails the entire command as sanitized CANCELLATION_EFFECT_FAILED; the host may map its own recognized business rejection outside core without exposing internals. The overload without an effect performs none. Effects must derive from the fingerprinted command and trusted host state; extra client effect inputs are not supported by this contract. Sandbox cancellation uses the no-effect overload.

### R03 — Command, result and recovery

Add operation CANCEL_WORKFLOW and immutable CancelWorkflow(commandId UUID, instanceId positive long, expectedLockVersion nonnegative long, reason String). Reason is required, nonblank, well-formed Unicode, at most 2000 UTF-16 code units (the existing termination_reason capacity), retained exactly without trimming/normalization. Reject unknown/duplicate HTTP fields and client actor, target-task, outcome or variable inputs.

Use a separate WorkflowCancellationResult containing commandId, operation, cancelled WorkflowInstanceView, cancelled WorkflowActivityView, cancelledTaskCount, firstHistorySequence and lastHistorySequence. Count only tasks changed from OPEN by this command, bounded 1–100. No representative task or full roster is returned. WorkflowCancellationCommandResult contains replayed and execution. Core cancelWorkflow returns this wrapper; typed findCancellationReplay returns Optional<WorkflowCancellationResult>. Results are provisional until the host transaction commits; HTTP adapters return only after commit.

Fingerprint operation, trusted actor kind/reference, instanceId, expectedLockVersion and exact reason using the existing request-v3 normalization convention. Command ID remains the receipt lookup key; attempt time/correlation are excluded. Preserve existing operations' fingerprints. Same successful request returns its frozen result before state/version checks; different input under its ID conflicts. Lookup-only recovery never executes on a miss and returns found=false. Receipt lookup must not require the instance still to be ACTIVE.

Use a cancellation-only result schema version 7 with the fields above and existing nested instance/activity codecs. Existing receipt writers/readers remain unchanged. Validate operation, receipt/instance identity, cancelled statuses, null result/outcome, INSTANCE_CANCELLED activity reason, shared closure actor/time, stopped node, instance termination reason, task count and history range. The range contains cancelledTaskCount + 2 events. Never reconstruct a receipt from current mutable state or weaken existing task-bearing receipt validation. Unknown/corrupt formats fail explicitly.

### R04 — Concurrency, transaction and failures

After authorization and successful-receipt miss, compare expected version, validate ACTIVE state, reserve the first history sequence and flush the real version-checked instance write before child writes or fresh host effects. Use the existing MANDATORY host transaction. All new closures, history, receipt, required host effects and durable event handoff commit together; any failure rolls back the whole attempted command, preserving earlier committed contributions/effects. Capture the actual final managed lock version.

Cancellation has no priority over completion, claim or release. Commands based on the same version compete through the aggregate claim. If another mutation commits first, cancellation fails stale/concurrent and does not silently cancel the newer activity. A user must refresh and explicitly submit a new command. If cancellation wins, the competing task operation cannot commit. Duplicate successful commands produce one mutation/event set; post-rollback recovery uses a fresh transaction without automatic business-command retries.

Malformed request/reason: INVALID_INPUT (400). Accessible missing target: NOT_FOUND (404). Stale expected token: STALE_VERSION (409). A fresh request with the current token for a terminal instance: INVALID_STATE (409). Different request under a used command ID: COMMAND_ID_CONFLICT (409). Overlap/persistence conflicts use existing sanitized concurrency categories (409). Authentication, integrity and adapter failures retain existing scoped handling; expose no reason text or internals in error messages.

### R05 — Evidence and reads

In task-key order, append one TASK_CANCELLED per newly cancelled task, then ACTIVITY_CANCELLED, then INSTANCE_CANCELLED, under one command/actor/time and contiguous history range. Select detailsSchemaVersion 1 explicitly for all three events; do not use the generic batch helper's default version. Exact history details are TASK_CANCELLED {taskKey, closureReason: INSTANCE_CANCELLED}, ACTIVITY_CANCELLED {closureReason: INSTANCE_CANCELLED}, and INSTANCE_CANCELLED {reason}. Existing columns carry entity links, actor/time and command ID. Instance cancellation has no task/activity link; activity cancellation has its activity link and no task link. No synthetic TASK_COMPLETED, ACTIVITY_COMPLETED, transition or variable-write events are emitted.

Deliver the same ordered event types through the existing transactional recorder, eventSchemaVersion 1. Exact payloads are TASK_CANCELLED {taskKey, closureReason: INSTANCE_CANCELLED}, ACTIVITY_CANCELLED {closureReason: INSTANCE_CANCELLED}, and INSTANCE_CANCELLED {cancelledTaskCount}, with the count a decimal string. Do not include free-text reason or submissions in delivery payloads. Preserve existing event envelopes and ACTIVITY_RESOLVED sibling-cancellation format.

Existing instance-read authorization governs terminationReason, already part of WorkflowInstanceView. General history authorization governs instance/activity cancellation evidence; exact-task restrictions still govern task events. Cancellation grants no new submission/history access. Graph and activity/task views show the stopped position and cancelled work without a fabricated outgoing edge or completed outcome. Earlier completed stages and submitted ALL answers remain inspectable through existing authorized reads. Closed tasks leave actionable inboxes and expose no ownership/completion actions.

### R06 — Shared HTTP and UI

Under existing runtime command activation add POST /instances/{instanceId}/cancel with exactly commandId and reason, and POST /commands/cancel/replay with those fields plus instanceId. Both use X-Expected-Lock-Version and existing canonical UUID/decimal-string ID/token transport, 16 KiB body bound and scoped errors. Mutation returns {replayed, execution}; recovery returns {found, result}, with result the cancellation command wrapper on a hit and null on a miss. Do not repurpose task endpoints.

Under runtime read activation add GET /instances/{instanceId}/cancellation-availability, returning exactly {allowed, lockVersion}. Require current instance access. allowed is true only for ACTIVE state and current host cancellation permission; missing cancellation support returns false. Adapter failure is a read error, not an allowed fallback. This is advisory and does not replace command authorization. No reason or permission explanation is exposed. Read and command groups remain independently activatable.

The shared instance viewer offers Cancel workflow only with optional cancellation transport configured and matching-version allowed availability. View-only consumers require no command provider. The Material dialog requires a reason, identifies the instance and explains that outstanding tasks stop while previous decisions/business effects remain. Confirmation freezes command ID, version and exact reason; prevent duplicate submission while pending. No automatic mutation retry. On stale/conflict, refresh and require a new confirmation; on unknown transport outcome retain the frozen command and perform explicit lookup-only recovery before permitting a replacement. A miss is not proof that an in-flight attempt cannot commit; any explicit retry must reuse the original command. Preserve existing session-change isolation and safe command-buffer behavior. Raw recovery diagnostics remain sandbox-only.

After success/recovery refresh authorized instance, graph and availability; render termination reason as plain text with actor/time and no available cancellation action. Existing task/activity screens must correctly render cancelled state and retained submissions. Permission loss or omitted adapters hide the action without making backend checks optional. Follow the shared frontend style guide; no unrelated viewer redesign.

## Acceptance scenarios

- **AC01 (R01/R05):** Cancel SINGLE with USER or claimed shared work; all new closure fields/reason/history agree, no route/service executes, inbox/actions close and prior state remains inspectable.
- **AC02 (R01/R05):** Cancel partially contributed ALL: completed tasks/results remain, only OPEN tasks cancel, activity has no outcome or final output, exact submission reads work and resolved-collection access remains unavailable. Include the 100-task roster bound.
- **AC03 (R02/R03):** Deny unauthenticated/inaccessible/not-permitted execution; fail closed on adapter failure. Original actor can recover under current business access after cancellation privilege loss; another actor or lost business access cannot recover. Invalid reason/transport fields fail without writes.
- **AC04 (R03/R04):** Identical replay after closure returns frozen success; changed reason/token/actor conflicts or is denied as appropriate. Lookup-only miss never mutates. Existing start/completion/ownership receipts remain readable. Fresh terminal cancellation fails.
- **AC05 (R04):** Controlled cancellation-versus-completion and cancellation-versus-ownership races commit only the winning aggregate mutation; stale cancellation never follows advancement into a new activity. Duplicate cancellation commits once.
- **AC06 (R04/R05):** Failure after child closures, in a participating host effect or durable recorder rolls back cancellation/history/receipt/handoff and that effect; prior ALL contributions and prior committed business effects survive.
- **AC07 (R05/R06):** Shared web/host wiring and viewer support confirmation, exact reason, safe unknown-outcome recovery, stale refresh, permission loss and read-only configuration. Cancelled graph/task/activity rendering retains evidence and shows no invented transition. Browser checks cover only changed interactions/rendering.
