# F005 — Minimal SINGLE workflow execution

**Status:** IMPLEMENTED (core); manual acceptance remains BLOCKED with T11 open. Package/artifact/bootstrap checks passed; AC01–AC13 behavioral execution is NOT RUN. See [implementation.md](implementation.md#4-verification). **Revision:** 1 — 2026-10-31. **Owner:** Workflow project owner. **Constitution:** [v3.0.0](../../constitution.md).

## Outcome and scope

Execute the exact F004 publication subset: `START → HUMAN_TASK (SINGLE) → END`. A trusted host starts a specific published version, core creates one directly assigned task, and the assigned user submits the sole declared outcome to complete the instance. Persist relational state, immutable accepted submission/history, successful-command receipts and transactional event handoff.

Build on [F004](../F004-definition-management-validation/spec.md), [F003 mappings](../F003-core-persistence-model/persistence-contract.md) and the [F001 storage contract](../F001-initial-database-schema/schema-contract.md). Apply CON-01–10, CON-12 and the no-result part of CON-13; ASM-01–05/08/09 remain integration and verification obligations. The [language design](../../architecture/workflow-definition-language-design.md) supplies SINGLE, comment, empty-input/result, immutable version and automatic-step rules. Current constitution/source decisions supersede older design sketches using ROWVERSION or versioned task types.

Included: start, complete, exact/bounded runtime reads, host assignment and start-link extension contracts, aggregate concurrency, idempotent replay, history and durable-event recorder contract. This selects exact APIs/normalization for this small slice; it does not freeze the future full runtime API.

Excluded: ALL/multiple tasks, cancellation, reassignment, variables, nonempty scalar inputs, structured results, guards/expressions, service tasks/gateways, scheduling, business decision engine, production APOLO adapters, REST/UI and automated tests. Existing CANCELLED/ALL storage values remain readable but F005 does not expose commands to create them. F006 remains independent; its separately specified host adapters/endpoints/pages are not implemented by this F005 task.

## Requirements

- **F005-R01 — Exact executable definition.** Start only an explicitly identified PUBLISHED definition version, pin its ID/hash and preserve its content. No latest-version lookup, implicit import/publication or fallback to another version. Runtime loading enforces the F004 structural/graph subset and stored canonical integrity without executing F004 publication validation or rewriting evidence. Catalog selectability changes must not prevent starting or completing an already published workflow. RETIRED blocks new starts but remains valid for existing instances and committed receipt replay.
- **F005-R02 — Atomic start.** In the host transaction, insert the instance, establish required host links before assignment, traverse START, resolve exactly one direct assignee, create one SINGLE activity/task and pause at the human node. Persist history, receipt and durable event handoff with the same commit. No partially started instance, orphan host link or successful receipt survives a failure.
- **F005-R03 — Fixed assignment.** Resolve the node's registered zero-input resolver exactly once on a successful new start; validate its whole result before retaining a roster. Exactly one valid task key/assignee is required. Missing/duplicate registration or zero/multiple/null assignments fail visibly. Store the assignment; do not recompute it on reads, completion or receipt replay.
- **F005-R04 — Exact task completion.** Require the target task to belong to the supplied instance and its active activity/current node, with OPEN/ACTIVE states and SINGLE roster count one. Require trusted USER actor equal to the stored assignee, the sole declared outcome and its comment rule. Complete task/activity and traverse the unconditional outcome transition to END atomically. Instance becomes COMPLETED with the declared result; no active activity/open task remains. No assignment override is implied by administrator authorization.
- **F005-R05 — Aggregate concurrency.** Every new mutation of an existing instance checks the expected numeric lock version, reserves the first history sequence through a managed instance update and flushes that version-checked write before child mutations or host effects. All subsequent changes share the transaction. Capture actual final managed lockVersion after final flush; never assume one increment, use child locks alone or rely on an unflushed FORCE_INCREMENT.
- **F005-R06 — Successful-command replay.** Globally unique command UUIDs identify START_WORKFLOW and COMPLETE_TASK. Resolve an authorized identical successful receipt before current lifecycle, selectability, assignment or stale-token checks. Return the original result without repeating any effect. Reuse with different semantic input/actor/operation conflicts. Rollbacks leave no successful receipt. Handle competing command IDs/instance versions without automatically retrying mutation logic.
- **F005-R07 — Trusted host transaction and identity.** Mutations require an existing host transaction (MANDATORY). The host authenticates/authorizes command and read access, including replay, supplies trusted context and exposes success only after commit. Core enforces assignment/lifecycle independently. Host links, workflow writes, history, receipt and event recording participate in the same effective transaction. No independent manager/connection, REQUIRES_NEW business effect or remote side effect is permitted.
- **F005-R08 — Immutable authoritative evidence.** Append deterministic ordered history with exact definition/task/activity/command references. Exactly one TASK_COMPLETED record is the authoritative accepted submission for a completed task; no completion evidence for OPEN tasks. Receipt result and history are bounded/versioned, immutable and retained; no runtime schema migration or extra result column/table is needed.
- **F005-R09 — Durable handoff.** Require a host WorkflowEventRecorder to persist the specified event batch transactionally. Absence, failure or malformed integration aborts commands. Logs, in-memory listeners and after-commit callbacks are not a substitute. Event delivery/retry remains host-owned and at-least-once; core does not send notifications or provide a dispatcher in this slice.
- **F005-R10 — Detached bounded reads.** Provide exact instance/task/activity views, bounded task/history/submission pages and actor-bound receipt replay lookup. Never expose entities, mutable provider data, unbounded histories or implicit latest activity/submission resolution. IDs alone grant no authorization; the trusted host gates each read.
- **F005-R11 — Fail closed with bounded work.** Reject unsupported execution contracts, bad inputs and inconsistent persisted graphs without partial effects. Preserve UTC precision, exact identifiers, comment text and token values. Apply the selected automatic-step limit of 50; this graph uses one step at start and one on completion. A failure rolls back the triggering command, not earlier committed work.
- **F005-R12 — Compatibility and evidence.** Preserve F001/F004 migrations, F002 authoring semantics, definition APIs and the two-module boundary. Record implementation and verification separately in implementation.md. No automated tests or production-readiness claim follows from these documents or a successful package.

## Supported Java API and value contracts

Add concrete `WorkflowExecutionService` and `WorkflowRuntimeQueryService` in `service.runtime`; immutable commands/context/results/views belong to `dto.runtime`. Runtime operations use documented services of other features, not host access to core entities. Extend the internal definition-loading boundary as described in the plan; do not treat the host's F004 validation fixture as executable support.

`WorkflowCommandContext(actorKind, actorRef, occurredAt, correlationId)` is constructed by the trusted host. actorKind is USER or SYSTEM for start; completion requires USER. actorRef is nonblank, untrimmed, valid Unicode, ≤200 code points and ≤400 UTF-16 bytes. occurredAt is an Instant exactly representable at seven fractional digits, stored as UTC; reject finer precision rather than silently rounding in core. Completion time must not precede instance start/activity entry/task creation. correlationId is nullable, otherwise nonblank and ≤100 UTF-16 code units. Correlation identifies a trace, not authorization or business membership.

Positive IDs and nonnegative lock/cursor values use long/Long; command IDs use non-null UUID. Technical keys match F004's ASCII technical-key grammar and 100-character maximum. Business correlation is either both null or `(businessType: technical key, businessId: bounded nonblank actor-sized reference)`; it is immutable, nonunique and not an association/authorization mechanism. No string trimming, case folding or Unicode normalization.

| Operation | Input → result |
| --- | --- |
| `start` | `StartWorkflow(commandId, definitionVersionId, businessType, businessId, hostStartIntent)`, trusted context, optional `StartLinkAction` → WorkflowCommandResult. |
| `completeTask` | `CompleteWorkflowTask(commandId, instanceId, taskId, expectedLockVersion, outcomeKey, comment)`, trusted context → WorkflowCommandResult. |
| `findReplay` (two overloads) | The original StartWorkflow or CompleteWorkflowTask and trusted context → Optional WorkflowCommandResult; actor/fingerprint checked, no mutation/host callback. Read-only REQUIRED; use a fresh transaction after a failed mutation. |

`comment` is nullable. If requiresComment=true, require non-null/nonblank; otherwise null, empty and whitespace are distinct accepted values. Preserve supplied text exactly. Maximum 2,000 code points and 4,000 raw UTF-16 bytes, valid Unicode. This Java slice has no start/task input map or structured-result field: those contracts are empty/FORBIDDEN. Future transport adapters must reject extra input/result fields, including explicit result:null, rather than discard them. The canonical accepted submission records `inputs:{}` and omits `result`.

`WorkflowCommandResult(replayed, execution)` wraps immutable `WorkflowExecutionResult(commandId, operation, instance, activity, task, firstHistorySequence, lastHistorySequence)`. Views contain the exact post-command snapshots below, including final managed instance token. Store only `execution` in the receipt; replay returns that same snapshot with replayed=true even if subsequent commands changed current state. New success returns replayed=false. All results are provisional until host commit. Do not overwrite a replay snapshot with fresh reads or append a new history/audit event for a replay.

### Host start links

`HostStartIntent(fingerprintVersion, fingerprintSha256)` is nullable. A non-null value requires a non-null `StartLinkAction`; a callback requires an intent. fingerprintVersion is a bounded technical identifier ≤40 characters and fingerprintSha256 is 64 lowercase hex characters. The host derives it from a versioned deterministic canonical representation of **all** authorized association inputs relevant to this start, including stable membership identities; it is not arbitrary client-supplied proof of access.

`StartLinkAction.link(AllocatedWorkflowInstance)` is a genuine per-invocation host callback. It receives only commandId, allocated instanceId, definitionVersionId, business correlation and trusted context; it may close over the authorized host input whose fingerprint is in the command. It runs once after instance insertion/ID allocation and before assignment. It writes required host links through the participating transaction, returns void and must not call back into workflow mutations, commit independently or perform remote effects. Failure aborts start. It never runs on replay. If no host links are required, both intent and callback are absent; no mandatory no-op adapter is needed. Core cannot verify that a host digest represents its business inputs; this is an explicit host integration obligation.

### Assignment and executable capabilities

Register `SingleTaskAssignmentResolver.identifier()` and `resolve(AssignmentContext)` implementations as named host extensions. Identifiers follow F004's nonblank resolver bounds (100 code points and 200 UTF-16 code units), are compared exactly and must be unique. AssignmentContext contains command/actor/time, allocated instance and exact definition version identity, human node key and optional business correlation; it exposes no EntityManager, writable variables or arbitrary Spring bean lookup. There are no input arguments in this subset.

Return `SingleAssignmentResult(tasks: List<ResolvedTask(taskKey, assignedUserRef)>, reviewRevisionRef)`. The list must contain exactly one non-null task; reject invalid cardinality before traversing or copying the roster. Validate taskKey and assignee bounds; optional reviewRevisionRef is a bounded nonblank actor-sized reference. No due-date or arbitrary metadata input is selected; due_at stays null. Frozen task count=1, policy=SINGLE, contribution_outcome_key=null. reviewRevisionRef is host evidence, not an authorization token or engine-owned membership list. The resolver is read-only with respect to workflow state and must not emit external side effects.

At start, require the named executable resolver and the deployed F004 task capability supporting the pinned node/outcome. At completion, require compatible task capability but do not call the resolver or require it to still be present merely to complete the stored assignment. Missing support fails as HOST_CONFIGURATION; catalog selectability is never checked for runtime eligibility. Real hosts must align publication descriptors with installed implementations and retain compatibility for published versions. F006's finite validation-only provider alone is insufficient to run F005. Core startup may still succeed without runtime adapters for management-only hosts; runtime calls must fail closed before any committed work.

## Definition eligibility and state transitions

The runtime loader verifies supported schema/canonicalization, canonical stored content/hash/indexed identity agreement, and the same minimal structure/topology as F004 without catalog-selectability or draft-validation writes. Reject unknown/unsupported semantics; do not rebuild canonical source from the typed graph. Start requires PUBLISHED; completion accepts the exact pinned PUBLISHED or RETIRED version. Missing/inconsistent stored state is an integration failure. A new engine cannot silently change the meaning of a pinned version.

For a new start, lock and refresh the definition-version row with a transaction-held lock that conflicts with retirement, then recheck PUBLISHED. Start and retirement must have a serial order: if retirement wins, the new start fails; if start wins, the instance pins that version and remains valid after retirement. The plan selects a pessimistic write lock for this narrow eligibility boundary; do not update definition metadata or increment its lockVersion merely to start. Receipt replay happens before this lock and remains valid after retirement.

Start inserts an ACTIVE instance initially at START with last_history_sequence=0 and null terminal fields. After the link callback, create the SINGLE activity and OPEN task, move current_node_key to the human key and finish at sequence 4. The activity's activation_sequence is the sequence of its ACTIVITY_ENTERED event (3 in this graph). Resolve the task catalog by stable code including nonselectable rows; retain its ID on the activity. No variable rows are created.

For completion, check instance existence/expected token, reserve next history sequence and flush the managed instance update before writing task/activity or invoking any host recorder. Re-read/refresh the task and activity after the claim to avoid stale persistence-context snapshots. Validate ownership, current position, roster, stored assignment, outcome/comment and pinned model. On success set task status=COMPLETED, outcome/closedAt/closedBy and closureReason=TASK_OUTCOME; activity status=COMPLETED with the same outcome/time/actor and closureReason=TASK_OUTCOME. Set instance current_node_key to END, status=COMPLETED, result_key to its result and endedAt/endedBy; termination_reason remains null. Final history sequence is 8 for this two-command graph. Flush all state and capture the resulting managed token before serializing the result.

No mutation is allowed on a completed instance except authorized replay of an already successful command. Do not turn a different completion command into a no-op success. Persisted CANCELLED or nonminimal runtime state is read-only for this feature; never coerce it into the selected flow.

## Idempotency, transaction ordering and errors

Fingerprint version `wf-runtime-request-v1`: SHA-256 over UTF-8 canonical JSON with lexicographically ordered property names, no whitespace, standard deterministic string escaping matching F004 canonicalization, explicit null for nullable fields and **decimal strings for every Long**. UUIDs are lowercase hyphenated strings. The root contains `version` (literal string `wf-runtime-request-v1`), `operation` (START_WORKFLOW or COMPLETE_TASK), `actorKind`, `actorRef`, `request`. START request fields are definitionVersionId, businessType, businessId and hostStartIntent (its two fields or null). COMPLETE request fields are instanceId, taskId, expectedLockVersion, outcomeKey and comment. Include the original expected token; it is not replaced during retry. Text/null distinctions are preserved. commandId is the receipt key; occurredAt and correlationId are attempt metadata and excluded. A retry with a later trusted time/correlation replays original timestamps/results, while any changed semantic field or actor conflicts. No arbitrary Java serialization or floating-point conversion.

Validate basic argument/context bounds before lookup, compute the semantic fingerprint, then look up the receipt. A recognized receipt must match actor, operation, fingerprint version/value and supported result schema. A mismatch raises COMMAND_ID_CONFLICT; unsupported stored algorithms/schema raise UNSUPPORTED_VERSION. Only after a miss perform state/expected-version/assignment checks and effects. Do not check new-attempt time against current lifecycle before resolving a receipt. Host reauthorization still applies on every attempt and before disclosing any stored result; core's trusted service boundary does not authenticate users.

Use SQL uniqueness plus the instance claim to protect races. A concurrent duplicate start may do transactional work before losing the receipt insert; the entire losing transaction, including links/events, must roll back. No external effects may have escaped. After CONCURRENT_COMMAND/STALE_VERSION, the host must finish rollback and may call findReplay with the original command in a **fresh** transaction; a matching committed receipt returns the original result, absent receipt leaves the conflict visible. No requery in the failed transaction, waiting loop or automatic second mutation. This specifies the recovery boundary of the older design's receipt-recheck sketch without creating core-owned independent transactions.

Public `WorkflowExecutionException` categories: INVALID_INPUT, NOT_FOUND, INVALID_STATE, NOT_ASSIGNED, STALE_VERSION, COMMAND_ID_CONFLICT, CONCURRENT_COMMAND, INVALID_ASSIGNMENT, UNSUPPORTED_VERSION, LIMIT_EXCEEDED and HOST_CONFIGURATION. Invalid runtime state/outcome/comment never succeeds; distinguish missing row from corrupt ownership/storage. Provider/recorder/link-callback failures retain internal causes and roll back, with sanitized stable messages to hosts. Null/unknown database constraint names are not an NPE or generic duplicate classification. Only the known receipt PK race maps to CONCURRENT_COMMAND; known optimistic failures map to STALE_VERSION; unrelated persistence failures map to HOST_CONFIGURATION. No HTTP mapping is selected by this core feature.

The host transaction encloses all mutations and durable handoff. Runtime command methods and recorder/link implementations must not reenter runtime mutations in the same call; fail explicitly if detected. A host must not perform additional workflow mutations after capturing a result and then present its token as current. Commit-time failures belong to the host boundary and yield no external success. Delivery occurs only after successful commit; no durable sink configured means commands are unavailable, not silently unaudited.

## History, receipts and event handoff

History `details_schema_version=1`; details are deterministic JSON objects. Long IDs/sequences/tokens in stored JSON use decimal strings, enum names are uppercase and times are UTC ISO-8601. Reject over-budget evidence rather than truncate it. Each complete details/result JSON must fit 128 KiB measured separately as UTF-16 bytes and UTF-8 bytes; this conservative F005 envelope is below the existing SQL DATALENGTH ceiling of 262144 bytes. This slice's comment limit keeps its ordinary records far below either ceiling.

| Command / sequence | Event | Details fields (besides the existing relational history envelope) |
| --- | --- | --- |
| Start / 1 | INSTANCE_STARTED | definitionVersionId, definitionKey, definitionVersion, definitionHash, businessType, businessId, hostStartIntent. |
| Start / 2 | TRANSITION_TAKEN | `{}`; source/target/transition keys identify START → human in the envelope. |
| Start / 3 | ACTIVITY_ENTERED | nodeKey, activationSequence, taskTypeId, taskTypeCode, completionPolicy, requiredTaskCount, reviewRevisionRef. |
| Start / 4 | TASK_CREATED | taskKey, assignedUserRef; activityId/taskId in the envelope. |
| Complete / 5 | TASK_COMPLETED | outcomeKey, comment, inputs `{}`; result omitted. This is the authoritative accepted submission. |
| Complete / 6 | ACTIVITY_COMPLETED | outcomeKey, closureReason `TASK_OUTCOME`. |
| Complete / 7 | TRANSITION_TAKEN | outcomeKey; envelope identifies human → END transition. |
| Complete / 8 | INSTANCE_COMPLETED | resultKey. |

All rows have command UUID, trusted initiating actor/time/correlation and owning instance. ACTIVITY_ENTERED/ACTIVITY_COMPLETED carry activityId; TASK_CREATED/TASK_COMPLETED carry both activityId and taskId; instance/transition records leave child IDs null. Source/target/transition fields are populated only for transitions. Use the initiating actor even for automatic movement caused by that command; do not invent a separate privileged actor. Sequences are consecutive committed per-instance order, not UUID/clock ordering. Rolled-back reservations leave no committed gaps.

Receipt result_schema_version=1 serializes the exact WorkflowExecutionResult; operation_type is START_WORKFLOW or COMPLETE_TASK; actor/fingerprint match the request and recorded_at is the command context time, not a measured commit timestamp. Serialize after final instance flush; later receipt/history flushes must not cause another unreflected instance mutation. Completion lookup verifies the unique TASK_COMPLETED evidence; a completed task missing that record is HOST_CONFIGURATION, not an empty submission. Never duplicate result payload in workflow_task or mutate earlier evidence.

`WorkflowEventRecorder.record(List<WorkflowEvent>)` is the required host durable-storage SPI. Emit exactly one event per history row, in sequence order, with event schema 1 and stable string eventId `instanceId:historySequence`. Envelope includes commandId, instanceId, definitionVersionId, event type, actor/time/correlation and applicable activity/task/transition identifiers. Payload contains only taskKey/assignee for TASK_CREATED, outcomeKey for TASK_COMPLETED/ACTIVITY_COMPLETED, resultKey for INSTANCE_COMPLETED, and an empty object for the other event types. No comment, host-start fingerprint, full definition or host business entity is delivered. Consumers use authorized reads for further information.

Record the batch once on a new command inside the host transaction, after final state flush and before returning. Duplicate delivery uses the same stable event IDs; receipt replay records nothing. Require immutable copies of lists/payloads. Recorder adapters own durable storage, retention and eventual dispatch; F005 defines and verifies the integration contract without adding a core outbox table. An adapter must not acknowledge before its transactional insert succeeds.

## Runtime reads

Views expose the corresponding F001 runtime columns with Java UTC Instants and enums, scalar owner IDs and defensive immutable collections; no entities. Instance view additionally identifies pinned definition key/version/hash. Task view includes owning instanceId/taskTypeId resolved through its activity, without adding physical columns. Activity view includes its stored fixed roster metadata. Views use current state; receipt results remain historical snapshots.

`WorkflowRuntimeQueryService` operations:

- `findInstance(id)`, `findActivity(id)`, `findTask(id)` → Optional detached view.
- Owner-requested monitoring extension in [F006 revision 4](../F006-test-host-definition-console/spec.md#revision-4--instance-monitoring-owner-request): `listInstances(WorkflowInstanceQuery(status, afterId, limit))` → immutable WorkflowInstancePage of WorkflowInstanceSummary, with nullable status meaning all states and no-argument query ACTIVE/0/50. Scalar summaries join immutable definition identity without loading pinned history/documents; exact findInstance retains pin verification. Existing page bounds/errors/host authorization apply. No execution, lifecycle, migration or receipt contract changes.
- `listTasks(instanceId, afterId, limit)` → all task states owned by that instance, ascending task ID; no task-result payloads.
- `listAssignedTasks(assignedUserRef, afterId, limit)` → stored OPEN assignments only, ascending task ID; host must authorize the requested assignee.
- `listHistory(instanceId, afterSequence, limit)` → envelope summaries in sequence order, no details payload; `findHistoryEvent(instanceId, sequence)` → exact envelope/details string.
- `findTaskSubmission(taskId)` → Optional immutable `TaskSubmission(taskId, activityId, instanceId, historySequence, commandId, actorKind, actorRef, occurredAt, outcomeKey, comment, inputs)`; inputs is the immutable empty map, no result field. OPEN/CANCELLED/absent task returns empty; a completed task with missing/inconsistent evidence fails explicitly.
- `listActivitySubmissions(activityId, afterTaskId, limit)` → the same typed submissions ordered by task ID, without requiring the host to parse arbitrary history. Missing activity yields an empty page.

IDs positive; cursors nonnegative; default page size 50, maximum 100; fetch limit+1 with nullable next cursor only when another matching item exists. Missing owners yield empty pages. Reads are REQUIRED/read-only and can observe same-transaction accepted submissions before host commit. Cap each page's deterministic DTO JSON representation at 1 MiB UTF-8 and UTF-16; if byte capacity ends a page, return a cursor after the last returned item when more exist, never silently drop rows. An individual item that cannot fit fails LIMIT_EXCEEDED. No stable snapshot across concurrent commits is promised. All reads/replay require host authorization; no public endpoint is added.

## Readiness and integration boundaries

No APOLO business policy is needed for this core slice. Concrete real resolvers, presentation capability declarations, host start-link canonicalization, authorization and durable recorder storage are host responsibilities. The specification fixes their call order and failure contracts; missing adapters must be explicit runtime configuration failures. Host-specific outbox schema/dispatcher and runtime HTTP/UI are separate deliverables, not placeholders hidden in core. New language forms and command kinds require their own specification and compatibility revision.
