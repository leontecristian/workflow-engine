# Specification — F023 Create next definition version

**Revision:** 3 — 2026-11-14. **Status:** IMPLEMENTED. **Owner:** project owner. **Constitution:** 6.6.1. Implementation explicitly authorized by the owner; verification outcomes and open gates are recorded in [implementation.md](implementation.md).

## Problem and analysis

The version editor supports draft replacement and immutable published/retired inspection, but offers no way to create a successor. F004 explicitly excluded allocation/clone convenience; F006 and F014 preserved that scope. Changing the version inside Save draft fails identity checks. Export/edit/import is possible but forces authors to manage numbering outside their workflow.

Evidence: `WorkflowDefinitionService.importDraft` creates or reuses an explicit identity, including identical published content; `replaceDraft` requires the same key/version. Shared `definition/version.ts` and `version.html` expose only save/check/publish/retire/export. At the original analysis baseline the repositories had no allocation coordination. The family has a numeric JPA lock version, and the database already enforces unique family/version identities.

**AGREED, owner 2026-11-14:** allocate the next version automatically, allow draft deletion and never reuse committed version numbers. This supersedes F004's no-allocation/no-deletion scope for these operations. Explicit import retains equivalent reuse only for versions that still exist. No constitutional principle changes.

A UI-only copy/import shortcut was considered and rejected for this selection: paginated client lists cannot safely allocate numbers, simultaneous authors can collide, and import may reuse immutable content. A dedicated server command creates a fresh draft and coordinates all version creation in the family. Revision 3 replaces the revision 2 ledger with a permanent highest-allocated counter on each family. The owner explicitly accepts rejection of new imports into unused lower gaps. Source edits require separate coordination from destination allocation.

Authority: [F004](../F004-definition-management-validation/spec.md), [F014](../F014-definition-catalog-administration/spec.md), [constitution](../../constitution.md) C03/C07/C09/C10, [constraints](../../constraints.md) CON-01/02/03/08/09/10/12, [assumptions](../../assumptions.md) ASM-01/02/03/05. [Design sources](../../design-sources.md) govern precedence. SQL Server locking remains a verification requirement, not a claim established by analysis.

## Scope and requirements

- **R01 — Source and user flow.** Add Create new draft to the shared version detail page for DRAFT, PUBLISHED and RETIRED sources. Copy the saved source, requiring local edits to be saved or explicitly discarded first. Disable while unloaded, dirty or busy. A native Material dialog identifies source key/version and explains automatic numbering; confirmation creates, Cancel/Escape/backdrop does nothing. No implicit save, validation or publication. Open the resulting draft through host navigation and display its allocated number. This saved-source choice is the scoped authoring default; it avoids silently discarding editor content.
- **R02 — Allocation.** Under the family write lock, automatic creation uses `highestAllocatedVersion + 1`. Explicit import first checks for a retained version: equivalent content returns unchanged and different content conflicts, regardless of the counter. If the requested version does not exist, require its number to be strictly greater than the counter; otherwise return conflict, even if that lower number was never used. Successful new import advances the counter to the requested number. Importing 10 after 1 therefore makes the next automatic version 11 and forbids new imports 2–10. Update the counter and insert the version in the same host transaction. Concurrent successful creations get distinct numbers; deletion never decreases the counter. At 2147483647 automatic creation fails with bounded conflict; never wrap, fill gaps or reset. Failures, including audit failure, roll back both creation and counter advancement. This field is per-family transactional state, not a database SEQUENCE, IDENTITY generator or global counter.
- **R03 — Snapshot.** Require the loaded source technical lock token. Check and hold the source stable through copying; stale source fails with conflict and requires explicit refresh. Copy its complete document, changing only root version semantically; preserve exact numeric values, unknown/designer fields and schemaVersion using existing core ingestion/canonicalization. Preserve source identity/content/state and descriptive family metadata. Allocation changes the counter and advances the family JPA lock token; stale family-metadata editors must explicitly refresh. Equivalent imports and deletion do not advance the counter. New draft has normal creation actor/time, content revision 1, recomputed canonical hash and empty validation/publication/retirement evidence. No runtime data, task results or lineage table is copied.
- **R04 — Authoring rules.** Apply existing ingestion bounds and current task-type authoring selectability. A formerly valid published source may fail new authoring if its referenced task type is disabled; retain the source and report the existing bounded error. Do not automatically validate capabilities or upgrade old document semantics; normal draft validation remains explicit. Incomplete but ingestion-valid drafts remain copyable.
- **R05 — Command boundary.** Add core `CreateWorkflowDraftFromVersion(sourceVersionId, expectedLockVersion)` in `dto.definition`, invoked through `WorkflowDefinitionService.createDraftFromVersion` in `service.definition`. Return existing DefinitionChange with empty before, new after, changed=true and operation CREATE_DRAFT_FROM_VERSION. Add POST `/versions/{id}/drafts` in the existing administration group, empty JSON object body and `X-Expected-Lock-Version` for the source. Reject unknown/body identity/version fields. Return existing DefinitionChange wire shape and HTTP 200. Host adapter supplies trusted context, transaction and audit. Existing access/CSRF checks apply. Invalid inputs 400, unauthenticated 401, denied 403, missing source 404, stale/exhausted/allocation conflict 409; bounded ingestion errors retain existing categories. No automatic retry on lock failure.
- **R06 — Failure and lifecycle.** A confirmed create occurs once per explicit submission; disable repeat clicks while pending. This management command has no runtime command receipt or replay guarantee. On uncertain transport outcome report that creation may have succeeded and direct the author to refresh the family version list before another attempt; never automatically resend or report rollback. Preserve local source text on ordinary errors; existing access-loss privacy clearing still applies. Session/source changes or destruction close the dialog and suppress late feedback/navigation. A successful create followed by navigation failure remains a successful create with its new identity visible.

Excluded: copying to another family, editing published versions, auto-publish, active-instance migration, general designer, draft merging, lineage browsing, automatic schema upgrades and a new receipt framework. Existing imports continue explicit numbering and identical-content reuse for retained rows, subject to permanent reservations. No undo/restore, family deletion or allocation-reset operation is included.

## Acceptance scenarios

- **AC01 (R01–03):** From each lifecycle create a draft, open it, edit/save/validate through existing controls; original is unchanged. An older source with later retained versions allocates above the allocation maximum, including gaps and retired versions.
- **AC02 (R02):** Two concurrent creates serialize to distinct next numbers. Explicit import racing creation respects the same lock/uniqueness boundary and its existing conflict/reuse rules. Exhaustion fails without writes.
- **AC03 (R03–04):** Preserve large integers, decimal values, nested version fields and designer/unknown fields; reset lifecycle evidence and recalculate hash. Stale source, disabled task type and oversized rewritten document fail without a new row. Ingestion-valid incomplete draft copies without implicit validation.
- **AC04 (R05):** Endpoint checks access, CSRF, empty-body contract and source token. Audit failure rolls back the new version; no source/family metadata changes persist.
- **AC05 (R01/R06):** Dirty blocking, confirmation/cancel/focus, busy double-click suppression, uncertain outcome, session invalidation and navigation failure behave as specified. Browser rendering remains usable at desktop and narrow widths.

## Revision 3 analysis and additional requirements

**Owner decision — 2026-11-14:** use the simpler family counter and reject new imports at or below it. The counter need not distinguish deleted identities from unused lower gaps because both are now rejected. This intentionally tightens the prior import contract, while retaining equivalent reuse of existing versions. The revision 2 allocation table, entity, composite ID and repository are superseded.

The counter records the highest successfully committed version number. It starts at zero for a family without versions and advances to the first imported number. An empty family left by draft deletion retains its nonzero counter. Rollbacks do not consume numbers; permanent non-reuse covers committed versions. The family is retained even when all drafts are deleted.

Evidence: the initial schema already enforces unique family/version numbers and a NO ACTION instance-to-version foreign key. `DefinitionChange.after` and `ConsoleManagement.audit(DefinitionChange)` assume a surviving version, requiring a separate deletion result. `ConsoleManagement` owns the actual transaction/audit boundary behind `ConsoleAdministrationHost`. The original baseline lacked allocation/deletion coordination; in-progress revision 2 code does not override revision 3. Existing lifecycle and runtime readers access version and family rows, so lock ordering must be checked across these paths.

- **R07 — Delete draft.** Offer Delete draft only on a loaded DRAFT, disabled while busy. A Material confirmation identifies key/version, states permanent content deletion and permanent number reservation, and explicitly warns that unsaved edits will be discarded. Dirty drafts may be deleted after this confirmation; Cancel/Escape/backdrop preserves text. Require the loaded lock token, hold the version stable and recheck DRAFT before deleting. Retain family, counter and host audit; never cascade runtime data. Published/retired or stale versions fail with conflict; missing/already-deleted versions return 404. Unexpected references fail safely with conflict. After success clear the obsolete editor and navigate to the family, including an empty family. If navigation fails, retain success feedback and a family link. No undo or mandatory reason is added.
- **R08 — Deletion command and audit.** Add `DeleteWorkflowDraft(versionId, expectedLockVersion)` and `DefinitionDeletion(before, operation, context)` in `dto.definition`; before is the removed DefinitionVersionSummary and operation is DELETE_DRAFT. `WorkflowDefinitionService.deleteDraft` flushes removal within the mandatory host transaction. DELETE `/versions/{id}` requires `X-Expected-Lock-Version`, accepts no request body (nonempty body is 400), and returns HTTP 200 with the deletion result using existing summary/context wire encodings. Existing access/CSRF and 400/401/403/404/409 categories apply. Host audit records the removed ID, before summary and after=null with trusted actor/time/correlation. Audit failure rolls back deletion. Do not preserve raw draft JSON in new audit fields. R06 duplicate-submission, session invalidation and no-retry rules also apply. An uncertain delete outcome preserves text until explicit refresh and reports uncertainty; 404 establishes absence, not which request deleted it. Do not fabricate a post-delete token or receipt replay.
- **R09 — Counter storage and rollout.** Add `highest_allocated_version INT NOT NULL` to core-owned `wf.workflow_definition`, default 0, with a nonnegative check. Map `highestAllocatedVersion` on WorkflowDefinitionEntity. Backfill each family from the maximum existing version across all statuses, or zero for an empty family. Migration preserves existing version IDs/documents/lifecycle and family lock tokens. Runtime allocation updates the managed family under the write lock, using normal numeric JPA versioning; no public counter reset/edit operation. Keep the existing version uniqueness constraint. No allocation table or database sequence is introduced. The owner confirms no F023 migration has been applied: replace the uncommitted ledger migration during implementation, rather than shipping both designs. Hosts quiesce old definition writers and deploy the additive migration before compatible writers; mixed versions and downgrade to counter-unaware writers are unsupported. Historical manual deletions outside supported engine operations cannot be reconstructed. The adoption baseline is the current maximum; subsequent committed numbers remain unavailable after deletion. Deleting INT_MAX or all drafts does not restore lower-number capacity.

### Additional acceptance scenarios

- **AC06 (R07–08):** Delete clean/dirty drafts only after confirmation; cancel retains text. Lookup/export then return 404 and lists omit the deleted version. Preserve the empty family and audit summary. Published/retired, stale and unexpectedly referenced versions reject deletion. Repeated deletion returns 404; audit failure restores the row.
- **AC07 (R02/R09):** After deleting the highest draft, automatic creation increases past it. Explicit import of its number conflicts, and a genuinely unused lower gap also conflicts. Equivalent import of a retained version is unchanged. Failed creation restores the previous counter; deleting INT_MAX does not restore automatic allocation capacity.
- **AC08 (R02–03/R07):** Overlap delete with save, validate/publish and copy: no lost update, deletion of immutable content or partial copy. Deletion winning makes source operations fail missing; publication winning makes deletion fail stale/state. A copy completed before deletion remains valid afterward. Two deletes yield one success and a missing/conflict loser. Import/create/delete preserve counter monotonicity and version uniqueness under concurrency.
- **AC09 (R09):** Upgrade populated fixtures with multiple families, gaps and statuses; backfill each family maximum (or zero for empty families) without altering content/IDs. Fresh creation reaches the same schema; repeated master execution is stable. Verify counters survive deletion and restart, higher imports advance the counter, and equivalent imports leave it unchanged. Verify stale family-metadata tokens conflict after allocation.
