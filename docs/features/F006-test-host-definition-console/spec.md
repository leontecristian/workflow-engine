# F006 — Test-host workflow console

**Status:** READY for implementation after the required F005 APIs are available. **Revision:** 3 — 2026-10-31. **Owner:** Workflow project owner. **Constitution:** [v3.0.0](../../constitution.md).

## Outcome and scope

Provide a small Angular application in `workflow-test-host` and host-owned HTTP endpoints for manually exercising F002 catalog administration, F004 definition management and F005 minimal SINGLE execution. Users can publish a definition, start a sandbox request, complete its assigned task and inspect persisted instance state, submissions, history, command results and durable events. This revision supersedes revision 1's management-only scope and validation-only capability fixture. The folder path is retained to preserve links. These documents specify work; actual implementation/verification belongs in [implementation.md](implementation.md).

[F005](../F005-minimal-single-workflow-execution/spec.md) owns execution semantics and is a dependency of the execution portion of F006. F006 supplies real development-host adapters, HTTP transaction boundaries and pages; it must not duplicate the engine. Management/UI infrastructure can progress independently, but the feature is not complete without the execution slice. Excluded: visual designer, ALL, cancellation/reassignment, variables/results/expressions/service tasks, production APOLO adapters, external messaging integrations and background dispatch schedules. Revision 3 retains revision 2's functional scope and adopts the owner's clarified policy: isolated unit tests are allowed; creating/running database integration tests requires explicit authorization.

Authority: [F002](../F002-task-type-catalog/spec.md), [F004](../F004-definition-management-validation/spec.md), [F005](../F005-minimal-single-workflow-execution/spec.md), [package structure](../../package-structure.md), [source precedence](../../design-sources.md). Apply CON-01–12 and ASM-01–05/08. Existing lifecycle, canonicalization, execution, error and transaction contracts remain authoritative. The bounded family read below is the sole additional core API owned by F006; runtime reads/commands use F005.

## Requirements

Older F005 references to F006's validation-only fixture or a future runtime-host extension describe F006 revision 1. This owner-requested revision supersedes those integration-scope references without changing F005's core execution contract or requiring its implementing agent to build the console.

- **F006-R01 — Development boundary.** Keep exactly two Maven modules. Angular and transport/security/audit/sandbox adapters belong to the test host. Console routes, API and sandbox capabilities require explicit `workflow.console.enabled=true`; they are unavailable by default. Bind the enabled console to loopback and reject incompatible bind configuration. The page identifies itself as a development console whose writes persist in the configured development database.
- **F006-R02 — Trusted host context.** Authenticate operations with separate configured administrator/reviewer accounts and the authorization rules below. Use server sessions and CSRF; do not accept actor/time/roles from request JSON. Construct F004/F005 context from the principal and server UTC clock, truncated to 100-nanosecond precision; runtime actorKind is USER. Missing credentials must not enable anonymous access. No credentials are committed or stored by Angular.
- **F006-R03 — Browse actual state.** Provide bounded persisted family, family-version and task-catalog lists, exact version details and exact key/version lookup. Include retired versions and nonselectable catalog entries. Display IDs, lifecycle, lock/content revisions, hashes, audit metadata and stored validation evidence. No unbounded entity dump or browser-only substitute for the database list.
- **F006-R04 — Author without losing data.** Import/paste/upload JSON, replace only DRAFT content with the loaded lock token, and edit family metadata separately. Use a plain text editor; the browser must not parse/stringify the workflow document on save/export, because duplicate properties and exact numeric spellings must reach core intact. No automatic version allocation, save-before-publish, automatic retry, default insertion or silent overwrite. Preserve unsaved editor contents on errors/conflicts; explicit reload may discard them after confirmation.
- **F006-R05 — Inspect validation and lifecycle.** Validate, publish and retire explicitly. Show ordinary failed validation as a completed check with its diagnostics and persisted DRAFT state, not a transport failure. Publication always calls core's fresh validation. Display diagnostics by severity/code/stage/pointer, `detailsOmitted`, and the returned `published` flag. Refresh state/tokens after successful mutations; show published/retired JSON read-only. Export returns the exact stored canonical document in every lifecycle.
- **F006-R06 — Catalog and executable sandbox support.** Supply catalog administration through F002 and real sandbox resolver/task presentation support for the F004 example. Capability descriptors must match these implementations; remove the revision 1 validation-only exception. No catalog/request/workflow seeds on startup. Users create SANDBOX_REVIEW explicitly before importing the example; catalog presence alone grants no capability support.
- **F006-R07 — Transactions and evidence.** Management mutations call core and persist management audit in the same host transaction, once per changed=true result; no-op produces no audit row. Runtime mutations atomically include host request links, F005 state/history/receipts and the real host event recorder. Return success only after commit. F005 owns runtime history/receipts; do not fabricate replacements or duplicate every runtime command into management audit.
- **F006-R08 — Exact, bounded HTTP contract.** Use the routes, encodings and errors below. Keep long IDs/tokens exact across JavaScript, bound requests before materialization, and return sanitized errors. Authentication and exception handling must cover commit-time failures as well as service calls. No automatic write retry or recovery query inside a failed transaction.
- **F006-R09 — Reproducible delivery.** Keep a separate locked Angular/npm build beneath the host and an opt-in packaged-console build. Ordinary Maven packaging must retain the existing tests-skipped workflow without requiring Node. The README must give exact toolchain, credentials configuration, build/start and manual-use instructions. Generated assets/caches/logs remain ignored.
- **F006-R10 — Unit and manual evidence.** Add and run focused isolated unit tests for meaningful behavior that can be verified without a database or running host. Execute the manual acceptance walkthrough against explicitly identified development data within its authorized scope. Record unit-test, build and manual results separately. Database integration tests, including embedded databases/Testcontainers/database-backed context tests, require explicit authorization to create/run; manual acceptance does not authorize an automatic database scenario harness. Unit-test/build success cannot establish real transaction/locking/durability acceptance.
- **F006-R11 — Start and host links.** Create an explicit persisted sandbox request and start an exact published version through F005, using the specified host-start fingerprint and callback. The callback attaches the allocated instance before assignment. A request can link to one instance; replay never creates a second link/instance. This is a sandbox policy, not a generic workflow/business constraint.
- **F006-R12 — Human completion.** A real resolver assigns the single task to the configured reviewer. The reviewer sees stored assignments, selects the pinned outcome and supplies a comment when required. Complete through F005 with the loaded instance token; administrator privilege never bypasses assignment. Show final END result and immutable accepted submission.
- **F006-R13 — Explicit command replay.** Generate a UUID for each intentional new runtime command, retain its exact payload/original token, and provide explicit retry/result-recovery controls. Retry uses the same ID/input and freshly authenticated identity. A lost response is an unknown outcome, not permission to generate a new command. Recover race results with findReplay in a fresh transaction after rollback; never automatically rerun a mutation.
- **F006-R14 — Durable local delivery.** Implement the F005 recorder as transactional database outbox inserts and an explicit administrator-operated dispatcher to a durable local inbox. Inspect pending/delivered events and demonstrate restart retention and duplicate suppression. No email/broker integration or scheduler; local atomic delivery is not evidence of production distributed delivery.
- **F006-R15 — Runtime inspection.** Provide persisted sandbox-request listing, exact instance lookup, task inbox/detail, history and typed submissions, original command-result display and outbox/inbox views. Separate current state from replay snapshots and management audit from execution history. Honor ownership/role restrictions, bounded pages and exact-string numeric tokens throughout.

## Host API contract

Base path: `/console/api`. Management routes below require the administrator; `/session` is available to either authenticated role. Runtime permissions are specified separately. Collection defaults: `afterId=0`, `limit=50`; limits 1–100, ascending ID, exclusive cursor, nullable `nextAfterId` only when more matching rows exist. History uses afterSequence/nextAfterSequence; activity submissions use afterTaskId/nextAfterTaskId. No total-count promise or snapshot consistency across concurrent changes.

All Java long/Long values, including IDs, lock/content/request versions, history sequences and cursors, are decimal **strings** on the wire; validate Long bounds and keep strings in Angular. UUIDs are lowercase hyphenated strings; F005 event IDs retain their instanceId:sequence string. Definition version/schemaVersion and page limits are JSON integers. Dates are UTC ISO-8601; optional values are null. Host DTO shapes follow F002/F004/F005 records with these conversions, Optional absence becomes null, and document/evidence JSON remains strings. No global mapper change or entity serialization.

For existing core-object mutations, require `X-Expected-Lock-Version` as a nonnegative decimal Long; malformed/missing returns 400. Family, definition-version and runtime instance tokens are distinct. Task completion uses the **instance** token, not a task token. Sandbox start instead carries expectedRequestVersion in its body; creates/imports/dispatch have no expected-token header. Reject duplicate/unknown envelope fields, including client actor/time/roles/hostStartIntent; path/header identity cannot be overridden in the body. Reject all runtime inputs/result fields, including result:null, because F005 forbids them.

Successful JSON operations return 200, including creates, no-ops and ordinary negative validation/publication reports. This console does not use 422 for a valid check request whose document fails validation. Export is 200 with `application/json` and attachment disposition. Unknown API paths return an API 404, never the Angular page.

The API error envelope is `{code, message, diagnostics, correlationId}`. `diagnostics` is an empty array unless core supplies bounded document diagnostics; do not duplicate raw request text. Use 400 for invalid arguments/document ingestion, 401 for unauthenticated API calls, 403 for denied role/CSRF, 404 for exact missing resources, 409 for CONFLICT/INVALID_STATE/DUPLICATE_CODE/STALE_VERSION, 413 for transport size limits, and 415 for unsupported media types. HOST_CONFIGURATION, UNSUPPORTED_CANONICALIZATION, STORAGE_FAILURE and unclassified transaction/commit failures return sanitized 500 with a server-generated correlation ID; preserve internal causes in host diagnostics. Do not turn every integrity exception into 409 or expose SQL, credentials or stack traces.

Runtime adds 403 NOT_ASSIGNED, 409 COMMAND_ID_CONFLICT/CONCURRENT_COMMAND/SANDBOX_REQUEST_CONFLICT and 500 INVALID_ASSIGNMENT/UNSUPPORTED_VERSION/HOST_CONFIGURATION (deployment/persisted-state failures). LIMIT_EXCEEDED from evidence/work limits is 422; 413 remains transport size. The trace correlation ID is server-generated for each attempt and distinct from the client's command UUID. Unauthorized reviewer resource reads return 404 without revealing owner/details; known-role action denial remains 403. A successful replay returns 200 with replayed=true and the original execution snapshot.

Raw document bodies have a 4 MiB byte ceiling, including chunked requests, and strict UTF-8 decoding; no controller/ObjectMapper parse/reserialize before core ingestion. Other command JSON bodies are capped at 16 KiB. Core's canonical/document/diagnostic limits still apply independently. Reject compressed request bodies for this console rather than expanding an unbounded compressed payload. Authentication/CSRF failure must occur before invoking a mutation.

### Bounded core read addition

Add `WorkflowDefinitionService.listDefinitions(DefinitionQuery(afterId, limit))` returning immutable `DefinitionPage(items: List<DefinitionView>, nextAfterId: Long?)`. Validate nonnegative cursor/1–100 limit using F004 INVALID_INPUT semantics. Query ascending family ID, strict `id > afterId`, fetch limit+1, and return no definition-version payloads. Empty database returns an empty page. Reads follow core's existing read-only REQUIRED boundary; the host authorizes access. No filter, full-text search, latest-version inference or new table/index is required. Host code must not bypass core by importing its repositories/entities.

## Development authentication, executable sandbox and audit

Require two distinct configured accounts, CONSOLE_ADMIN and CONSOLE_REVIEWER, with external username/password settings and no default password. Usernames are stable actor references satisfying F005 bounds; changing the reviewer does not reassign stored tasks. Missing/ambiguous credentials fail enabled startup. Admin owns catalog/definitions/starts/audit/event delivery; reviewer owns its assigned work and related instance reads. Standard session/form login/logout and CSRF apply; API unauthenticated responses are JSON 401. Use separate browser profiles/private windows to exercise roles, not a client actor-switch field. No wildcard CORS or remote deployment. Development roles are not APOLO policy.

With console enabled, `workflow.console.capabilities=sample` (default) registers a real `sandbox.singleReviewer` resolver and task presentation/completion support for SANDBOX_REVIEW/COMPLETE, empty inputs and forbidden results, including optional/required comments. The resolver verifies the allocated instance is already linked to its sandbox request in the same transaction, then returns exactly one task with taskKey=REVIEW and assignedUserRef equal to the configured reviewer, reviewRevisionRef=null. It performs no external effects. The Angular task page and F005 completion adapter implement the advertised task support. `none` removes both descriptors and resolver for missing-support checks; unknown modes fail startup. Snapshots are immutable until restart. Register one provider, not overlapping synthetic and real providers; no allow-all registration or catalog seeds. This is real but deliberately simple sandbox behavior, not APOLO business assignment logic.

Add a host-owned `wf_test.management_audit` table through the test-host changelog after the core include. Store generated BIGINT ID, trusted actor/time, operation, entity kind/ID, and versioned JSON evidence containing the full returned before/after summaries (catalog snapshots for F002), changed validation outcome/context and the operation correlation ID. Omit full workflow documents and credentials. Retain records, expose bounded authenticated reads, and provide no delete/reset API. F001/F004 changesets and the core master are unchanged.

Persist audit with the same datasource/transaction manager as core. An insert/serialization/size failure aborts the entire host transaction; application logs and in-memory lists cannot substitute. An optional startup-only `workflow.console.fail-audit=true` setting, default false and allowed only with the enabled loopback console, deliberately fails after a changed core result but before audit persistence for manual rollback observation. Display the active failure mode prominently. No request-controlled fault switch or generic SQL/exception endpoint is permitted.

### Sandbox request and start identity

Persist host-owned `wf_test.sandbox_request` rows with immutable name/creator/time, nullable workflow instance link and numeric request lockVersion. Creation is an admin action; name uses F004's name bounds. No edits/deletes/reset, business approval rules or core FK are introduced. List requests to discover their instances; do not add a generic core listInstances API solely for this page.

Start maps requestId to businessType=`SANDBOX_REQUEST`, businessId=its decimal ID. Derive HostStartIntent version `wf-test-start-v1` and SHA-256 of canonical UTF-8 JSON `{"expectedRequestVersion":"<decimal>","requestId":"<decimal>"}`, with literal sorted field names/no whitespace; no callback identity supplied by clients. Both fields are canonical nonnegative/positive decimal Long strings. Authorize the request but do not reject its now-linked state before receipt lookup. The StartLinkAction atomically sets instance_id and advances request lockVersion only where id matches, instance_id IS NULL and lock_version equals expectedRequestVersion. A zero-row update is a sandbox conflict and rolls back the whole start. The resolver observes that new link before assignment. Concurrent distinct starts for one request cannot both commit; identical replay keeps the original link/token/result. No host row is prelocked before F005's definition eligibility lock; use the callback's conditional update for consistent lock ordering.

Wrap core calls in a transactional host service invoked by a **nontransactional** HTTP coordinator. If CONCURRENT_COMMAND, STALE_VERSION or the specifically identified SANDBOX_REQUEST_CONFLICT escapes and the transaction has fully rolled back, perform at most one read-only findReplay in a separate REQUIRED transaction using original input/actor. This includes duplicate starts that lose the link update before receipt insertion. Return replay only when found; a miss retains the original conflict and a mismatched receipt returns COMMAND_ID_CONFLICT. Never retry mutation automatically or recover inside a failed transaction. Replay endpoints reauthorize and never execute callbacks. Only the known wrapped host link-conflict marker maps to the sandbox 409; other callback failures remain 500.

### Durable outbox and local inbox

The host WorkflowEventRecorder writes every F005 event to `wf_test.workflow_event_outbox` on the same datasource/effective transaction as core. Store the immutable complete event, stable event ID and sequence/command/instance references, with PENDING delivery state. Receipt replay emits no new events. No management-audit substitute or post-commit in-memory enqueue is permitted.

The explicit dispatcher uses a **new host request transaction after workflow commit**. It reads a bounded pending batch in insertion order, writes each event once to `wf_test.workflow_event_inbox` under unique eventId, then marks the outbox row delivered in the same transaction. Serialize competing delivery/redelivery through an outbox row lock, compare payload identity on duplicates and reject mismatches; identical redelivery returns duplicate=true with no second inbox effect. Retain both records. Restart preserves pending/delivered rows. Local inbox persistence is the visible sink; no broker, email, business mutation or automatic scheduler is involved. This proves durable local handoff/recovery/idempotency only, not distributed exactly-once delivery.

Startup-only `workflow.console.fail-start-link`, `workflow.console.fail-event-recording` and `workflow.console.fail-runtime-after-result` default false. Respectively throw after the link update, after outbox batch insertion, or after core returns a new result but before facade commit. All are gated to the enabled loopback console, displayed to the administrator, and never request-controlled. They establish rollback observations; a replay does not invoke link/recorder or trigger the after-result failure for a new command. Do not add generic exception/SQL injection endpoints.

## Pages and interaction

- **Definitions:** persisted family page and Next control, family details/metadata editor, version page/status filter, exact key/version lookup, and Import action.
- **Version:** identity/status/revisions, JSON text editor or read-only document, explicit Save/Validate/Publish/Retire/Export actions, structured latest/stored validation diagnostics and a collapsible sanitized HTTP response. New responses must not leave an old PASSED label attached to edited content. Unsaved text requires an explicit save before validation/publication; the UI never silently saves it.
- **Catalog:** bounded list, explicit create and metadata/selectability edit with current tokens. Explain that capabilities and selectability are separate prerequisites; provide a prefilled, unsaved SANDBOX_REVIEW form for convenience.
- **Audit:** bounded summaries with expandable exact evidence, useful for observing persistence and rollback. Show no-op responses without suggesting an audit row was inserted.
- **Sandbox requests / Start:** create a named request, select an exact PUBLISHED version, show the request token and explicitly start. Display committed linked instance and command result. Disabled catalog selectability must not remove already published versions from runtime selection. Retired versions cannot be selected for a new start.
- **Instance:** exact current state, pinned version, result/token, task/activity links, ordered history and accepted submissions. Show the final END result after completion and distinguish it from an original replay snapshot. Reload from the server; no fake browser progression.
- **My tasks / Task:** the authenticated reviewer's actual OPEN inbox, task/instance details, pinned COMPLETE label/comment requirement, explicit Complete action and current instance token. Closed tasks remain inspectable through instance/history links. No candidate claiming or administrator assignment override.
- **Command results:** keep each attempted command UUID, exact request and original token in the current page session; show new/replayed/unknown outcome distinctly. Explicit Retry reuses them unchanged; Find result uses replay-only endpoints. A deliberate new action uses a new UUID. Provide copy/download of the command envelope for recovery after a full reload, without saving credentials; submission comments are never put in URL query strings. Do not replace an original token during retry or retain one actor's command buffer after logout/account change.
- **Events:** admin outbox/inbox pages with sequence, event ID, status and exact payload; explicit Dispatch pending and Redeliver actions expose outcomes without suggesting workflow execution ran again.

Show loading/empty/error states, disable duplicate submission while a request is in flight, and retain error/conflict details. Use accessible labels and keyboard-operable controls. No component library or graphical workflow editor is required. Any sample JSON inserted into the editor is unsaved and derived from F004's normative example; users choose explicit key/version. Angular displays imported text as text, never executable HTML.
