## Module allocation and dependency review

Follow the specification's module responsibilities and the existing [package structure](../../package-structure.md). Keep the three Maven modules and separate Angular library. No new module, dependency reversal or production dependency on test-host is proposed.

- Keep domain operations and persistence in `workflow-core` through its existing public services and DTOs. The administration extraction requires no core dependency on web or host adapters.
- Put HTTP mapping in `workflow-web` controllers and generic mutation/audit coordination in `io.github.leontecristian.workflow.web.service.administration`. Shared code uses the existing host transaction manager; it installs no competing transaction infrastructure or global configuration.
- Declare `WorkflowAdministrationIdentity`, `WorkflowAdministrationAuthorization` and `WorkflowAdministrationAuditRecorder` in `io.github.leontecristian.workflow.web.integration.administration`, with R01 methods, and the single `WorkflowAdministrationAudit` record in `io.github.leontecristian.workflow.web.dto.administration`. These types must not expose host entities, security objects or persistence internals. Require each interface independently even if one host class implements all three. Inject the host-provided `java.time.Clock` separately; do not create a library fallback Clock. Use the specification's selected audit fields and existing summary DTO payloads without additional enums or snapshot wrappers.
- Keep sandbox identity, permission policy and audit storage integration in `io.github.leontecristian.workflow.testhost.service.administration`, with explicit wiring in `io.github.leontecristian.workflow.testhost.configuration.console`. Remove generic command forwarding under the recorded authorization. APOLO will provide equivalent host integrations; changing APOLO sources is outside this repository's slice.
- Keep host business orchestration and independently activated runtime groups outside F029. `workflow-ui` and host frontends continue to consume the existing HTTP contract; no frontend changes are proposed.

Three separate interfaces, a host Clock, the simple audit record and `@Transactional` with REQUIRED propagation are selected design decisions. Implementation authorization received on 2026-11-16. Review the resulting dependency path as host → web → core, with optional host → core calls. Host callbacks implement library-owned interfaces and do not create reverse module dependencies.

## Host configuration and commit ownership

Document and verify that hosts enable annotation-driven transaction interception using their existing Spring/Boot configuration and provide the applicable PlatformTransactionManager. Core mutation and audit persistence must use the same transaction/resources; multiple-manager hosts must configure unambiguous manager selection. Do not install a transaction manager or `@EnableTransactionManagement` from shared web. Retain host defaults for isolation/timeout and avoid automatic retries or REQUIRES_NEW.

Require the manager dependency in explicit administration configuration for missing-bean activation failure. Its presence does not prove effective interception or override annotation manager selection. Verify interception through focused host integration tests; do not add a proxy-inspection framework or automatic configuration repair.

Register the concrete service as a managed bean and inject its proxy into controllers. The normal HTTP route has no enclosing transaction, so the service proxy commits before returning. Direct callers within an outer host transaction join it: the outer caller owns final commit/rollback, and service return is not proof of commitment. An audit failure must mark the joined transaction rollback-only. Document this distinction for host integrations and ensure HTTP success is not reported before the owning transaction completes.
