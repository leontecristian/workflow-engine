# F017 — Task claiming and release

**Status:** READY, revision 3 — 2026-11-09. **Owner:** Workflow project owner. **Constitution:** 6.2.0. Authorization covers specification and planning. O01–O06 are closed; implementation requires a subsequent request.

## Purpose and authority

An eligible member can reserve a shared task while working on it, then complete it or return it to the eligible group/role. A planner can require reservation for an individual human stage. The original assignment remains available after release.

Authority is constitution C02/C03/C05/C06/C07/C09, CON-03–08/10/12 and ASM-02–06. Follow [design precedence](../../design-sources.md) and the [development workflow](../../specification-driven-development.md). [F016 revision 2](../F016-shared-group-role-task-assignment/spec.md) remains the implemented baseline for assignment, membership and access. F017 changes its direct-completion rule only as specified here.

## Agreed decisions

- D01. Claim policy belongs to each HUMAN_TASK node in the immutable workflow definition. OPTIONAL is the default; REQUIRED requires individual ownership before completion. A shared task obtains ownership through a claim; direct USER assignment establishes it at creation. O01 specifies the JSON representation.
- D02. An eligible member may complete an unclaimed OPTIONAL shared task directly. Once claimed, only its claimant may complete it. REQUIRED shared tasks must be claimed first. Completion always also requires current eligibility and host business authorization.
- D03. The planner's policy is pinned with the workflow version. Omitted policy in existing definitions means OPTIONAL. Publishing a different policy affects new instances using that version; existing instances retain their pinned contract.
- D04. Preserve assignment_kind and assignment_ref. Add a separate nullable assignee_ref column to wf.workflow_task for the current responsible individual. A new USER task initializes assignee_ref to assignment_ref; a new GROUP/ROLE task initializes it to null. Claiming a shared task sets assignee_ref to the trusted actor; releasing clears it. The original assignment is retained throughout.
- D05. Support release of GROUP/ROLE tasks by their current assignee and a host-authorized administrator. A former member may release their own claim while retaining host business access, but cannot complete the task. Administrator release clears the reservation and records the administrator who acted. Neither owner nor administrator may release a directly assigned USER task.
- D06. Direct USER tasks need no Claim action under OPTIONAL or REQUIRED. Only their assigned user may complete, with host business authorization. Claim actions apply only to GROUP/ROLE tasks. USER-only and mixed-kind resolvers are valid under either policy; apply the ownership rule to the actual resolved target. Changing the responsible individual on a USER task requires a future reassignment feature.

D07. Eligible peers continue seeing claimed shared work. A current assignee retains discovery and release access after membership removal while business access remains. Own committed receipt recovery requires business access but not continued membership/admin privilege. Administrative release requires a short recorded reason; owner release requires none. O01–O06 specify the accepted behavior.

## Scope

Include SINGLE shared-task claiming, release, completion enforcement, definition policy, preserving storage evolution, authoritative history and command recovery, shared HTTP/UI support and sandbox demonstration. Reuse host identity, membership, business access and transaction infrastructure.

Exclude delegation, reassignment of the original target, takeover by another member, timers/automatic expiry, new collective policies, membership administration, draft task results, graphical designer authoring and APOLO implementation. The existing definition import/edit flow is the authoring surface for this slice.

## Requirements

- R01 — Policy. Decode the pinned human-node policy and enforce D01–D03 on the server. Reject unsupported policy values and invalid placement. Retain original published JSON, hashes and evidence. Missing policy remains compatible across existing drafts, published versions and active instances.
- R02 — Claim. Claim only an open shared task in the active stage, using trusted USER identity, current membership and host business access. Persist exactly one claimant. A different member cannot displace an existing claimant. The original task ID, assignment, activity and workflow position remain stable. New same-owner claims conflict under O04.
- R03 — Completion. For an unclaimed OPTIONAL shared task, retain direct completion. An unclaimed REQUIRED shared task cannot complete. Whenever assignee_ref is populated, only that individual may complete, subject to current eligibility and business authorization. Direct USER tasks have assignee_ref equal to assignment_ref from creation and complete without a Claim action under either policy. Administrator release permission does not grant completion rights. Membership revocation never silently releases a claim. Apply F016's once-per-new-command membership decision rule; successful receipt recovery is separate.
- R04 — Release. On an open GROUP/ROLE task, the current assignee may release with current host business access even after membership removal. A host-authorized administrator may release another user's claim without group membership. Both preserve the original target and return the task to its policy-governed unclaimed state. USER tasks reject release from both their owner and an administrator. A stale release must never clear a newer reservation. Release cannot reopen a closed task or progress the workflow. Authorization must be enforced for direct core consumers as well as HTTP callers; O05 specifies the integration contract.
- R05 — Atomic commands. Claim/release participate in the host transaction, acquire the existing early version-checked instance write and atomically persist task changes, history, successful receipt and durable handoff. Results contain the actual final managed version. Preserve authorized receipt-first retries and reject command-ID reuse with different normalized input. A claim-versus-completion race has one valid serialized outcome; a failed mutation leaves no partial reservation or release. Refresh current state separately from historical replay results.
- R06 — Evidence and storage. Add assignee_ref through an ordered preserving core migration. Backfill existing OPEN USER tasks from assignment_ref; existing OPEN GROUP/ROLE tasks remain unassigned to an individual. Match trusted user-reference validation and exact identity semantics. Retain assignment and actual completing actor independently. New USER task creation records its initial individual assignee without synthesizing an explicit claim event. Record explicit shared-task claim/release actor, task, time, prior/new assignee and whether release was administrative in authoritative history. Preserve existing immutable evidence. O06 specifies exact encodings, already closed-task treatment, retention on future closure and receipt evolution. Host identity foreign keys and candidate-link tables are unnecessary for the selected single-target model.
- R07 — Authorized reads and UI. Present the stable assignment and current assignee separately, expose the pinned policy and server-derived available actions, and offer Claim and Release only on authorized GROUP/ROLE tasks. USER tasks show their initial assignee and completion action without Claim or Release controls, including for administrators. Reflect exclusive completion in controls. Refresh after success or conflict. Stale controls never authorize a command. Keep current business access checks and bounded pagination; retain claimed-task visibility under O03. Read-only consumers require no command provider. Preserve sandbox-only diagnostic recovery and safe handling of uncertain command responses.

## Observable failures

Denied business access, nonmembership on claim/completion, a different claimant, required-but-absent claim, stale instance version, closed/noncurrent task and unavailable membership/authorization providers must fail without changing ownership or advancing the workflow. An absent or failing authorization adapter cannot grant administrator release. Distinguish malformed input, denial, conflict and infrastructure failure internally while preserving existing non-disclosure rules. Exact categories and HTTP mappings are O04/O05.

## Closed contracts — revision 3

O01–O06 are CLOSED. The owner accepted the product recommendations; the encodings, bounds and integration choices below are engineering decisions within that scope. READY means the implementation contract is settled. Implementation and runtime verification require subsequent work.

### O01 — Definition policy

Add optional claimPolicy directly to HUMAN_TASK, accepting exactly the strings OPTIONAL and REQUIRED. Omission means OPTIONAL; explicit null, unknown values and placement on other node types fail structural validation. Add dto.runtime.TaskClaimPolicy and include the effective value in the parsed Human model. Apply this to minimal-v1.schema.json, scalar-service-v1.schema.json and exclusive-routing-v1.schema.json, with all parser paths interpreting omission identically. Keep schemaVersion 1 and the current canonicalization algorithm; do not inject a default into stored JSON or change retained publication bytes/hashes. New publication provenance uses wf-task-claim-validator-v1 and the applicable updated structural-schema digest.

Core provides both policies as a built-in capability. Keep existing resolver targetKinds validation and required GROUP/ROLE membership-provider checks. No new host capability flag or task-type catalog property is needed. Policy support is independent of optional HTTP activation. Claim administration adapters are checked when their operations are activated/invoked, not during publication. New and pinned definitions use their own node contract; omitted policy preserves earlier behavior. Old binaries reject explicit claimPolicy as unknown and are prohibited from writing after the migration under O06.

### O02 — Direct users and mixed resolvers

USER-only and mixed-kind resolvers support both policies. USER resolution sets assignee_ref to assignment_ref at task creation, so REQUIRED is satisfied without a Claim action. GROUP/ROLE resolution starts with null assignee_ref and follows the node's shared-task policy. Claim and both release operations reject USER targets. Every populated assignee_ref is the exclusive completing individual, additionally subject to current eligibility/business access. OPTIONAL direct completion of an unclaimed shared task leaves assignee_ref null and records the actor in closed_by; completion does not synthesize a claim.

### O03 — Discovery, exact access and action projection

The existing open-task inbox includes a task once when current host business access permits it and the actor is either currently assignment-eligible or its current individual assignee. Eligible peers continue seeing claimed shared tasks, with assignee displayed and Claim/Complete disabled. A removed member who remains the assignee continues finding and reading that exact open task for release while business access remains. This uses the existing inbox and its bounded ascending task-ID scan, 500-candidate budget, source continuation and byte/page bounds from F016. No separate owned-task endpoint or new filter is added. A current assignee can be included without a membership lookup merely to discover/release their task; evaluating claim/completion eligibility still follows the fail-closed membership contract.

Extend WorkflowTaskView and matching wire/UI task models with nullable assigneeRef. Extend WorkflowTaskContract with claimPolicy, canClaim, canRelease and canAdminRelease, retaining canComplete and assignmentLabel. Policy is obtained from the pinned human node. Return the assignee reference only through authorized task projections; the initial UI may display the exact reference without a directory-label API. canClaim requires an open shared unassigned task, current membership and business access. canRelease requires an open shared assigned task, actor equal to assigneeRef and business access. canAdminRelease requires an open shared assigned task plus explicit administrative authorization and business access. canComplete applies R03. A failed provider check is an error, not a false permission silently masking an outage. Action flags also reflect deployed operation support. A read-only host without the optional ownership authorization provider returns canClaim/canRelease/canAdminRelease=false and preserves independently authorized reads and existing canComplete semantics. A configured provider failure still returns an error. Host read-access policy remains independent of this optional command SPI. Read-only consumers expose no command controls when command transport is absent.

Former-assignee release access does not by itself grant instance variables, general history, sibling task submissions or completed-task access. Retain their independent host policies and F016 completed-task/completer access. Update task-event filtering to allow ownership events only where the exact task is authorized; administrative reason text follows the same restriction. Once released, a former member loses this ownership-based inbox/exact-task grant. Own receipt recovery remains possible under O05.

### O04 — Commands, HTTP, results and errors

Add three WorkflowOperation values and immutable dto.runtime commands. ClaimWorkflowTask and ReleaseWorkflowTask contain commandId (UUID), instanceId, taskId and expectedLockVersion (long). AdministrativelyReleaseWorkflowTask adds reason (String). Operations are CLAIM_TASK, RELEASE_TASK and ADMIN_RELEASE_TASK. There is no client actor, assignee, permission or administrator boolean. Core derives identity from WorkflowCommandContext, requires ActorKind.USER and uses trusted host time/correlation. Add corresponding concrete WorkflowExecutionService methods claimTask, releaseTask and administrativelyReleaseTask, plus typed findReplay overloads returning the existing Optional<WorkflowExecutionResult> shape. Normal mutations return WorkflowCommandResult.

Administrative reason is required, nonblank, well-formed Unicode and at most 1000 UTF-16 code units. Preserve it exactly without trimming or normalization. Owner release has no reason field. New claim commands against any already-assigned shared task, including the same owner, conflict. New release commands against an unassigned shared task conflict. Only an identical authorized retry of a previously successful command returns its original success.

Under the existing runtime route prefix and WorkflowRuntimeCommandConfiguration, add POST /instances/{instanceId}/tasks/{taskId}/claim, /release and /admin-release. Request bodies contain exactly commandId, plus reason for admin-release. Add replay-only POST /commands/claim/replay, /commands/release/replay and /commands/admin-release/replay; bodies additionally contain instanceId and taskId. Use existing X-Expected-Lock-Version header on mutations and replay, canonical UUID and exact decimal-string IDs/tokens, 16 KiB request bound, duplicate/unknown-field rejection and scoped errors. Successful mutation returns the existing WorkflowCommandResult wrapper; replay returns the existing found/result wrapper and never executes on a miss. Extend WorkflowRuntimeCommandHost with matching execution/replay methods. Shared activation requires the corresponding host adapter, retaining independent read-only activation.

Use existing wf-runtime-request-v3 normalization with the new operation names. Canonical request contains decimal-string instanceId, taskId, expectedLockVersion and, only for admin-release, exact reason. Actor kind/reference and operation remain in the canonical root. UUID remains the receipt lookup key; time/correlation remain outside the fingerprint. Existing START/COMPLETE normalization remains byte-compatible. New UI envelope kinds are claim, release and admin-release, retaining body/expectedToken structure and exact matching fields, including IDs for execution/recovery. Preserve old start/complete envelope readers. No automatic mutation retry after uncertainty or conflict; preserve the original envelope for authorized recovery.

For a new mutation, validate input, resolve the exact task-instance relationship and current business access, then check own successful receipt. An identical receipt returns before current ownership, membership, admin privilege, lifecycle and expected-version checks. Without a receipt, require matching instance version and active instance/stage/open task, acquire the early checked aggregate write, refresh task state, enforce target/action authorization and mutate. All effects and recording remain in the same transaction. A stale release after any release/reclaim conflicts even when the same individual owns the later claim. Preserve fresh-transaction recovery after rollback; replay never changes current ownership.

Reuse INVALID_INPUT (400), NOT_FOUND (404), NOT_ASSIGNED (403), ASSIGNMENT_LOOKUP_FAILED (503), STALE_VERSION/CONCURRENT_COMMAND/COMMAND_ID_CONFLICT/INVALID_STATE (409) and HOST_CONFIGURATION (500). Add TASK_ALREADY_ASSIGNED, TASK_NOT_ASSIGNED, CLAIM_REQUIRED and TASK_NOT_CLAIMABLE as 409 state conflicts; TASK_ASSIGNED_TO_OTHER and ADMIN_RELEASE_FORBIDDEN as 403; AUTHORIZATION_LOOKUP_FAILED as 503. TASK_NOT_CLAIMABLE covers USER claim/release. Unclaimed REQUIRED completion yields CLAIM_REQUIRED; claimed completion by another actor yields TASK_ASSIGNED_TO_OTHER after current eligibility checks. Inaccessible or mismatched task/instance pairs return NOT_FOUND before exposing ownership or receipts. Input precedes access, authorized receipt precedes state, version/lifecycle precede target-kind and operation checks. Owner release checks actor against assigneeRef; admin-release checks the host permission. Failures produce no successful receipt or ownership history.

Claim/release results reuse WorkflowExecutionResult with ACTIVE instance/activity, OPEN task, unchanged process node, no outcome/closure fields, the updated assigneeRef and actual managed lock version. Exactly one new ownership history event is recorded, so firstHistorySequence equals lastHistorySequence. Claim result assigneeRef equals receipt actor; release result assigneeRef is null. Validate these operation-specific invariants rather than applying completion receipt invariants. Original start/completion result semantics remain supported.

### O05 — Authorization, reasons and recovery

Add the real host extension service.runtime.WorkflowTaskOwnershipAuthorization with boolean canAccess(TaskEligibilityContext context) and boolean canAdministrativelyRelease(TaskEligibilityContext context). Reuse the neutral task/actor context. canAccess means current business permission for the exact task's instance independently of assignment membership or previous admin status; it must not grant access solely because a caller supplied an ID. The second method supplies explicit permission for administrative release. Both are read-only, participate in the host context, and cannot commit or perform external effects. Core invokes this provider for all new ownership operations and their receipt lookup, including direct library calls. It enforces target, owner and membership rules itself; a positive administrative decision never bypasses them for completion.

Require exactly one provider when ownership commands are used; missing/duplicate providers yield HOST_CONFIGURATION, exceptions yield AUTHORIZATION_LOOKUP_FAILED. Boolean business denial is concealed as NOT_FOUND; administrative denial yields ADMIN_RELEASE_FORBIDDEN after business access. Query/UI adapters use the same host policy. A read-only consumer or a host using only existing start/complete operations need not install this new provider. Sandbox implementation uses existing trusted identity and request-instance links, with its administrator permission for the administrative method. Do not introduce a new security system.

Owner release requires actor==assigneeRef and current business access, with no current membership requirement. Administrative release requires current business access and the administrator decision even when the actor is also the assignee; it always requires a reason and is recorded as administrative. Owner and administrator actions share the same state/version checks. For new claim and completion, retain F016's single fresh membership decision after aggregate acquisition and allow an already-authorized in-flight command to finish under that rule.

Receipt lookup and mutation retries require current business access and the original actor/operation/fingerprint. They do not require current membership, retained ownership or current administrator privilege to recover that actor's own committed result. Another actor cannot recover it as their own. This applies even after later release, reassignment of current ownership through claim, or task completion. Sandbox host routing/coordinator recovery must use operation-appropriate business authorization rather than its existing membership-based OPEN-task read gate. Reason text stays within authorized history/receipts and is not put in external event payloads.

### O06 — Migration, evidence, receipts and rollout

Append changes/005-task-claim-release.xml to workflow-master.xml with changeset id 005-task-claim-release, author workflow. Add wf.workflow_task.assignee_ref NVARCHAR(200) COLLATE Latin1_General_100_BIN2 NULL. Backfill only OPEN USER rows from assignment_ref. All existing closed rows and OPEN GROUP/ROLE rows remain null. Add ck_workflow_task_assignee requiring null or DATALENGTH between 2 and 400, and requiring a non-null exact assignment_ref match for OPEN USER rows (including equal DATALENGTH to avoid SQL padded-space equality). Any non-null USER assignee must equal its original target. Use explicit null-aware predicates for USER invariants: (assignment_kind <> USER OR status <> OPEN OR assignee_ref IS NOT NULL), and (assignment_kind <> USER OR assignee_ref IS NULL OR exact target equality including DATALENGTH). SQL literals must be quoted in the migration. This prevents CHECK accepting UNKNOWN for an OPEN USER row. Application validation additionally enforces nonblank, well-formed Unicode and existing exact user-reference bounds. Preserve task IDs, relationships, lifecycle, assignment columns and immutable evidence. Existing open scan/index ordering is sufficient; no new index is required for the bounded scan, nor a policy/timestamp column.

New USER tasks initialize their assignee at creation; new shared tasks begin null. Claim changes null to actor; release changes actor to null. On future completion, retain the current assignee value; OPTIONAL shared completion without a claim retains null. closed_by remains authoritative for the actual completer. Already closed legacy rows remain null permanently unless a separately specified migration changes them. No historical claim is inferred from a completion actor. Retain OPEN/COMPLETED/CANCELLED lifecycle encodings; claiming does not add a task status.

New TASK_CREATED detailsSchemaVersion 4 has exactly taskKey, assignment:{kind,ref}, assigneeRef. USER creation has assigneeRef==assignment.ref; shared creation has null. Continue strict readers for v2 USER and v3 typed creation details. Compare their original fields against immutable task identity; do not compare historical initial assignee to later claim state. New TASK_CREATED delivery eventSchemaVersion 3 retains taskKey/assignmentKind/assignmentRef and adds assigneeRef only for USER (payload maps cannot carry null). Retain readers/delivery of queued v1/v2 creation events without rewriting them.

New TASK_CLAIMED and TASK_RELEASED history use detailsSchemaVersion 1. TASK_CLAIMED details are exactly {previousAssigneeRef:null, assigneeRef:<actor>}. TASK_RELEASED details are exactly {previousAssigneeRef:<prior>, assigneeRef:null, administrative:<boolean>, reason:<string-or-null>}; owner release uses false/null, administrative release true/validated reason. Existing history columns carry actor, timestamp, command, task/activity IDs and sequence. Their delivery events use eventSchemaVersion 1. Claim payload contains assigneeRef; release payload contains previousAssigneeRef and administrative encoded as lowercase true/false string. Actor and task linkage remain in the event envelope. No reason is delivered externally. Keep existing completion detail/event formats and history byte bounds. Consumers must use event type plus schema version, preserving unknown-version rejection.

Write new resultSchemaVersion 5 for all operations, adding nullable assigneeRef to the existing task result shape. Strict v3/v4 readers accept only their original fields and operations, then project assigneeRef=null as an unavailable historical value through a legacy DTO or explicitly inserted null before strict construction of the new model. Never infer it from current rows or rewrite stored receipt bytes. Retain old USER equality and completion invariants when validating those older results. V5 validates USER ownership for new OPEN snapshots, shared claim/release state under O04 and non-null assignee==closedBy on completion when assigned. Old receipt null does not establish that a USER task was unassigned historically. Current task reads remain separate from replay snapshots. No new request fingerprint version is needed because existing operations' inputs are unchanged; new operations have distinct identifiers. SQL operation_type/event_type are bounded strings without enumerated checks, so adding these values requires no widened schema or rewritten existing constraints.

Deploy core/web/UI/host adapters and event consumers together with writers stopped before applying 005 through the host migration owner. Old binaries cannot safely coexist as writers after claims become possible, including on omitted-policy definitions. Mixed old/new writers and downgrade are unsupported. Reads of retained history/receipts and queued delivery formats remain supported as above. JPA validates schema; it never applies the migration. APOLO integration and its production transaction/dependency acceptance remain separate.

## Acceptance scenarios

- AC01 (R01/R03). Omitted policy preserves direct completion on existing unclaimed shared tasks. OPTIONAL supports direct completion and claiming; REQUIRED rejects unclaimed completion. A newly published policy does not change a running instance.
- AC02 (R02/R03). Two eligible members race to claim one task; one becomes claimant. The other cannot claim or complete it. The claimant can complete while still eligible. Exercise the claim-versus-direct-completion race for OPTIONAL.
- AC03 (R04/R06). Owner release clears assignee_ref and preserves task ID and group/role target; another eligible member can claim. Authorized administrator release requires a bounded nonblank reason and records that administrator, previous assignee and reason; an unauthorized release fails. Reason text is absent from delivery payloads. A stale release cannot clear the subsequent claim, including reacquisition by the same actor. New same-owner claim and release-of-unassigned requests conflict.
- AC04 (R02–R04/R07). Membership loss prevents claim/completion, preserves an existing reservation and retains inbox/exact-task release access while business access remains. Eligible peers still discover the claimed task once with disabled claim/completion actions. Business-access loss blocks owner release; authorized administrator recovery remains available. Include bounded pagination/continuation across mixed eligible/current-assignee rows and independent general-history/submission access checks.
- AC05 (R05/R06). Identical authorized claim/release retries recover the original result without another effect; different input/actor conflicts. Own replay after membership or administrator-privilege removal succeeds with current business access and fails after business-access revocation. A forced recording failure rolls back ownership, aggregate version, history and receipt. Validate historical receipt snapshots after later release/reclaim and strict v3/v4/v5 readers.
- AC06 (R01/R06). Migration preserves existing tasks/targets/evidence, backfills OPEN USER assignee_ref from assignment_ref and leaves OPEN GROUP/ROLE assignee_ref null. Already closed tasks retain null assigneeRef under O06. Strict old receipt/history readers and newly versioned evidence remain usable.
- AC08 (R01–R04/R06/R07). Under both OPTIONAL and REQUIRED, new USER tasks initialize assignee_ref to assignment_ref and permit direct completion only by that user with business access. Creation evidence records initial assignment without an explicit claim event. Owner/admin release and explicit Claim requests for USER tasks are rejected with no state change; UI exposes neither action. A mixed-kind resolver returning USER follows this rule, while one returning GROUP/ROLE starts unclaimed and follows its shared-task policy.
- AC07 (R07). Shared UI shows target, claimant and policy with correct Claim/Release/completion controls, including administrator release, success/conflict refresh and uncertain-response handling. Verify read-only composition and the selected claimed-task visibility without rerunning unrelated workflows.

## Research context

Candidate eligibility and individual responsibility are separate in [Camunda's schema](https://github.com/camunda/camunda-bpm-platform/blob/master/engine/src/main/resources/org/camunda/bpm/engine/db/create/activiti.mysql.create.engine.sql) and [Flowable's claim implementation](https://github.com/flowable/flowable-engine/blob/main/modules/flowable-engine/src/main/java/org/flowable/engine/impl/cmd/ClaimTaskCmd.java). These informed D04. Their broader assignment, permissions and lifecycle contracts are not adopted implicitly.
