# F016 — Shared group/role task assignment with current membership

**Status:** IMPLEMENTED, revision 2 — 2026-11-07. **Owner:** Workflow project owner. **Constitution:** 6.1.0. **Authorization:** owner requested implementation through verification and handover on 2026-11-07.

## Purpose and decisions

One Finance approval task should be visible to eligible Finance members and complete once when any eligible member submits. Current code requires an individual assignedUserRef in resolution, persistence, completion, creation evidence and inbox access. This feature extends that boundary while retaining SINGLE progression.

**AGREED:** one shared task; current host group/role membership; no claiming; one accepted completion; actual actor attribution. USER assignment remains supported. GROUP and ROLE identify host-owned targets, not lists of task copies. Claiming/releasing is the next separate feature, with its own specification. Its ID is assigned when that specification begins.

Authority: [constitution](../../constitution.md) C02/C03/C05/C06/C09/C10; [constraints](../../constraints.md) CON-05–08/10/12; [assumptions](../../assumptions.md) ASM-02–06; [design precedence](../../design-sources.md). F016 supersedes direct-user-only assignment for SINGLE; it does not implement ALL or change the fixed obligation count.

## Scope

Include core assignment and eligibility, preserving persistence/evidence evolution, authorized task discovery and exact reads, workflow-web runtime mapping, workflow-ui task presentation, and a sandbox membership adapter sufficient to demonstrate the behavior. Use existing host identity and transaction ownership.

Exclude claim/release/reservation, delegation, administrative reassignment/override, ALL implementation, ANY/QUORUM, per-member task expansion, group administration/directory synchronization, structured submissions, new workflow node types, APOLO implementation and the designer. No membership snapshot is stored as the authority for future completion.

## Requirements

- **R01 — Assignment:** one SINGLE activity creates exactly one task with one valid typed USER, GROUP or ROLE target. The resolver returns the target, not its members. Missing/invalid target or invalid task count fails entry atomically. The stable target is retained for the task's lifetime in this slice. Group and role identifiers must be unambiguous within the host's relevant scope. Existing direct-user definitions and tasks remain usable.
- **R02 — Mandatory eligibility:** core requires a trusted actor. USER eligibility checks identity; shared eligibility requires a host-supplied current-membership decision for that actor and exact task target. The check is mandatory for new completion and cannot be bypassed by omitting optional guards. Host business authorization remains additional. Missing adapters and lookup failures fail closed; membership failure and provider unavailability remain distinguishable internally without leaking protected target existence externally.
- **R03 — Membership changes:** a newly eligible member may discover/complete open work; a removed member may no longer do so. Completion must recheck independently of earlier reads and browser controls. Membership changes do not create/cancel tasks, alter the assignment target or reopen completed tasks. A valid target can temporarily have no eligible members: no completion is possible and F016 adds no timeout, fallback assignee or automatic cancellation. The once-per-command decision and invalid/deleted target rules are settled in O02 below.
- **R04 — Completion:** no claim, persistent ownership reservation or new intermediate status is needed. Retain early checked instance mutation and the host transaction. Only one competing completion may commit; a losing different command cannot overwrite the accepted actor/outcome or be reported as its own success. Downstream failure rolls back this completion and its effects. Existing outcome/comment and sequential-stage semantics continue.
- **R05 — Authorized discovery:** host-authorized inbox results include eligible direct and shared tasks once per task ID. Apply authorization with correct bounded pagination and continuation; do not filter one fixed database page and falsely report exhaustion. Exact task/activity reads and completion controls use host access decisions. Group membership is not an automatic grant to all instance/business/history data. A stale page does not authorize completion.
- **R06 — Evidence:** retain the target on creation and the actual trusted completing actor on accepted completion, with the existing outcome/submission evidence. Membership changes never rewrite historical actors or assignment evidence. Do not impersonate a group, overwrite assignment with the completing user, or copy the directory roster into core. O05 specifies evidence/schema compatibility.
- **R07 — Recovery and historical access:** preserve successful-command identity and actor-sensitive normalization. Another member's different submission is not a replay of the winner's command. New-completion membership checks must not replace the authorized successful-receipt path. A former member can recover their own successful command while current host business access permits it, under O04. Recovery UI is a testing/diagnostic tool, not an end-user feature.
- **R08 — Web/UI:** show the assignment kind and host-resolved display label/reference without presenting it as an individual assignee. Eligible users complete directly. Refresh outstanding work after accepted completion or conflict; other sessions cease seeing the task on their next authorized refresh. Push notifications/live synchronization are outside scope. Preserve F015 read-only consumption without command providers and independent HTTP group activation.
- **R09 — Compatibility and migration:** evolve the non-null assigned_user_ref model through the ordered preserving core migration specified in O05, with hosts executing it. Retain existing USER task identity, status, actor history, pinned definitions and valid receipt behavior. Do not modify applied changesets, reinterpret a user reference as a group, or rewrite immutable historical evidence.

## Observable failures

Invalid resolver output fails stage entry without a partial activity. Nonmembership/denied business access prevents a new completion. Membership-provider failure never implies eligibility. Concurrent/stale submissions fail without replacing the committed result; UI refresh exposes the current authorized state. Unsupported assignment capability fails explicitly rather than falling back to USER behavior. Exact categories and transport mapping are specified in O01.

## Acceptance scenarios

- **AC01 (R01/R09):** an existing USER assignment retains its direct completion behavior; a new GROUP or ROLE target produces one shared task ID regardless of member count. Invalid target output creates no partial stage.
- **AC02 (R02/R03/R05):** two eligible members can independently discover the same task. A new member becomes eligible; a removed member cannot submit from an already-open page. Nonmembers and a failing/unconfigured provider cannot complete it.
- **AC03 (R03):** an existing valid target with no current eligible members leaves the task open; adding an eligible member makes it actionable without replacing the task.
- **AC04 (R04/R06):** competing members submit different outcomes for the same task; at most one commits, exactly one completion actor/outcome is retained, and progression happens once. A forced downstream failure leaves that command's completion uncommitted.
- **AC05 (R05/R08):** mixed direct/group/role eligibility produces bounded, nonduplicated pages and correct continuation, including access-filtered candidates. Task UI displays the target, completes without claiming, and refreshes correctly after success/conflict. Read-only composition still requires no command provider.
- **AC06 (R06/R07):** creation and completion distinguish target from actor; history does not change after membership changes. Winner retries and authorized recovery follow the closed recovery contract; another member cannot reuse the winner's command as their own result.
- **AC07 (R09):** migration and history readers retain representative pre-F016 USER tasks, creation evidence and receipts, including completion of a previously open USER task. New target kinds round-trip without weakening existing evidence validation.

### O01 — Typed assignment and host integration

Use `AssignmentTargetKind { USER, GROUP, ROLE }` and `TaskAssignmentTarget(AssignmentTargetKind kind, String ref)` in core `dto.runtime`. Both fields are required. References are nonblank, well-formed Unicode, at most 200 UTF-16 code units (400 bytes), case-sensitive and preserved exactly without normalization/trimming. SQL equality also checks byte length to avoid padded-space equality. This retains current USER reference bounds. Kind is part of identity. Host references must encode their own tenant/organization scope where needed; do not add a second scope field or use display names as identity. Deleted identities must not be recycled to grant access to old tasks.

`ResolvedTask` becomes `(String taskKey, TaskAssignmentTarget assignment)`; `SingleAssignmentResult` keeps its task list and reviewRevisionRef. `WorkflowTaskView` replaces assignedUserRef with assignment and retains its other fields. No source/binary compatibility shim is required for the coordinated core/web/UI/test-host update; stored data/evidence compatibility is required by O05.

Extend `SingleAssignmentCapability` to `(String resolver, Set<AssignmentTargetKind> targetKinds)`, a nonempty immutable set. Existing descriptors are updated explicitly to `{USER}`. Keep the existing definition JSON `assignment.resolver` notation and language schemaVersion 1. Do not add a group expression or identity field to the workflow definition. Add `targetKinds()` to `SingleTaskAssignmentResolver`; registry kinds and capability descriptor kinds must agree. Publication provenance includes the sorted target kinds and validator identifier `wf-shared-assignment-validator-v1`. Publication checks installed resolver/descriptor agreement and the presence of exactly one shared assignment provider when a referenced resolver declares GROUP or ROLE. No resolver or membership lookup runs during publication. New resolution validates returned kind against the descriptor before persistence.

Stable resolver IDs keep their existing assignment contract. Existing USER resolvers cannot silently begin returning groups for pinned workflows: use a new resolver ID and new draft/publication for that change. A new resolver may declare multiple supported kinds, but its documented stable business contract governs selection. Existing publication documents/hashes remain untouched. At new stage entry, check the actual resolver/kinds and provider; completion of an existing task uses its persisted target and does not rerun assignment resolution. USER-only hosts need no shared provider, including for read-only consumption.

Add one real host extension in `service.runtime`: `WorkflowSharedAssignmentProvider` with `boolean targetExists(AssignmentContext context, TaskAssignmentTarget target)` and `boolean isCurrentMember(TaskEligibilityContext context)`. `TaskEligibilityContext` in `dto.runtime` contains `(WorkflowTaskView task, String actorRef)`; the exact task/instance IDs allow host policy lookup without exposing persistence or security objects. Core invokes these only for GROUP/ROLE. `targetExists` is called on stage entry before creating its task; a false result fails entry. `isCurrentMember` must return false for a missing/disabled target, or a person who is not currently a member. Providers are read-only, cannot independently commit or modify workflow state, and throw on lookup failure rather than returning a synthetic allow. USER eligibility is enforced directly by core.

Malformed resolver target, false targetExists or undeclared returned kind yields `INVALID_ASSIGNMENT` (HTTP 500, sanitized, as an invalid host resolver output). Missing/duplicate provider or descriptor mismatch yields `HOST_CONFIGURATION` (500). Membership false yields `NOT_ASSIGNED` (403 after host visibility authorization). Add `ASSIGNMENT_LOOKUP_FAILED` (503) for provider exceptions/unavailability, with diagnostic causes retained server-side only. Read providers use the same category; no partial successful page on failure. Existing `INVALID_INPUT` 400, `NOT_FOUND` 404, stale/concurrent/state/command-ID conflict 409 and limits 422 stay unchanged. Host authorization hides unreadable records with 404 before disclosing state; loss of membership on a still-readable task can return 403. Never automatically retry business effects; an explicit retry retains the original command ID/payload.

### O02 — Current membership and the decision instant

**Owner decision:** once the fresh completion membership check succeeds, later revocation does not invalidate that in-flight command. Revocation affects subsequent checks/commands. There is no second membership check at flush/commit and no lock coupling the external directory to the workflow transaction.

For a new completion: validate trusted input and current host business access; attempt same-actor receipt replay; if absent, load/check the instance, perform the existing early version-checked instance write, load and validate the exact active task/creation evidence and pinned outcome, then perform the single mandatory membership check before task closure or downstream business effects. Failure rolls back the early instance write as well. Ordinary read/UI eligibility checks never substitute for this decision. Existing nonmembership checks for USER remain identity checks. Additional independent host business validation remains permitted.

The provider must consult the host's authoritative membership source for this invocation; do not authorize from login-time token roles, a prior inbox response, or a cross-request membership cache. The contract is current as observed by that authoritative lookup, not globally linearizable directory replication. A remote failure returns 503; it cannot fall back to cached allow. APOLO chooses its actual authoritative source during integration and verifies this contract there. That future integration choice does not block implementing the neutral boundary and sandbox.

The sandbox uses a host-owned in-memory membership registry keyed by typed stable target, with atomic immutable set replacement and per-call reads. It is development fixture state, not production persistence. A shared task sample uses two reviewer principals with GROUP membership and a ROLE sample; fixtures can add/remove membership and remove a target from tests without a membership-management endpoint or screen. Existing USER sample resolver IDs retain their behavior; new sample IDs select shared targets. Provider absence/lookup failures and membership changes during an in-flight completion are controllable by test doubles/fixtures.

A valid empty target permits task creation and leaves work pending. A missing/disabled target at entry fails with INVALID_ASSIGNMENT; deletion/disablement after creation leaves the existing task OPEN and makes all new eligibility checks false. Retain its stable reference for diagnostics/history. F016 adds no cancellation, fallback, reassignment or target re-creation operation. Provider lookup failure is distinct from known deletion. Fixing the host target under the same retained identity can restore eligibility; assigning that identity to an unrelated group is prohibited.

### O03 — Bounded inbox, reads and presentation

Add core query `listEligibleTasks(String actorRef, long afterId, int limit, Predicate<WorkflowTaskView> hostAccess)` returning the existing `WorkflowTaskPage`. Actor is trusted host input, not a request field; hostAccess is required, read-only and grants business visibility. Existing listAssignedTasks remains an exact USER-only query for direct-assignee callers. The shared web `listAssignedTasks` adapter uses the new eligible query; its HTTP route stays `GET /tasks/mine` with afterId/limit. No client-supplied membership list is accepted.

Use ascending task-ID keyset scanning of OPEN tasks, filtering USER candidates to the supplied actor with exact equality and including shared candidates. Scan at most 500 candidates per call in chunks of at most 100; evaluate hostAccess before membership. Return at most limit (1–100, default 50) eligible rows. Stop on reaching the result limit or scan budget. The continuation is the last examined candidate ID when more source rows exist; peek one source row to determine exhaustion without advancing past an unexamined row. No returned item is skipped. Return null only on source exhaustion. An empty page may have continuation and must retain a working Next control. Do not auto-drain pages in the UI. Membership/provider checks are bounded by examined candidates; no unbounded directory enumeration is needed. A provider/access error fails the page instead of silently skipping it.

The cursor is a source position, not proof of access, a count or a stable snapshot. It may refer to an unreturned candidate, matching the existing source-continuation model; disclose no candidate fields or totals. Reauthorize every page. Membership changes or task changes between pages require a refresh from zero to rediscover newly eligible earlier IDs. The same rules apply when host-filtering instance task pages; authorized instance access is still separately required.

Historical visibility remains host-owned. Sandbox policy: administrators may inspect all; existing USER assignees retain their current task/history access; current shared members may read their OPEN shared tasks and the corresponding instance/activity context; the actual completer retains access to their completed shared task/context while host business access allows it. Shared membership alone does not expose completed tasks, sibling task submissions, or other instances. Exact activity/instance/graph links must use the same task-based policy and bounded existing traversal, not broader role-name access. Hosts may supply stricter business rules or explicitly authorize broader historical access. Submission pages must filter each exact task and preserve continuation rather than expose every sibling submission merely because the activity is readable.

Core task views and command results carry `assignment: {kind, ref}`. Extend `WorkflowTaskContract` with `boolean canComplete` and `String assignmentLabel`; add read-host methods `canCompleteTask(WorkflowTaskView task)` (default false) and `assignmentLabel(WorkflowTaskView task)` (default target.ref). These are evaluated only after task access is authorized. The sandbox canComplete rule requires OPEN plus current assignment eligibility and business completion permission; admin inspection alone does not grant completion. This is a UI hint and is rechecked on command execution. Labels are plain escaped text up to 200 code points/400 UTF-16 bytes; absent/unavailable display-name enrichment falls back to the stable reference and never changes authorization. Lists show kind/reference; exact task uses the label. Core evidence stores no mutable labels.

### O04 — Own-command recovery and user-facing behavior

**Owner decision:** a former member may recover their own successful result if current host business access still allows it. Core's actor/operation/full-fingerprint validation remains authoritative. Neither current membership nor current OPEN state is required for this successful replay. Different actors or different payloads cannot use the receipt; after visibility authorization they receive COMMAND_ID_CONFLICT, with no winner payload leaked. A replay-only lookup with no receipt returns the existing absent result and never executes. With no receipt, ordinary completion proceeds to the fresh membership check and can be denied.

Host adapters must authorize current business access before both execution and receipt lookup without requiring current assignment. Move the sandbox replayComplete precheck away from the existing membership-shaped access.task check. Original completing actors retain exact-task visibility as specified in O03; core still checks receipt ownership. Revocation of business access denies retrieval even to the original actor. Apply this ordering to normal POST retries and the coordinator's post-rollback replay path, not just the diagnostic endpoint. No new generic ownership-bypass API is introduced.

**Recovery is testing/diagnostics only.** Keep the backend receipt guarantees and existing diagnostic routes; production consumers need not mount a recovery page. Add `diagnosticsEnabled` to the shared task component, default false. With false, hide recovery links, raw expected tokens, command/envelope diagnostics and diagnostic navigation; on successful completion show confirmation and refresh the task/current-work view. With true, the sandbox may retain its existing recovery navigation and exact diagnostic details. Normal users see concise success, access/conflict or uncertain-outcome feedback. An uncertain response preserves the frozen command internally and must not generate a replacement ID or automatically re-execute; hosts can resolve it through their backend without exposing the testing screen. Read-only components still need no command transport. F016 does not redesign the diagnostic page or build a new production retry UI.

### Focused acceptance refinements

AC02 includes revocation before the fresh check (deny), revocation after a successful check (allow that command to finish), and later commands (deny). AC03 includes target deletion after entry without automatic cancellation. AC05 includes a scan-budget-exhausted empty page with continuation, memberships changing between pages, read-only/admin inspection without completion, and default non-diagnostic completion versus sandbox opt-in. AC06 includes own receipt lookup after membership removal, denied retrieval after business-access revocation, different-actor receipt conflict, and an absent lookup that never executes. AC07 includes v2 creation evidence, v3 receipt decoding, new shared v3/v4 evidence and old queued delivery payloads. These are targeted changes to the existing scenarios, not a new full-system campaign.

No material F016 contract remains open. APOLO membership-provider implementation and production access policy are integration work under ASM-05/06. Claim/release remains the next separately specified feature. Routine implementation details can vary only within these observable contracts.
