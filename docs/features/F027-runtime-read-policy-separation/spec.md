# F027 — Runtime read policy separation

**Status:** IMPLEMENTED, revision 6 — 2026-11-16. **Owner:** Workflow project owner. **Constitution:** 6.6.1. **Authorization:** owner approved revision 6 implementation and focused verification on 2026-11-16.

## Outcome and authority

Replace host implementations of workflow retrieval/paging with one library-owned authorized read implementation. Hosts supply trusted actor identity, access decisions, existing operation-authorization adapters and external identity/directory information. Preserve current sandbox access, errors, HTTP responses and pagination, including distinctions between routes. Revision 2 adopts the owner's clarification: ordinary reads take actor identity only; command context is supplied separately where an existing operation-specific adapter needs it.

Revision 3 adopts the owner's simple visibility policy: administrators can see all workflow instances, tasks and activities across business domains; ordinary users retain existing visibility rules; operation permissions remain separate. This explicit administrator read grant takes precedence over baseline-preservation wording where the current implementation checks business access before recognizing an administrator.

Revision 4 selects `canReadTask` plus core eligibility for My Tasks. `WorkflowTaskOwnershipAuthorization` is confined to claim/release operations (including administrative release), their availability hints and recovery; it is not a dependency of task discovery or read visibility.

Revision 5 explicitly removes reassignment authorization's dependency on ownership authorization. Shared business-access checks are reused through a host-private helper, preserving existing decisions and keeping operation contracts independent.

Revision 6 makes reassignment directory search default to unsupported/denied, allowing a host to implement only assignment labels.

The owner selected this analysis/planning scope after reviewing `WorkflowRuntimeReadHost`. Interface sketches from that discussion were illustrative. This revision refines them against implementation at `d62bfda0eccab656e14e2d16253f355c0043ffce`; the API shape in [plan.md](plan.md) was proposed during preparation and adopted for this implementation. The subsequent owner request on 2026-11-16 approves this public integration change and its implementation.

Apply [CON-01/02/03/10/12](../../constraints.md), [ASM-01 and ASM-06](../../assumptions.md), [constitution C03/C09/C10](../../constitution.md), [source precedence](../../design-sources.md) and [package boundaries](../../package-structure.md). Existing policy and wire contracts are owned by [F015](../F015-runtime-task-instance-extraction/spec.md), [F017](../F017-task-claim-release/spec.md), [F022](../F022-previous-decision-comments/spec.md), [F025](../F025-workflow-cancellation/spec.md) and [F026 revision 2](../F026-task-administration-reassignment/spec.md). APOLO policy/compatibility remains unverified under ASM-01/06.

## Scope

Include the seven retrieval methods on `WorkflowRuntimeReadHost` (four collections and instance/task/activity exact reads), their runtime-controller consumers, advisory action composition, host identity, and separation of directory/label lookup. Migrate the sandbox and affected tests/integration documentation together. Existing core queries remain the persistence implementation.

Exclude schema/migration changes, command execution/replay changes, permissions or business rules beyond the selected administrator visibility policy, tenant/query engines, custom query-provider frameworks, batch-authorization infrastructure without a demonstrated need, UI redesign, new filters/totals, and broad viewer-interface redesign. Existing graph/history consumers of sandbox access helpers retain their ordinary-user behavior and honor the selected administrator read grant when those helpers change.

## Required behavior

### R01 — Ownership and activation

Core owns workflow selection, bounded filtering, paging and engine eligibility/state calculations. A concrete authorized-read facade uses neutral DTOs and host policy; raw `WorkflowRuntimeQueryService` queries remain documented as requiring caller authorization. Web owns HTTP parsing/projection, route error mapping and command-activation presentation gates. Host owns trusted identity, policy, directory data and transaction infrastructure. No security-provider objects, web exceptions or web DTOs enter core.

Core inclusion/root scanning must not newly require runtime-read or command adapters for consumers that do not use authorized reads. Explicit web runtime-read activation requires its identity/read-policy adapters. Optional mutation authorization remains fail-closed without activating command endpoints. Direct-core hosts may call the authorized facade with a trusted actor reference without consuming web or implementing the web identity adapter. Missing policy/configuration never grants access; no fallback to an unscoped page.

### R02 — Distinct read permissions

Keep monitor and task-administration collection grants separate. Their existing 403 denial runs before protected query parsing; ordinary task visibility grants neither permission. Monitoring metadata visibility is a separate decision from exact-instance access: do not require pinned evidence or scan each instance's tasks merely to list monitor summaries.

**Selected host policy:** `canMonitor` and `canAdministerTasks` allow administrators and deny ordinary users. `canListInstance`, `canReadInstance`, `canReadTask` and `canReadActivity` allow administrators without domain, country, business-association, assignment or membership visibility restrictions. This includes booking and budget workflows alike; no separate per-task administration-visibility permission or domain-scoped administrator model is introduced. The host resolves administrator status from trusted identity; core does not hardcode a role name or security-provider dependency. Readable task evidence/submissions remain subject to normal resource existence, integrity and endpoint projection rules, not extra administrator visibility filters. Existing query filters, page/size bounds and pinned display settings still apply; an administrator grant is not a request to return every row in one response or bypass validation.

Exact instance, task and activity reads load through core and ask the host about the loaded resource. Missing and denied exact resources retain concealed 404. Policy lookup failures propagate fail-closed, preserving existing failure categories rather than becoming ordinary denial, empty results or permission grants. Preserve assignment lookup 503, authorization lookup 503, bounded-policy scan 422, malformed input 400 and existing sanitized error projection where applicable.

For ordinary users, sandbox policy remains unchanged: exact OPEN-task access first requires existing business access and admits the current assignee after membership loss. Assignment-based visibility otherwise retains current direct USER, shared-member and actual-completer rules. Instance/activity access uses assignment-based task visibility, not the OPEN-assignee shortcut, with the existing 100 pages of 100 tasks bound and LIMIT_EXCEEDED behavior. Administrators are recognized before these visibility restrictions, including the OPEN-task business-access check. These are host policy choices, not universal engine authorization rules.

Exact-task access can authorize its contract, captured inputs and configured previous decisions without general instance/activity or source-task access. Activity access alone never grants every source submission. Do not conflate task discovery, task reading and permission to mutate it. The host may query business data and use existing public core reads to evaluate policy; it no longer constructs workflow response pages.

### R03 — Preserve each collection algorithm

All lists preserve current ascending exclusive ID continuation, established status/filter defaults, limit validation, no global totals/snapshot guarantee and exact decimal-string wire IDs. Denied candidates advance source continuation. Empty visible pages with continuation remain navigable. Truncation must not skip an authorized row omitted from the response.

- **Monitor:** preserve core summary query and one candidate page, default ACTIVE, ALL semantics, default 50/maximum 100; apply host metadata visibility without refilling or loading each instance's pinned evidence. Sandbox administrator results are unchanged.
- **My tasks:** retain `listEligibleTasks`, not the narrower similarly named assignee query. For each existing candidate require `canReadTask(new TaskEligibilityContext(task, actorRef)) && (isCurrentAssignee(task, actorRef) || isEligible(task, actorRef))`. Core owns the current-assignee/eligibility calculation; the host owns task visibility. Do not call or require `WorkflowTaskOwnershipAuthorization` for this list. Retain at most 500 examined candidates, chunks of at most 100, visible-count stopping, source continuation and the existing core UTF-8 page bound. Ordinary-user read policy retains its existing business-access rules; current assignees retain discovery after membership loss when that read policy allows it. Read-only hosts can expose My Tasks without an ownership adapter; shared-task eligibility still uses the existing membership provider.
- **Instance tasks:** first authorize the instance, then apply exact-task visibility. Preserve the current bounded scan/refill until requested visible count, exhaustion or 500 examined candidates, including continuation over denied rows.
- **Administration tasks:** first require the separate collection grant. Preserve exactly one candidate page of at most `limit` rows, current filters including case-insensitive literal pinned-name matching, metadata projection, authorization filtering and source continuation; no refill. Sandbox filtering continues using exact-task read policy.

Under R02, administrators pass monitor/administration row visibility and instance-task read checks across domains. **My Tasks remains a personal work list**: administrators pass its read predicate but still must be the current assignee or currently eligible. No additional ownership-business-access filter applies to administrators or ordinary users beyond the selected read predicate. Administrators inspect all tasks through administration or instance-task lists. The visibility grant does not assign every task to the administrator or change any pagination algorithm.

F015 R02's blanket “Do not refill pages” wording conflicts with the implemented bounded instance-task adapter and its retained tests. On adoption, this requirement supersedes that wording **only for the existing bounded instance-task scan**, preserving observed behavior as requested. It does not change administration or monitor paging, permit unbounded scanning or alter historical evidence. Activity-submission filtering retains its own existing 500-candidate bound and per-source-task checks; it is not replaced by the administration algorithm.

### R04 — Reuse operation authorization without merging grants

Reuse `WorkflowTaskOwnershipAuthorization` (`canAccess`, `canAdministrativelyRelease`), `WorkflowTaskReassignmentAuthorization` (`canAccess`, `canReassign`, `isValidTarget`), `WorkflowCancellationAuthorization` (`canAccess`, `canCancel`) and `WorkflowSharedAssignmentProvider` (membership/target existence). Do not introduce competing read-side copies of those operation policies. Read visibility is not an implementation of their business-access grants.

Ownership `canAccess` and `canAdministrativelyRelease` remain authoritative only for claim/release operations, their advisory availability and recovery. Read policy must not invoke the ownership adapter indirectly to obtain business access. The host may share an internal business-access helper between its read policy and operation adapters, preserving existing ordinary-user decisions without making either public contract depend on the other. Membership and assignment eligibility remain separate from ownership-operation permission. This separation introduces no new business-access interface and changes no claim/release or recovery semantics.

`WorkflowTaskReassignmentAuthorization` must neither inject nor call `WorkflowTaskOwnershipAuthorization`, including indirectly for `canAccess`. In the sandbox, extract/reuse the existing business-access check through a host-private helper used by both authorization adapters and ordinary-user read policy where appropriate. Preserve its actor/instance-link decisions and failure behavior. The helper must not apply the administrator read shortcut, ownership privilege, current assignment or reassignment privilege as an extra business-access condition. `canReassign` and `isValidTarget` remain reassignment-specific decisions; `canAdministrativelyRelease` remains ownership-specific. Reassignment availability and recovery must work without an ownership adapter when their own required adapters are supplied. Current business access and original-actor receipt rules remain required for reassignment recovery, without newly requiring fresh reassignment permission or destination validation on a successful replay. No public business-access interface or core dependency on host implementation is added.

Administrator read access does not automatically grant completion/approval, claim, release, administrative release, reassignment or cancellation. Keep `canCompleteTask` and the existing operation adapters independent of the administrator read shortcut. An administrator may read a task while every mutation is unavailable; existing operation policy may independently authorize a specific administrative action.

Library availability calculation combines existing operation decisions with engine state, ownership, claim policy and membership. Retain a narrow, default-false host completion permission hint because no equivalent general completion adapter exists. It is advisory, adds no new command authorization hook, and preserves the sandbox's present completion policy. Missing optional operation adapters suppress their corresponding hints; missing ownership policy does not block or broaden My Tasks and leaves ownership-operation hints unavailable.

Preserve existing asymmetry: completion availability in the task contract is not gated by command-endpoint activation; claim/release/administrative release hints are. Cancellation/reassignment availability retain their own existing activation semantics. Cancellation requires an authorized ACTIVE instance; reassignment availability retains OPEN task, ACTIVE instance and current-activity checks. Retain owner release after membership loss under business access and inability to complete another actor's claimed task. Commands remain authoritative and revalidate exactly as before.

Keep the snapshot order: initial exact-task authorization, aggregate token read, then final task read/authorization for contract and reassignment availability. Preserve submission reauthorization when completion becomes visible after the initial OPEN-task grant. This refactor must not replace those reads with a stale cached grant.

### R05 — Trusted actor identity and separate operation context

Ordinary read facade methods and read-policy callbacks accept only the trusted actor reference as identity, plus their existing resource/query arguments. Shared web obtains it from `WorkflowRuntimeReadIdentity.currentActorRef()`; a direct-core host passes the reference obtained from its authenticated server context. Reuse `TaskEligibilityContext` for task policies because it already contains only a task and actor reference. No ordinary read requires `WorkflowCommandContext`, timestamp, correlation ID or actor-kind field. Validate the actor reference under existing core actor-reference rules; validation does not establish authentication. Clients cannot choose identity through new read parameters. Existing HTTP correlation/error reporting remains independent of read-policy inputs.

Cancellation availability is the specific exception at the operation-authorization boundary: the existing `WorkflowCancellationAuthorizationContext` embeds `WorkflowCommandContext`. Obtain that richer context separately from a trusted host cancellation-context factory, only after the instance read grant and ACTIVE check and when cancellation authorization is configured. Its actor reference must match the actor authorized for the read; mismatch fails closed as a host configuration error. Preserve existing actor-kind/authorization semantics; do not manufacture a USER actor or a timestamp in the read facade. Missing cancellation-context support suppresses cancellation availability, without blocking unrelated reads; configured factory/authorization failures follow existing fail-closed error handling. Core availability evaluation takes this explicit operation context, while ordinary reads remain actor-only. Obtaining it performs no command, receipt or mutation. Retain the existing cancellation adapter signature and all actual command context construction/execution behavior.

Directory search and assignment labels remain separate host integration. Exact-task access and reassignment permission precede directory lookup. Preserve current directory validation, opaque cursor, failure behavior and execution-time target revalidation; enumerating suggestions grants no command permission. Preserve label fallback to assignment reference on absent, blank, malformed, overlong or failing labels. Keep the task available to the label resolver so existing task-sensitive labels can migrate unchanged.

`WorkflowAssignmentDirectory.reassignmentTargets` has a default implementation that denies lookup with the existing web 403 `REASSIGNMENT_FORBIDDEN` response. It returns neither an empty successful page nor an unrestricted directory. A host may override only `assignmentLabel`; registering that label-only adapter does not enable reassignment search or grant operation permission. The default label remains the task's assignment reference. Label resolution displays an existing task's assignment target regardless of how its reference was selected; picker result labels come from `reassignmentTargets`. No manual-reference input flow, endpoint or command change is introduced. Explicitly implemented search retains its existing contract.

### R06 — Compatibility and adoption

Preserve endpoint paths, request/response shapes, action flags, error categories and frontend contracts. This is an approved Java host-integration source change: replace data-returning host methods, migrate test host and shared web together, and document the mapping. Do not claim unchanged source compatibility or silently reinterpret a custom host's additional restrictions as granted access. Custom consumers must explicitly map their policies before adopting this version; legacy custom page-query compatibility is outside this slice.

Existing required command adapters, transaction boundaries, pinned evidence, schema, receipts and migration ownership are unchanged. No constitutional principle amendment is needed; feature/source-precedence documentation should identify the narrowly superseded F015 integration requirement when implemented.

## Acceptance scenarios

- **AC01 — Authorized exact reads:** direct facade and shared web return the same authorized resources; denied/missing are concealed consistently. Administrators can inspect existing instances, tasks, activities and readable task evidence across business domains without assignment or business-access visibility restrictions, including OPEN tasks. Ordinary-user rules remain: a former shared member/current assignee may read the exact task while general instance/activity access remains denied. Lookup errors never become grants.
- **AC02 — Collections:** monitor/admin grants precede parsing. Retained fixtures exercise each R03 algorithm independently, including empty continuation, scan limits and byte-truncation resume. My Tasks works without an ownership adapter, excludes unreadable tasks even when eligible, excludes readable tasks when neither assigned nor eligible, and retains eligible peers/current assignee behavior under the ordinary-user read policy. Administrators pass visibility but not automatic personal eligibility. Neither My Tasks nor its read predicate calls ownership authorization. Administration never refills.
- **AC03 — Narrow evidence access:** task contract/inputs/previous decisions need only the appropriate receiving-task grant; activity submissions filter exact tasks. Snapshot ordering and post-completion submission reauthorization are preserved.
- **AC04 — Availability and reuse:** existing operation adapters drive their matching hints; engine state/ownership/claim gates and read-only activation asymmetry remain. An administrator with read access but no corresponding operation grant cannot gain a mutation hint from that read grant. Completion veto/default-false, missing optional adapters, membership loss and adapter failure are covered without executing new mutations.
- **AC06 — Independent reassignment authorization:** reassignment adapter construction and its business-access decisions need no ownership adapter. The shared host helper preserves allowed/denied business access and failure behavior for both adapters; their operation-specific grants remain independent. Existing reassignment recovery authorization is preserved without adding an ownership check, fresh reassignment permission or target lookup on receipt replay.
- **AC07 — Label-only directory:** a host implements only `assignmentLabel` and obtains friendly task assignment labels with the existing fallback behavior. If an otherwise authorized search reaches the inherited `reassignmentTargets`, it receives 403 `REASSIGNMENT_FORBIDDEN`; the label-only adapter neither enables search nor changes reassignment command permissions. Explicit search overrides still return their normal bounded pages.
- **AC05 — Integration:** core-only consumers pass trusted actor references without a web adapter or command context; shared web obtains the same identity from its required identity adapter. Ordinary reads work with no cancellation-context factory and never call it. Cancellation availability alone uses the separate trusted operation context, rejects actor mismatch, and preserves missing-support/failure behavior. Explicit read configuration works without command endpoints and has no competing transaction manager. Sandbox HTTP DTOs and relevant UI interactions remain compatible. Directory/label behavior is preserved.

## Adoption boundaries

The owner approved revision 6 on 2026-11-16. The integration shape in the plan is adopted for implementation; routine provider wiring and neutral error mapping are delegated engineering choices. No additional business policy is assumed. Domain-scoped administrator visibility, per-task administration grants, query-level custom host scoping and batching are outside this stage. Any further discovery that cannot preserve the baseline must be resolved in this specification before dependent implementation, rather than treated as an incidental cleanup.
