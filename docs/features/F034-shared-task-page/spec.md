# F034 — Shared Task page

Revision 6 · READY · 2026-11-19 · Owner: workflow maintainer. [Constitution v6.6.1](../../constitution.md), [constraints](../../constraints.md) CON-03/08/10/13, [assumptions](../../assumptions.md) ASM-05/10, [design sources](../../design-sources.md) and [frontend style guide](../../frontend-style-guide.md).

## Outcome and scope

A person opening a task in APOLO or another host can identify the work, see the information needed for a decision and act on it in one column. An administrator sees the same business page with a separate inspection area at the end. This revision specifies the shared Angular Task detail page, its HTTP responses and its sandbox integration. The host owns navigation, theme and authenticated roles. The mockup's role picker and restart control exist only for preview.

## Reviewer experience

**Page layout.** Follow My tasks with a **Your workspace** page heading, the task name as the title, and the clipboard icon and **Reviewer workspace** at the right of the title row. Allow the workspace label to stack on narrow screens. Use a short description appropriate to the available view. Below the heading, group assignment, status, available actions, business context and the decision form or recorded decision inside one outlined Material card. In the sandbox it uses the same white surface as My tasks, with subtle dividers between sections. Keep the administrator disclosure separate below it.

**Shared assignment and actions.** Introduce a named target with “Assigned to:” and preserve the standalone “Shared task” fallback. Place the status alongside the assignment and any claim guidance below it. Align the task actions to the right when they fit and stack them below the guidance on narrow screens. Label the ownership action “Claim task”. When a claim is required and available, explain the prerequisite. When claiming and direct completion are both available and claiming is optional, show “You can review this task without claiming it.”

**Open status.** Use the host's paired Material 3 secondary container and on-secondary-container colors for the shared Open badge, with readable text in light and dark themes.

**Approve and Reject controls.** In the shared default editor and sandbox booking editor, align decision actions to the right. When the pinned outcomes are the Approve and Reject pair, show outlined Reject in the Material error color followed by filled Approve. Keep the pinned labels. When Reject requires a comment, a blank or whitespace-only comment alone leaves Reject enabled. Activating it shows “Add a comment to reject” on the Comment field and focuses that field before any submission. Clear the displayed error when a valid comment is entered. Preserve protection while an action is pending or unavailable and keep the existing checks for required result fields.

**Previous decisions layout.** Use the grouped timeline from Artboard A. Show one group per displayed step name, with a group count, reviewer initials, reviewer name, outcome, time and comment. Connect entries within a group. Default to oldest first using the supplied history order and let the reviewer reverse the order within and across the loaded groups. Show the number of visible decisions and a breakdown by outcome, marked as loaded while another page is available. Present exact Approve/Approved and Reject/Rejected labels as Approved and Rejected with their respective colors and icons. Preserve other workflow labels in neutral styling and include them as other outcomes in the breakdown. Show a short date and time with the full timestamp available on focus or hover. Render comments as plain text with their original line breaks, show “No comment” for blank entries, and provide Show more / Show less when a comment exceeds three rendered lines. Preserve existing paging, retry and visibility behavior.

- **R1 — Orient the reader.** Lead with the task's node display name, a readable status and relevant ownership. Fall back to the task type display name, then “Task” when names are unavailable. Show “Assigned to you” only when the current identity is known to be the assignee. Use the available assignment label for shared work and show the due date when present. Omit empty metadata, duplicate headings and sandbox instructions from the shared page. Preserve entry from My Tasks, instance and administration.
- **R2 — Present the work once.** Place the frozen business inputs before the decision. For the booking example, show “Booking reference” and “TEST-001” once. Use readable labels and values, including for inputs without a custom editor. Distinguish a missing value from false, zero and an empty string, and preserve significant digits and nested values. Selecting a custom editor must neither duplicate its displayed inputs nor silently discard other inputs. Inspection still shows business context when the editor is absent. Show previous decisions where enabled by the receiving task, before its decision controls, with the step, outcome, actor, time and comment. Preserve the existing visibility, paging and read-error behavior. [F020](../F020-human-task-input-bindings/spec.md) · [F022](../F022-previous-decision-comments/spec.md)
- **R3 — Make the decision actionable.** Show one form selected by the pinned task type. The host editor or shared default owns its fields and outcome buttons. In the booking example, both outcomes require a reviewed room. A nonblank room enables Approve. Reject additionally requires a nonblank comment. Explain the condition at the comment field and use the pinned outcome labels on the buttons. Other task types follow their own contract. When no custom editor is registered, the shared editor renders named fields for the pinned structured result. Reviewers can complete every supported task without entering JSON. Required business data entry is part of the form. The exact schema is diagnostic material. Read-only hosts show inspection only. [F018](../F018-structured-task-submissions/spec.md) · [F033](../F033-optional-task-handlers/spec.md)
- **R4 — Explain availability.** Place permitted Claim or Release actions alongside ownership. Explain when claiming is required, or when the current user can inspect but cannot complete. Show ordinary validation, loading and failure feedback near the work. A conflict refreshes the current task. An uncertain command keeps its frozen request and gives the user a safe next step without exposing a command ID or inviting a fresh submission. Keep keyboard labels, focus and reading order usable as controls wrap on narrow screens. [F015](../F015-runtime-task-instance-extraction/spec.md) · [F017](../F017-task-claim-release/spec.md)
- **R5 — Show the recorded outcome.** An open task has no empty accepted-submission card. On successful completion, refresh the page for either role. Show the recorded outcome label from the pinned contract, submitter, time when available, comment and business result when authorized and present. Present structured results as readable labeled values, retaining exact values. Preserve authorized onward navigation and the distinction between a contribution accepted and a collective review resolved. A closed task has no decision form. For cancellation, explain workflow cancellation or early review resolution from its recorded cause. When submission detail is unavailable, show only the task information the user may read and do not infer an outcome, comment or result from missing data. [F021](../F021-all-collective-review/spec.md) · [F025](../F025-workflow-cancellation/spec.md)

## Administrator experience and access

- **R6 — One final disclosure.** After the business view and any authorized actions, render one collapsed **Technical details** section only for users the authenticated host identifies as administrators. Group the existing task, instance, activity and type IDs, instance/activity inspection links, internal keys, assignment kind and raw references, claim policy, audit metadata and closure codes here. Also place the exact task record, pinned completion contract and schema, expected version token, exact accepted submission/result, JSON download and applicable command-recovery link here. Render entries only when available to this session. Expanding the section must preserve an in-progress form. Successful completion stays on the task even when inspection is enabled.
- **R7 — Keep host authority explicit.** Default to the reviewer view when the role is absent, unknown or loading. The sandbox derives visibility from its authenticated administrator session. Another host maps its own administrator role. Changing task or session discards the prior view and disclosure state. Ordinary users have no technical section, its contents or its links in the rendered page. Reassign and administrative release remain separately authorized actions, distinct from the inspection panel. Administrator visibility confers no task command permission. The server enforces both resource access and field visibility before serializing a response. [F026](../F026-task-administration-reassignment/spec.md) · [F027](../F027-runtime-read-policy-separation/spec.md)

Preserve the decision draft, clear the disclosure on task or session change, and disregard responses for the previous scope. The shared Task and its read integration have no diagnostics hook.
- Reviewers with the relevant instance access can open business history and follow permitted event links. Enforce existing event-specific and exact-task restrictions on the server for both list and direct detail. Return a readable event label, time and actor display, with the permitted step name, decision label, comment and exact-task link where applicable. History navigation uses an event reference and continuation. The raw evidence record, internal keys, actor references and technical event details are reserved for administrators with the relevant grants.
- Sandbox reviewer history uses opaque references and continuations scoped to the process, actor, instance and purpose. Older numeric bookmarks remain valid subject to the existing authorization checks. The owner agreed that previously issued opaque links expire at this upgrade. New opaque links expire at restart or when evicted from the bounded lookup. Reopen history to obtain current links.

## Acceptance scenarios

1. **AC1 · Booking review (R1–R3).** An assigned reviewer sees Review booking, Open, ownership, the booking reference once and the form in that order. After entering a room, both decision buttons are enabled. Activating Reject with a whitespace-only comment focuses Comment and shows the required-comment error without sending a command. A substantive comment clears the error and permits submission. Technical IDs, contract captions, raw payloads and an empty submission panel are absent.
2. **AC2 · Generic or shared work (R2–R4).** An unregistered task type shows its captured inputs and configured outcomes. A reviewer can supply a required structured result using the default editor. When claiming is required and available, the page explains the prerequisite and offers Claim. A read-only host exposes the same permitted business context without mutation controls.
3. **AC3 · Closed and unavailable states (R4–R5).** A successful decision replaces the form with the authorized recorded decision. A cancelled task explains its closure. A denied submission read reveals no submitted values. An uncertain completion displays recovery guidance and prevents a duplicate decision.
4. **AC4 · Administrator and session change (R6–R7).** On the same task an administrator sees the same business content and a collapsed final disclosure. Expanding it reveals the authorized technical records and preserves the draft. An administrator lacking completion or reassignment permission cannot perform that operation. Switching to a reviewer session removes the panel and its contents.

5. **AC5 · HTTP disclosure (R8).** For the same task, inspect actual HTTP bodies for a permitted reviewer, an administrator with task access, and an actor without task access. The reviewer receives only business fields and necessary authorized interaction data. Restricted members are absent, including nested records, command/replay results and error details. Requesting the administrator representation directly does not reveal it. An actor denied task access receives no task data. Missing display labels do not expose raw references. A read-only task response carries no command precondition.

## HTTP field inventory

**R8 · AGREED boundary (2026-11-19).** Technical fields must be withheld from unauthorized users at the server. A UI flag is never evidence of permission. Task access, submission/previous-decision visibility, diagnostics access and authorization to execute a particular command are separate decisions. The field allocation below is AGREED, together with D1–D5. Names below identify current fields, not finalized replacement DTOs.

- **Task detail.** Deliver `nodeName`, `taskTypeName` as title fallback, `status`, `dueAt` and meaningful closure time (`closedAt`). Provide ownership and cancellation explanations as display information. Reserve `activityId`, `taskTypeId`, `taskKey`, `assignment.kind`, `assignment.ref`, `assigneeRef`, `createdAt`, `closedBy` and raw `closureReason` for diagnostics. Display the recorded outcome by its label. Omit redundant `id`/`taskId` on an exact-task read. The task reference used to open an authorized task remains navigation data. See below for `instanceId`, `taskType` and `outcomeKey`.
- **Ownership and people.** Deliver a host-approved assignment or actor display label when available and “Assigned to you” when established by trusted identity. Compute any claim prerequisite from pinned `claimPolicy` and current ownership. Withhold raw policy, account references and `actorKind` from the reviewer. Today's assignment-label fallback returns the raw reference and the node-name fallback can return a key. Use a neutral fallback when display data is missing. Apply the same rule to previous decisions and submissions.
- **Completion contract.** Retain authorized frozen `inputs` (business key, type and exact value), outcome labels and `requiresComment`, `resultContract.mode`, and `canComplete`, `canClaim`, `canRelease` as appropriate. These drive the form even when their machine names are not printed. Supply only the field information required to render, edit and submit the permitted result. Withhold the full pinned contract and `resultContract.schema` (including the client's exact-text copy), raw `previousDecisions.mode` and `claimPolicy`. Expose whether previous decisions are available. Administrative release/reassignment availability and destination lookup belong to callers with the relevant operation access.
- **Accepted submission.** Subject to submission access, deliver the readable outcome, submitter display, `occurredAt`, `comment`, and the authorized business `result` with exact values. JSON business content can be necessary to read a decision. Restrict its full evidence envelope and diagnostic export. Omit submission `taskId`, `activityId`, `instanceId`, `historySequence`, historical `commandId`, `actorKind`, `actorRef`, raw `outcomeKey` and the legacy empty `inputs` map from reviewer reads.
- **Previous decisions.** Deliver `nodeName`, `outcomeLabel`, actor display, `occurredAt` and `comment` within existing task-context visibility. Withhold row `taskId`, `activityId`, `nodeKey`, `outcomeKey`, `actorKind`, `actorRef` and `historySequence`. The reviewer needs continuation for Load more. Use an opaque continuation in place of the raw `nextAfterSequence`.
- **Command and recovery responses.** Return the authorized operation outcome and business state needed for confirmation, conflicts, outstanding collective review and onward task navigation. Withhold nested raw `execution.instance`, `execution.activity`, `execution.task`, receipt metadata, `firstHistorySequence` and `lastHistorySequence` from ordinary responses, including replay. A client-generated command ID for the actor's own pending action remains necessary for existing retry/recovery semantics. It does not grant access to historical command IDs. Retain actionable validation messages without diagnostic snapshots.
- **Coverage.** Enforce the policy on direct reads of task detail, contract, submission, previous decisions and reassignment availability, and on task command/replay responses. Apply equivalent filtering wherever the same records are returned to the same audience, including My Tasks, instance task lists and activity submission lists. Review viewer/history and host-specific equivalents for exposure of these same records under existing grants before selecting changes. Preserve separately authorized business views. Do not return restricted values under aliases, in headers, legacy routes or diagnostic error bodies.

### Agreed command and editor contract (2026-11-19)

1. **D1 · Instance routing — AGREED.** Reviewer task commands identify the authorized task and retain the client-generated command ID. The server resolves the owning instance from that task. The reviewer neither receives nor supplies an `instanceId` for this purpose.
2. **D2 · Version precondition — AGREED.** When an action is available, return an opaque precondition for the displayed task version. Freeze it with the original request. The server checks it on a fresh command and preserves existing authorized replay of that original request. A stale precondition cannot authorize a new mutation. Read-only callers receive no command precondition. Raw `instanceLockVersion` remains diagnostic. Encoding and transport migration belong in the plan.
3. **D3 · Editor and outcome keys — AGREED.** Deliver `taskType` only when needed to select the authorized editor and `outcomes[].key` only when needed to submit an available decision. The chosen key accompanies the command and remains subject to server validation. Use labels for historical and display-only records.

### Display names and generic forms

**Task header follow-up · 2026-11-24.** In the sandbox, show the task's only H1 in the white shell header band, below a breadcrumb from My tasks to the task name. The band shows status, authorized ownership and assignment labels, the pinned workflow name and instance ID, and an optional due date. Keep action and closure information in the task card. The white toolbar and band share one bottom divider above the card area. The band and cards align at desktop and narrow widths. The exact authorized task contract may return the pinned workflow name and owning instance ID for display. This grants no instance navigation or additional reads and does not change the task command contract. Hosts using an earlier response can omit this metadata. Other hosts may use the library's default header.

**D4 · Display-name source — AGREED.** Use current display names supplied by the host, including for previous decisions. Resolve permitted labels on the server after authorizing the task or decision. The trusted request identity supplies the current actor reference for comparison. It supplies no directory of names. Ownership, the assignment target and the person who submitted a decision are different subjects. For a claimed group task, for example, “Finance team” identifies the target while “Claimed by you” identifies its current owner. Use the host's existing user/group/role directory or equivalent identity service for permitted labels. APOLO selects its own backing source. Reuse the optional assignment-directory integration where appropriate, without requiring search, browser directory access or a new core user store.

**Fallback wording — AGREED.** Show “Assigned to you” for a verified self-assignment and “You” for the current user's decision. For other people show the host-approved display name. When a name is withheld, missing or temporarily unavailable, use “Assigned to another user”, “Shared task” or “Reviewer” as appropriate. For a shared assignment with a known claimant, show “Claimed by you” or “Claimed by another user” when a display name is unavailable. A missing display name never implies the task is unclaimed. For a system actor use “System” only when supported by the recorded actor kind. Missing labels must not block work or reveal a login, email or raw reference through a fallback. The current directory default returns the reference and cannot serve as a safe display-name default. Resolve current permitted names when reading history. This does not change the recorded actor or promise the name seen at the time of the decision. A historical-name snapshot would be a separate requirement. [Request identity](../../../workflow-web/src/main/java/io/github/leontecristian/workflow/web/integration/WorkflowRequestIdentity.java) · [Assignment directory](../../../workflow-web/src/main/java/io/github/leontecristian/workflow/web/integration/runtime/WorkflowAssignmentDirectory.java)

**D5 · Generic named fields — AGREED.** When a task has no registered custom editor, the shared Task page must let an authorized reviewer complete it with labeled form controls. This applies to existing published task versions, including nested, repeating and conditional results. No reviewer JSON editor or raw-schema fallback. A registered task-specific editor continues to own its form and decisions. This supersedes F018's generic JSON editing choice for the shared Task page while preserving its validation, precision and accepted-result semantics. ### Named-field behavior (F1–F6 AGREED · 2026-11-19)

- **F1 · What appears.** Derive a reviewer-safe form description on the server from the task's pinned result contract. Resolve local references there. Supply labels, control types, choices and relevant limits or dependencies sufficient for all supported shapes. Keep raw schema documents and validator internals behind diagnostics authorization. Prefer a permitted published title, otherwise split the business property name into readable words (for example, `approvedAmount` becomes “Approved amount”). Use published property order as the display default, relevant permitted descriptions as help, and examples only as hints. Keep frozen inputs read-only and keep the workflow Comment separate from result fields.
- **F2 · Which answers exist.** FORBIDDEN shows no result controls. REQUIRED opens the result fields. OPTIONAL starts with an “Add result” action. Removing an optional result omits it entirely. Within a supplied result, untouched optional fields are omitted. Provide explicit controls where needed to include an empty value, remove an optional answer or choose “No value” when null is permitted. Distinguish omission, null, empty text, empty object/list, zero and false. A required text property with no positive minimum length may be sent empty. A required boolean starts unanswered until the user chooses Yes or No. Never invent an answer to satisfy a constraint.
- **F3 · Simple controls.** Use text fields for strings, exact numeric entry for integers/decimals, Yes/No for booleans and a choice control for enumerations. A required fixed value is supplied automatically by the contract and can be shown read-only when meaningful. Calendar dates have no time zone. Date/time fields allow an explicit offset and preserve supported precision. UUID fields accept text with format guidance. Preserve string content and exact numbers throughout entry, submission and error recovery. A number must reach validation as a number even when it exceeds JavaScript's safe integer range.
- **F4 · Groups and lists.** Show item headings and list controls only for declared arrays. Render a nested object as a labeled group and an array as ordered, individually editable items with Add and Remove. Support primitive and structured items. Preserve order and provide a way to change it. Explain item-count limits at the list. Identify errors by item and field, for example “Item 2 · Reason”. An empty list remains a valid supplied answer wherever the pinned rules allow it.
- **F5 · Dependent fields.** Re-evaluate requiredness and limits when a controlling answer changes. For example, Reject can make Reason required, while Approve can leave it optional. Preserve a still-permitted answer when a condition relaxes. For mutually exclusive object shapes, show a labeled choice first, then the fields for the selected shape. Exclude other shapes' fields from the submitted result. Retain inactive drafts locally while editing the same task so switching back restores them. Clear drafts on completion, task replacement or session change.
- **F6 · Decisions and errors.** Explain an unmet prerequisite beside its field or outcome. Check straightforward requirements before sending. The server validates the assembled result against the pinned schema and business rules. On a definitive validation rejection, keep entries, show the correction at the corresponding control and identify any form-level error. An uncertain command follows R4. If form information cannot be loaded, show a recoverable error and prevent incomplete submission. An existing valid contract must not require a custom editor to work.

**Acceptance examples for the agreed named-field rules.**

1. In the [published-format amount review fixture](../F018-structured-task-submissions/sandbox-structured-review.json), show Approved amount, Note, the separate Comment and Complete. Zero with an empty Note is a valid form result. Send the amount as a number and include the empty note property. A negative amount or a note over 500 characters gets a field-specific correction.
2. On an optional result, compare completion without adding a result, with a permitted empty object, and with an explicitly nullable answer. An untouched optional boolean is absent. Choosing No supplies false.
3. In a repeated conditional item, changing its decision updates the reason requirement for that item alone. Switching an alternative from booking to resource omits booking-only fields from submission. A rejected item retains its draft and displays the error beside the affected field.
4. For the separate display-name behavior (D4), a prior decision shows the current permitted host name after a rename. A missing directory entry still shows the decision with neutral attribution and never reveals the raw actor reference.
