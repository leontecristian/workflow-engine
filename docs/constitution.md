## C01 — Specifications lead implementation

Substantial behavior MUST have a versioned specification before implementation. The specification must describe the problem, scope, observable outcomes, inputs, errors, acceptance scenarios and unresolved decisions. Exact contracts must be settled before dependent code or migrations encode them.

Every implementation task MUST trace to a specified requirement or an explicitly identified enabling task. Implementation discoveries must feed back into the specification. Existing code is evidence of current behavior, not automatic authority to change an agreed contract.

Use AGREED, PROPOSED, PROVISIONAL, OPEN, PENDING VERIFICATION and DEFERRED consistently. Do not convert a proposed table, interface, API path, numeric limit or booking policy into a confirmed requirement without recording the decision. Routine implementation choices within an agreed contract do not need a separate approval step.

## C02 — Deliver workflow execution first

The first capability is a small reusable workflow engine: a working sandbox workflow, then one cross-team booking approval integration in APOLO. The Angular workflow designer follows the first successful APOLO integration.

V1 includes `START`, `HUMAN_TASK`, `SERVICE_TASK`, `EXCLUSIVE_GATEWAY` and `END`, one active process position, human tasks with explicit assignment targets within an activity, a simple persistent task-type catalog, restricted expression routing, relational persistence and authoritative history. Multiple tasks do not introduce parallel process branches. SINGLE is selected: a named resolver with explicit validated inputs MUST return exactly one task with a valid assignment target; invalid count or missing target fails entry. Its accepted outcome resolves the activity and routes within the same command transaction. ALL is also selected: every required task must submit the configured contribution outcome, or another permitted outcome resolves the activity immediately. The task list MUST be fixed and created atomically at activation; additions, removals and waivers are unsupported. Any future audited reassignment must preserve task identity; no general reassignment command is delivered. Early resolution cancels open siblings and preserves earlier submissions. The first decisive command that successfully commits under concurrency protection determines the result, without implicit outcome priority. Submission, resolution, cancellations and synchronous progression MUST roll back together on failure; prior committed contributions remain. F021 specifies and implements the fixed 1–100 task roster, limits and API contracts. These generic policies do not select APOLO approval rules.

The standalone business decision engine is optional later work. Initial delivery MUST operate without decision tables, FIRST/UNIQUE policies, separate decision-definition storage or decision-management APIs. Do not add placeholder modules or schema for that extension.

`EXCLUSIVE_GATEWAY` replaces the former routing type name `DECISION`. Boolean conditions belong to outgoing transitions; the gateway MUST NOT calculate or write a business result. A separate service action may calculate a result through explicit variable mappings. Inclusive and parallel gateways remain distinct future extensions requiring specified branch/join and execution-state semantics; unsupported gateway types MUST be rejected rather than treated as exclusive routing.

Claim/release is selected under F017. Shared tasks use a pinned per-human-node OPTIONAL default or REQUIRED claim policy. Once claimed, only the claimant may complete while currently eligible and host-authorized. Preserve the original assignment separately from nullable assignee_ref. Direct USER tasks initialize assignee_ref to assignment_ref and may complete without claiming under either policy. Claim and owner/administrator release apply only to GROUP/ROLE tasks. Release clears assignee_ref and preserves the original target. A former member may release their own claim while retaining business access. F017 revision 3 specifies and implements these contracts. General delegation, timers, expiration, advanced collective policies such as ANY/QUORUM, parallel orchestration, subprocesses and live migration of active instances remain deferred. Audited administrative reassignment does not authorize a general delegation feature. New capabilities require a concrete need and a specification; changes to this scope require an amendment.

## C03 — Reusable core, web and UI with a clear host boundary

The agreed and implemented separate-development reactor has exactly three Maven modules:

- `workflow-core`: ordinary library JAR containing workflow models, JPA entities/repositories, services, expressions, codecs, neutral integration interfaces/configuration and workflow changelog resources.
- `workflow-web`: ordinary Spring MVC library JAR depending on core, containing reusable HTTP controllers, transport mapping and scoped error handling. Hosts explicitly activate API groups and supply required integration adapters; consumption is optional for hosts using core directly.
- `workflow-test-host`: executable Spring Boot development host containing sample endpoints/adapters and the infrastructure needed to run core locally.

`workflow-ui` is a separate Angular 19-compatible library, targeting APOLO's 19.2.x Angular/Material/CDK line; it is not an additional Maven module. It supplies reusable pages/components and the later designer within APOLO's application shell. The sandbox console consumes the same library. F012 established Angular 19.2 alignment; F013–F015 implemented the three-module reactor, library packaging and shared viewer, administration and runtime functionality. Their feature records specify adapters, exports and scoped verification. APOLO consumption, effective dependency compatibility and production integration remain separate work; the designer remains deferred.

Use packages within core to separate responsibilities. Core MUST NOT depend on web, UI, the test host, APOLO backend implementation, designer or a concrete optional business decision engine. Dependency direction is host → web → core, with direct host → core dependencies when used. Keep one authoritative implementation of each reusable library.

Core may use Spring/JPA internally. Public integration contracts MUST use standard Java or workflow-owned types, without exposing JPA entities, APOLO entities, security-provider objects, JDBC connections or messaging-provider classes. External users and business objects are referenced by stable identifiers.

Hosts own endpoint activation, identity, authorization policy, business data/rules and orchestration, navigation, business forms, datasource, transaction infrastructure, connection pooling, runtime configuration and external delivery. Web/UI share generic implementation, not host policy. Required adapters MUST NOT fall back to permissive authorization; generic commands MUST NOT bypass host business validation. The libraries MUST NOT create competing infrastructure, login/bootstrap or security chains, or mutate global host JSON/theme/provider settings. UI consumes host-approved APIs and preserves exact values and safe command handling; backend enforcement remains authoritative. Command recovery screens are sandbox diagnostics, not end-user functionality; backend idempotency and authorized receipt recovery remain required.

## C04 — Prepare for source integration into APOLO

`workflow-core` will become a sibling Maven module inside APOLO alongside backend, frontend and configuration. Backend depends on core. Core retains its library boundary while joining APOLO's build and release lifecycle. Keep one authoritative implementation.

The move MUST review APOLO's effective root parent, shared versions and plugin configuration before reparenting core. Backend is neither core's parent nor its code dependency. Preserve ordinary JAR packaging and avoid inheriting backend-only infrastructure dependencies.

Move timing, final coordinates and the test host's future location remain open. The test host stays outside backend's production dependency graph. A permanently separate repository or publishing lifecycle is not required.

The adopted web/UI libraries follow the same single-implementation principle: APOLO backend consumes web/core and its frontend compiles the Angular library into its existing application. Their final source locations, coordinates and distribution remain OPEN. This selects no separate production workflow server or frontend application; designer delivery remains after first APOLO integration.

## C05 — Core owns schema; the host owns migration execution

Core MUST package workflow migrations under `db/changelog/workflow/`, with the stable entry point `db/changelog/workflow/workflow-master.xml`.

The test host includes that master in its local Liquibase master. APOLO includes it in its existing master and remains the single production migration owner. Core MUST NOT create a `SpringLiquibase` runner or ship global migration application settings.

Preserve applied changeset identities and resource paths, including during the source move. Evolve schema through new ordered changesets. JPA MUST NOT independently create or update production schema. Host fixture migrations remain outside core's master.

Workflow migrations MUST work without APOLO-owned tables or foreign keys to them. Use workflow-internal constraints for workflow relationships and logical identifiers for external references. Definitions are versioned JSON; runtime state, tasks, variables, receipts and history are relational. Physical names, encodings and concurrency mappings require specification before schema implementation.

## C06 — Commands preserve atomicity and reliability

A successful command MUST atomically cover required synchronous business updates, workflow/variable changes, task changes, history, command receipt and durable event handoff. Workflow persistence participates in the host transaction; an independently committed business action violates this boundary.

Optimistic concurrency MUST protect the instance aggregate, including activity, task and variable mutations. The selected mapping is Hibernate-managed numeric `BIGINT lock_version`, represented by Java `Long` with JPA `@Version`. Every mutation of an existing instance MUST acquire an early version-checked instance write before business effects; a child-row update alone is insufficient. Results and receipts MUST capture the actual final managed version, not assume a single increment. The database design specifies the history-sequence reservation approach; provider behavior, flush ordering and shared transactions remain host verification gates.

Command idempotency MUST return the committed result for an identical authorized retry and reject reuse of the identifier with different input. Successful-receipt resolution precedes state-dependent stale checks and business mutations. Access to a previous result must be reauthorized. Request fingerprints include relevant host association inputs and optional business correlation. The delivered runtime features specify wire encoding, versioned request normalization and command ordering; the [database design](architecture/Workflow_Engine_Database_Design_v1.md) reconciles the current receipt and concurrency contracts. Their local evidence does not replace APOLO host verification.

Registered `SERVICE_TASK` actions execute synchronously with declared, validated inputs/outputs. Failure rolls back the command. Workflow business actions belong in service nodes; transitions select the next node. Each business effect has one owner so host orchestration and a service node do not duplicate it.

Automatic execution must be bounded and reach a human task or an end node on success. The supported graph is acyclic; general loops remain deferred. Each command permits at most 50 automatic node visits: START, SERVICE_TASK (including its action), EXCLUSIVE_GATEWAY and END each cost one; human entry and transitions cost zero. A nonfinal ALL contribution uses no automatic steps. Reject before a 51st visit and roll back the whole command, preserving earlier committed contributions. Initial execution does not automatically retry failed business commands.

External delivery MUST follow a durable handoff recorded in the same transaction and occur after commit through host infrastructure. An after-commit callback alone does not establish durability. Delivery can repeat; consumers must be idempotent. These guarantees apply to every production deployment, including one preceding the designer.

## C07 — Published definitions are immutable; task codes are stable

Workflow definition versions follow `DRAFT -> PUBLISHED -> RETIRED`. Validation results belong to an exact draft revision; `VALIDATED` is not a lifecycle status. Publication validates the current revision and target-host capabilities.

Published workflow content is immutable, including embedded designer metadata. Instances pin exact workflow versions. The pinned human node owns permitted outcomes, incoming input bindings, result contract, comment requirements, guards, completion/claim policy and optional named output and previous-decision visibility override. Workflow-version retirement prevents new selection while retaining existing references and compatible support.

Each human node MUST explicitly declare one structured-result contract shared by all its outcomes. Optional incoming `inputs` bindings supply review data with source-derived types; omission means an empty map. New authoring MUST omit human-node `inputContract`; published legacy definitions with the empty array remain readable without rewriting content or hashes. Nonempty scalar submission contracts remain unsupported. `startPolicy.inputContract` is unchanged. Outcome-specific contract overrides are outside the initial scope; guards and comment requirements belong to individual outcomes. Human-task outcomes MUST NOT have a dedicated permission field. Authorization is optional through declared host guards, which may receive fixed permission names as literal arguments. Omitting an authorization guard does not grant business access or bypass host policy. F018 provides a separate optional host submission-validation hook; hosts requiring business validation supply it, as described in C09. Structured results are explicitly forbidden, optional or required: forbidden requires absence, optional permits absence, and required needs a valid object. Any supplied result MUST be a valid object; top-level null is rejected in every mode, while nested nulls follow the schema. OPTIONAL and REQUIRED use an embedded schema under F018’s restricted Draft 2020-12 profile, including supported local acyclic references. External/versioned schema-reference resolution remains deferred; unsupported references MUST be rejected. FORBIDDEN permits no schema. Publication MUST reject unsupported or mutable contracts. Existing simple tasks remain supported without a result. Retain readers, validators and host capabilities needed by published definitions and retained evidence; task-type business versions are not required for this capability.

The initial language uses integer schemaVersion 1, key and definition version fields, and exactly one START node as its entry point without a separate startNodeKey. Start-input contracts MUST be explicit, including when empty; language design section 12.1 defines their nesting and descriptor fields. Omitted guards means an empty list. Start authorization is optional through declared host guards: startPolicy MUST NOT contain permission and core MUST NOT require a separate start authorization hook. Without an authorization guard, core performs no start authorization check; declared guards and all other workflow rules still apply. Human-task outcomes use the same optional authorization-guard model. L18 and the delivered feature specifications settle supported document fields, defaults, schemas, host APIs and encoding/validation contracts. Unsupported extensions still require specification before implementation.

Task types use a simple `workflow_task_type` catalog with codes immutable from creation, retained rows, editable descriptive metadata, an authoring `selectable` flag and a technical concurrency version. They have no business-version or publication lifecycle. Renaming codes and physically deleting rows MUST NOT be supported, even for unused entries. `selectable = false` prevents new authoring selection; it MUST NOT invalidate published definitions or prevent their execution, including new instances of those definitions. The activity holds the task-type reference; its tasks inherit that type. F002 specifies the catalog service and F014 supplies shared administration. Any additional catalog-import contract remains separate specification work; no versioned task-type import lifecycle is mandated.

Catalog metadata is not executable behavior. Publication checks catalog references, node contracts and capabilities supplied by the deployed host. Unsupported task types must fail visibly. APOLO resolves screens and handlers by stable task code and retains compatibility with published workflow contracts. V1 has no separate form key/version contract.

## C08 — Expressions are restricted, explicit and deterministic

Implemented V1 routing uses restricted SpEL over validated `#vars` projections. `#facts` remains unsupported until a declared provider/snapshot/fingerprint contract is specified; it MUST NOT silently resolve to an empty map. Conditions MUST return actual Boolean values. Evaluate non-default conditions in the explicit priority order declared by the definition and select the first true result. Stop evaluation at that match; later conditions MUST NOT be evaluated or recorded as false. Overlaps are resolved by priority. If all conditions are false, use the separately identified unconditional default; if absent, fail the command. At most one default is permitted. Missing required input, invalid conversion, non-Boolean results and errors in an evaluated condition MUST fail the command without trying later routes or the default.

Publication MUST validate every condition's syntax and permitted expression features. The definition MUST preserve evaluation order, and the designer MUST expose priority independently of diagram layout. Published order is immutable and instances retain their pinned version. Relative order of a gateway's conditional transitions in the top-level transitions array defines priority; its default is considered only after all conditions are false, regardless of position. Section 12.1.16 of the language design defines the JSON fields. F008/F009 specify the supported evaluation and diagnostic contracts; optional unreachable-route warnings do not imply complete static overlap detection. This routing rule does not introduce the deferred decision-table engine or selectable matching policies.

Expression rules MUST be centrally enforced as part of the declared workflow-language version. Definitions MUST NOT select an independent expressionPolicy, and host configuration MUST NOT substitute different expression semantics for that version. Incompatible expression-rule changes require a new language version; an engine upgrade must preserve a supported version's meaning or reject it explicitly.

Expression rules MUST allow only specified syntax and read-only access to bounded data. They must exclude type/constructor/bean access, general method invocation, assignment, mutation and access to arbitrary application objects. A restricted evaluation context alone is insufficient evidence of safety.

Time and other decision inputs must be supplied explicitly; expressions cannot fetch business data or read hidden mutable globals. Specify limits for expression size/complexity, inputs and evaluations, plus stable errors, before implementing evaluation.

Initial scalar types are STRING, LONG, DECIMAL, BOOLEAN, DATE and DATETIME. Preserve exact declared-input decoding, transport and storage, and define explicit date/timestamp semantics. Expression arithmetic retains native SpEL numeric behavior. F007/F009 specify exact encodings, precision, nullability and date/time semantics for the delivered value types. Unsupported versions and semantic features MUST be rejected.

A task may submit a bounded JSON object containing nested objects/arrays under its pinned result contract. Core validates structure and bounds; the host validates business meaning. Reject duplicate JSON keys and inexact conversions. F018 specifies and implements the schema profile, 64 KiB UTF-16 result ceiling, depth/collection/string limits and versioned canonicalization; these remain distinct from the larger execution-value limits. Task submissions are not automatically exposed or merged into expressions/variables. Declared services may aggregate exact-activity submissions and return validated scalar or JSON outputs through explicit bindings without changing the original evidence.

JSON is an additional execution-variable type for objects and arrays, including nested combinations. Its declared origin, nullability and permitted writers belong to the pinned workflow definition, including explicitly configured human outputs. In the initial JSON start/service/variable slice, per-field structure schemas are deferred: accept arbitrary nested fields within JSON validity, exact-value and resource constraints. Workflow-document validation and task-result schemas remain unchanged. APOLO supplies serialized neutral data; core does not serialize host DTOs. Current values are mutable execution state stored in workflow_variable.json_value; task submissions remain immutable. Preserve existing scalar types and absent/explicit-null semantics. JSON variables use SQL NULL for explicit top-level null; nested nulls are ordinary JSON data. No arbitrary Java-object serialization is permitted.

Initialize or replace complete JSON values only through pinned start/service bindings and explicitly configured human outputs, under the same instance concurrency and transaction protocol as other variables. No standalone variable-update command is delivered. Include the full submitted value in versioned fingerprints and retain required write/routing evidence independently of current state. Read-only object-key/array-index navigation under #vars must be explicitly allowlisted and bounded; missing object properties in F009 project to null, allowing hosts to omit null-valued fields. Undeclared/uninitialized variables, incompatible operations and invalid index types still fail; F009 D06 makes out-of-range integer array reads return null without reverse indexing or mutation; F009 D05 requires explicit per-access `?.` for null-safe property traversal; ordinary property access on null fails. F009 implements D09’s standard SpEL navigation, including explicit null-safe indexing, with the agreed JSON adaptations. Stored absence and explicit null remain distinct. No implicit deep merge, nested mutation, method access or arbitrary JSON-path search is enabled. F021 supersedes the earlier F009 capacities with 8 MiB UTF-16 per ordinary JSON value and 10 MiB UTF-16 per current-variable/input/output map, with coordinated evidence and transport bounds in its [capacity contract](features/F021-all-collective-review/spec.md#c01--capacity-contract). Individual task results retain the 64 KiB limit. F009’s scoped pre-baseline compatibility exception is retained in C10; codecs and bounded navigation have delivered contracts and scoped evidence, without establishing APOLO compatibility. Storage does not imply indexed querying.

An optional pinned human-node `outputVariable` creates a JSON variable without a separate top-level declaration: for SINGLE, only when an accepted completion supplies a result; for ALL, only when the activity resolves and its original collection is available. Reject name collisions and preserve explicit absence and bounded existence checks. No row or capacity is reserved on entry, and partial ALL contributions create no output. Later declared service bindings may replace the whole value under ordinary instance-variable visibility; the original submission/collection evidence remains immutable. Explicit submission-by-node-key service/human bindings read that original evidence, not the mutable output copy. F019/F021 specify exact occurrence selection and bounded collection contracts; repeated-activity/loop selection remains deferred.

## C09 — Host policy and trusted identity govern business actions

Explicit human-node input bindings MUST capture immutable, bounded review data at task creation in the entering command's transaction. The copy MUST follow the receiving task's current read authorization, including through history details, without granting source-task access. It MUST remain separate from reviewer submissions and MUST NOT refresh implicitly. F020 specifies SINGLE snapshots; F021 resolves one shared immutable input snapshot at ALL activity entry for the fixed roster. Host business invalidation policy remains independent.

APOLO owns booking data, forms, validation, assignment sources, permissions, materiality rules and domain orchestration. Core MUST NOT encode overbooking calculations, country routing or alternative-resource policy.

APOLO owns booking-to-workflow associations by storing the engine-issued instance ID in host data and using the engine API to retrieve instance state, tasks and history. Several bookings may share an instance ID. A booking column or host association table may represent the links according to cardinality and history needs; this constitution does not mandate a host table. APOLO resolves and authorizes related bookings when composing task details or applying business effects. Prior execution links and reviewed membership must remain available when current associations change. A JSON variable may hold a booking selection as execution context; it does not replace host associations or establish membership/authorization. Partial ALL contributions must not alter shared review material, including JSON variables.
